# 性能基线

> 用途：**判断"慢"是否真的慢**。没有基线的时候，人容易往错的方向优化
> （README 的 AOT 红线第 9 条记录过：以为没达标，花半轮优化一件早就达标的事）。
>
> 数据来源：`bench/` 下的工程，WSL2 / 单机，tpc 0.9.6，**`-O2`**。

## 场景容量（v0.12.0 实测，单进程纯逻辑）

吞吐之外的另一组基线：**一帧能推进多少东西**。判据是 20Hz 的 50ms 预算。

| 形态 | 规模 | 单帧耗时 | 说明 |
|:--|:--|--:|:--|
| 房卡房 | 1,000 房 × 20 人 | 10.8 ms | 按 20 人房折算；MODE_SHARED |
| 房卡房 | 4,000 房 × 20 人 | 43 ms | 单 worker 接近上限 |
| 副本 | 200 个 × 20 人 | 2.07 ms | 一房一 Service（MODE_DEDICATED） |
| 副本 | 500 个 × 20 人 | 5.41 ms | |
| 万人世界 | 1 万实体 / 单场景 | 9.61 ms | 密度 1 人/格 |
| 万人世界 | 2 万实体 | 19.91 ms | 仍线性 |
| 万人世界 | 3 万实体 | **44.78 ms** | 超线性（密度效应） |
| 对照 | EntitySet 推进 1 万实体 | 2.60 ms | 不含 AOI |

**读法**：

- 这些是**纯逻辑**（移动 + 换格 + 视野差集），不含广播编码和网络发送。
  广播按 1KB 包 ≈ 23 µs/消息另加（见下面的吞吐表）。
- 世界超过 **2 万人**就不是"优化 AOI"的问题了，是密度导致视野差集变贵——
  该按位置分区（见 `scene-carrier.md` 第一节）。
- 载体本身很便宜：一个空 Service 322–333 B，带帧定时器 780–802 B。

完整数据与测量方法：`bench/SCENE-CAPACITY.md`、`bench/service-cost/`。

## 一、单机核心指标

| 场景 | 数值 | 说明 |
|:--|:--|:--|
| 单服务吞吐（echo） | **1,144k msg/s** | 单 worker、单消息往返 |
| 单条消息成本 | **874 ns** | 含解码 + 分发 + 编码 |
| 10 万定时器注册 | **1,339 ns/个** | 一次性注册耗时 |
| 200 实体单帧 | **67 µs** | 帧循环里遍历 + 广播 |
| AOI 格内移动 | **322 ns** | 单实体跨格 |
| 8 worker 在线 | **3.4 万** | 10Hz 心跳 |

## 一之二、大规模：帧预算怎么被吃掉的

单次操作成本（上一张表）**推不出**"1000 人能不能跑"——帧预算是"每帧所有工作的总和"，
必须实测。以下是 battle demo（`/data/tserver`，单 worker、30Hz、33ms 预算）的实测：

| 1000 人在线 | p50 | p99 | 备注 |
|:--|--:|--:|:--|
| 命中判定用全量遍历 | — | **40 ms** | 超帧预算，不可用 |
| AOI 按半径查询（`Scene::around`） | 4.1 ms | 20.3 ms | |
| + 事件改扁平元组 | 4.2 ms | **13.8 ms** | p99 −32%，p50 不变（压的是分配尖峰） |
| + 视野广播，每事件一条消息 | — | **65.9 ms** | 打爆：客户端发 3.6 万次施法，服务端只结算 2658 次 |
| + 事件按"一次施法"聚合成一条 | 4.1 ms | **15.2 ms** | 广播净成本只剩 1.4 ms |

**三条可迁移的结论**：

1. **AOI 不是"优化"，是"规模化的前提"**。200 人时它比全量遍历**慢一倍**
   （7.5 vs 3.3 ms），临界点约 245 人（全量 ~20 ns/人 vs 扫格 ~100 ns/格）。
   小规模别上 AOI，大规模必须上——"上 AOI 就更快"是错的。
2. **消息条数比字节数值钱**。一次 AOE 命中 12 人产生 13 条消息，合成 1 条后
   千人广播从 65.9 ms 降到 15.2 ms，而字节数只少一半。
   优化的第一刀应该砍"条数"，不是砍"大小"。
3. **p99 在 200~1000 人区间噪声很大**（同一份代码两次测能差 5 ms）。
   做 A/B 时看 **p50**，或交替多轮取中位比值；别拿单次 p99 下结论。

## 二、先确认是不是 `-O0`

**这是最容易踩的坑**：手写 `project.yml` 漏 `-O2`，所有指标**偏低约一倍**，而且不会报错。

| 指标 | `-O0`（错） | `-O2`（对） | 倍数 |
|:--|:--:|:--:|:--:|
| 单服务吞吐 | 510k msg/s | **1,144k** | 2.2× |
| 单条消息成本 | 1,959 ns | **874 ns** | 2.2× |
| 10 万定时器 | 4,300 ns/个 | **1,339 ns** | 3.2× |
| 200 实体单帧 | 176 µs | **67 µs** | 2.6× |
| AOI 格内移动 | 940 ns | **322 ns** | 2.9× |

**判据**：如果你的数据大约只有上表的一半，**先别优化代码**，确认编译参数：

```bash
grep 'cxx-flags' project.yml     # 应该有 -O2
```

`project.yml` 必须由 `tsf build` 生成，不要手写。

## 三、怎么测才可信

**不要拿两次先后测量的结果做比较。** 框架存档
（`docs/archive/tsf-readme-full.md` §5.7）记录过一次事故：
因为顺序采样（先测 A 再测 B），把机器抖动（当轮变异系数 106%）当成了代码差异，
得出"`mixed` 参数慢一倍"的错误结论。

**正确做法**：

1. **编两个只差一个变量的二进制**（比如 `mixed` 版和 `string` 版）
2. **交替压测**，记录**比值**（让机器漂移在比值里约掉）
3. **取多轮中位数**
4. 微基准也要看（`bench/probe-types` 那种）

```bash
# 交替 5 轮，每轮记录 A/B 比值
for i in 1 2 3 4 5; do
    a=$(./bench_a | tail -1)
    b=$(./bench_b | tail -1)
    echo "第${i}轮  a=$a b=$b 比值=$(echo "scale=3; $a/$b" | bc)"
done
```

**看中位比值**，不看单轮。

## 四、常见"假性能问题"

| 现象 | 先查什么 |
|:--|:--|
| 吞吐只有一半 | `-O2` 是不是漏了 |
| 延迟突然从 0.2ms 涨到 100ms+ | **闭包引用参数没回写**，同一帧被重复解析（AOT 红线第 5 条） |
| 内存一直涨 | 限流/会话表的桶没 GC，或信箱没上限（README「信箱是有界的」） |
| 连接数到某个值就 OOM | `ulimit -n` 截断了 `max_conn`（AOT 红线第 10 条） |
| 单次跑得快，跑 10 分钟变慢 | 定时器泄漏 / GC 压力 / 日志文件没轮转 |

## 五、什么时候才该优化

按这个顺序判断：

1. **有没有达标？** 对比上面第一张表。差 10% 不值得动。
2. **是不是 `-O0`？** 差一倍几乎都是这个。
3. **是不是"重复劳动"？** 延迟爆炸但吞吐正常 → 查 AOT 红线第 5 条（引用参数）。
4. **是不是测量方法有问题？** 顺序采样、样本量不足、没取中位。
5. **以上都不是**，才考虑改代码或改架构。

> **优先怀疑测量，其次怀疑配置，最后才怀疑代码。**
