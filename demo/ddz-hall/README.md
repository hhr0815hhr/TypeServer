# ddz-hall —— 斗地主：大厅 + 房间列表 + 房卡

用 `14-architecture.md` 那套分层写的完整示例。**能跑、有单测、结构清楚**。

```bash
tsf build .
./ddz_hall               # 监听 9061
php85 client.php         # 另开终端，三开验证全链路
php85 tests/run.php      # 规则单测：53 条断言，不编译、不起服务
```

`client.php` 会模拟三个玩家：登录 → A 建房（扣房卡）→ 看房间列表 → B/C 加入
→ 三人齐自动开局 → A 出牌。输出 `OK: 大厅 / 房卡 / 房间列表 / 开局 / 出牌 全链路通过`。

## 几个设计决定，以及为什么

**牌用 int 不用对象**。一副牌 54 张，每局频繁比较、排序、做频次统计。`int` 的数组操作
是 AOT 下最快的形式；`Card` 对象会带来 54 次分配和每个属性访问一次间接。牌是**值**，
没有身份、没有生命周期。

**房间状态全放成员变量，不放静态属性**。静态属性在进程里是全局的，两个房间同时开
手牌会互相覆盖；成员变量随 Service 销毁一起没了。

**大厅不暴露 `roomList()` 给房间调**。第一版写了 `public function roomList()`，让房间直接调，
等于把两个 Service 焊死在一个进程里——拆进程那天会发现调不通。现在列表请求也是
发消息进来的，房间和大厅之间只有地址 + 消息。

**handler 只做"解析 JSON + 投递"**。六个 handler 长得几乎一样，抽成了 `postLobby()`。
少写五份就少五处能写错的地方（少传一个字段、op 写错），改内部消息结构时也只改一处。

**房卡扣在大厅**。房价 `1/2/5` 张按档位，新玩家 10 张。真实项目这笔账属于玩家资产，
应该在 `PlayerService` + `Infra/Repo`（带事务、带流水），这里用进程内 map 代替。

## 简化（不影响玩法正确性）

| 简化 | 真实做法 |
|:--|:--|
| 没有叫地主，座位 0（房主）直接当地主 | 一轮叫分（1/2/3 分或不叫） |
| 没有"准备"，三人齐自动开局 | 各自点准备，房主点开始 |
| 房卡在内存，重启即清 | PlayerService + DB + 流水 |
| 房间打完整局就销毁 | 可续局（房主再开一局） |
| 断线不重连 | 断线保留座位 N 秒，重连恢复 |
| 飞机带翅膀只支持带单/带对 | 支持翅膀是三张的拆解 |

## 牌型覆盖

单张、对子、三张、三带一、三带二、顺子、连对、飞机、飞机带单、飞机带对、
四带二、四带两对、炸弹、王炸。

比大小：王炸 > 炸弹 > 同型同长比主点数。不同型不同长一律压不了
（炸弹压普通牌是唯一的跨型例外）。

## 想继续加什么

- **叫地主**：在 `Doudizhu::start()` 前面加一个叫分阶段，三个阶段（叫分/抢地主/明牌）
- **断线重连**：`RoomService` 记录 uid → 座位，重连时用同 uid 找回来
- **战绩**：结算时写 `Infra/Repo`，大厅加一个"我的战绩"接口
- **观战**：房间多一个"旁观者"列表，只收 `PUSH_PLAY` 不收 `PUSH_DEAL`
