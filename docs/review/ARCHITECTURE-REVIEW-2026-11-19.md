# TSF 架构评审：与成熟游戏服务端架构的对比

> 评审对象：`D:\hhr\TypeServer`（tsf 子模块 `a84f10f`，`tsf 0.10.0`）  
> 评审日期：2026-11-19  
> 评审方式：源码通读 + 在 `tsf:latest` 容器与 WSL 副本上实跑测试与基准  
> 原则：本文所有"实测"数字均可复现（命令见 §11）；所有"评估"与"外部对标"明确标注为判断

---

## 一、一句话结论

TSF 是**把 Skynet 的 Actor 模型用 PHP + AOT 重新实现了一遍**，并且在"钱"这条路径上的工程纪律明显高于同体量的自研框架（幂等、重放、对账都有测试兜底）。  
它的定位不是"通用游戏服务端平台"，而是**单机、单玩法、强正确性优先的房间/活动服框架**。  
当前最大的三个约束是：**集群只支持单机（Unix socket）**、**没有代码级热更**、**工具链单人维护且预发布**。

## 四、运行模型（实际代码）

### 4.1 调度：单进程 Actor + 就绪队列

```
业务代码 ──deliver()──> 目标 Mailbox ──tick()──> Service::onMessage()
```

- 地址是 `(nodeId, localId)` 打包的整数；`deliver()` 用一次位运算决定走本地信箱还是 Cluster。
- 就绪队列 FIFO，每服务每轮预算 200 条（防饿死），撞预算则排到队尾。
- 定时器到期**不直接回调**，而是投一条消息进信箱——保证服务执行路径唯一，不存在重入。
- 服务抛异常 = **销毁该服务**（`onCrashed`），受监督服务按 `maxRestarts / withinMs` 重启，超限放弃。这是刻意的"钱优先"选择。

### 4.2 与 OTP 的对应关系（作者自己列过，我核对后确认成立）

| OTP                    | TSF                        | 成立度                   |
| :--------------------- | :------------------------- | :-------------------- |
| `gen_server` + mailbox | Service + Mailbox          | ✅                     |
| pid 位置透明               | `Addr::pack(node, id)`     | ✅（但 node 目前只能同机）      |
| supervisor + 重启强度      | `Scheduler::supervise()`   | ✅ 语义一致，**状态不保留**      |
| `code_change/3` 状态迁移   | `Snapshot\Schema` 迁移链（§18） | ✅ 协议一致（机制不同：阈值步骤而非回调） |
| per-process heap       | 无（worker 内共享堆）             | ❌                     |
| 抢占式调度                  | 无（协作式，只能事后记账）              | ❌                     |
| 两版本模块共存                | 无（PHP 类表只增不减）              | ❌                     |

**判断**：这不是"PHP 版 Erlang"，而是"PHP 版 Skynet"。差异在失效模型——Skynet 服务崩了也不重启，靠上层；TSF 多了 supervisor，比 Skynet 更接近 OTP。

### 4.3 集群：最强的能力，也是最大的天花板

评审当时，`tsf/src/Cluster/Cluster.php` **只实现了 Unix domain socket**：

```php
stream_socket_server("unix://" . $this->path, ...);   // 评审时的 :70
stream_socket_client("unix://" . $path, ...);         // 评审时的 :82
```

配套的服务发现是**本地文件注册表**（`{node}.json` + `{node}.beat`，靠 `scandir` 轮询）。

**这意味着**：`node_id` 1..255 的地址空间是为多机设计的，但**实现只能跑在同一台机器上**。  
`Shard\Router`、`CircuitBreaker`、`Discovery` 这一整套跨服基础设施，在单机上跑得通，跨机跑不通——换传输层（TCP + 握手鉴权 + 序列化协商）是必须补的一课。

> **2026-11-20 已补传输层**（§13）：`tcp://host:port` 与 unix 同一套 API，每条连接先握手  
> （节点号 / codec / HMAC 三校验，失败带原因）。  
> **同一天也补了节点目录**（§14）：`pkg/registry` 的 `RedisRegistry` 替代本机文件注册表。  
> 也就是说"传输 + 目录"都通了，跨机寻址这套基础设施第一次真正成立；  
> 仍然缺的是**分区与迁移**——那是上层策略，不是这一层的事。

### 5.3 三个最能说明差距的地方

**① 位置透明有了，跨机没有。**  
TSF 的 `Addr::pack(nodeId, id)` + `deliver()` 位运算，是 OTP/Skynet 那套"业务不关心目标在哪"的正确抽象。  
Skynet 用 `harbor` + TCP 把这条路走完；TSF 原本停在 Unix socket。  
**抽象对了，实现没走完**——这是"好的架构设计 + 未完成的工程"的典型状态。

> **2026-11-20 更新**：传输层已补上 TCP + 握手（§13），`tcp://host:port` 与 unix 走同一套 API，  
> 跨机传包可用。**但节点目录仍是本地文件注册表**（`Discovery\FileRegistry` 靠 `scandir` 轮询），  
> 跨机还没有中心化注册表——所以现在是"传输能跨机，目录还不能"，离"多机集群"还差一步。
>
> **2026-11-20 补齐**：`pkg/registry` 提供 `RedisRegistry`（自带 RESP，不依赖 php-redis），  
> 节点目录可以跨机了（§14）。至此"地址透明 + 传输 + 目录"三件套齐了，  
> 缺的是在这之上做**分区与迁移**（谁该搬、搬到哪、搬的时候玩家怎么办）。

**② 热更：文档诚实，代价真实。**  
`ARCHITECTURE-DESIGN.md` 明确写"进程内类替换不成立"，给出 T0（配置）/T1（闭包）/T2（滚动重启）三级方案，这一步比很多自研框架诚实。  
但对**运营期改玩法**来说，Lua 系（Skynet / C++ + Lua）能在**不丢状态**的前提下换逻辑，TSF 的 T1 只能放"几十行、无热点"的薄逻辑，T2 会丢进程内状态（靠快照 + 重连兜）。  
**对活动频繁、需要紧急修 bug 的线上游戏，这是最大的运营短板。**

**③ 钱这条路径，反而比很多成熟框架做得好。**  
`pkg/eventlog` 的 seq + 幂等 ref + 启动全量重放 + 崩溃对账，配 91 + 14 项测试（含 3 轮 `kill -9` 后 `dup=0 torn=0`）。  
Skynet 官方不带这种设施；传统 C++ 服通常有，但很少有可跑的回归测试。  
**这是 TSF 真正可以被借鉴的部分。**

## 七、性能定位

| 层              | TSF 实测                       | 同层参考（量级，非本次实测）                                 | 差距判断                        |
| :------------- | :--------------------------- | :--------------------------------------------- | :-------------------------- |
| Actor 调度（进程内）  | 115 万 msg/s / 870 ns         | Skynet ≈ 数百万/s；Go channel ≈ 100–300 万/s        | **同量级**，PHP AOT 在这里不落后      |
| 网络回环（每消息）      | 29 µs @ 3.4 万/s              | Skynet ≈ 5–10 µs；Go ≈ 10–15 µs；Node ≈ 30–50 µs | **落后 Skynet 3–5 倍，优于 Node** |
| 单机在线（10 Hz 心跳） | ≈ 3,400 在线/worker（按 1KB 帧折算） | C++ 服 1–3 万/进程                                 | 差 3–10 倍                    |
| 增量编译           | 101 文件 17.6 s                | —                                              | 迭代速度可用，但冷构建仍受 C++ 约束        |

**结论**：AOT 把 PHP 从"PHP-FPM 级"拉到了"接近原生逻辑层"，但**网络路径的固定开销（Swoole 回调 + PHP 闭包 + 帧编解码）无法靠 AOT 消掉**。  
对回合制、房间制、活动服（单局消息量中等）够用；对 30 Hz 状态同步的 MOBA/FPS 不够。

## 八、场景适配判断

### 适合

1. **单机房间类玩法**：棋牌、1v1、回合制、小局制对战（这正是 `demo/duel` 的形态）。
2. **活动服 / 跨服排行**：状态可外置、生命周期短、需要快速迭代。
3. **已有 PHP 团队**的游戏公司：把现有 PHP 业务能力直接搬到服务端，人效优势明显。
4. **强正确性场景**：金币、订单、结算——`eventlog` + 幂等 + 对账是现成资产。

### 不适合

1. **重度 MMO 的全量迁移**：传输层已可跨机，但服务发现仍是本机文件注册表，节点目录没有中心化，`Shard`/`Router` 的透明寻址在跨机场景下还缺"目录"这一环。
2. **要求不停服改逻辑的线上项目**：没有代码级热更，T2 丢状态。
3. **高频状态同步（30 Hz+）**：3.4 万 msg/s/worker 撑不住百人同屏。
4. **平台化中台**：缺中心化注册/配置中心/链路追踪，运维能力停留在"打日志"。
5. **团队没有 AOT 子集纪律**：`mixed`、动态调用、`switch` fallthrough 都会静默降级或报错。

## 十二、D1–D3 修复记录（2026-11-19）

### D1 · `tsf doctor` 的 phpx 路径改为从 TPC 推导

改 `tsf/bin/tsf`：不再写死 `$HOME/typephp-src/...`，改为按以下顺序解析，取第一个存在的：

3. 报告时给出实际尝试的路径，而不是一个不存在的默认值

### D2 · 行尾规则入库

新增 `.gitattributes`（父仓库 + `tsf` 子模块各一份），只钉「必须在 Linux 上被解释执行」的两类：

```gitattributes
*.sh   text eol=lf
*.bash text eol=lf
/tsf/bin/tsf text eol=lf      # 子模块内写作 /bin/tsf
```

**为什么不用 `* text=auto eol=lf`**：本仓库 blob 已是 LF，但 `core.autocrlf=true` 会把它检出成 CRLF；  
加全局规则等于让 892 个文件同时产生行尾 diff，噪音会盖住真实改动。只钉脚本与入口，收益全覆盖、代价为零。

同时 `.gitignore` 补了 `!.gitattributes`——这个仓库用「白名单」忽略（首行是 `*`），  
不加这行新文件根本进不了库，正是它自己注释里警告的「本机有、clone 没有」。

**复验**：`git check-attr eol` 对 `.sh` 与 `bin/tsf` 返回 `lf`；重新检出的脚本首行是 `\n` 结尾；  
`bin/tsf` 的 shebang 恢复为 `#!/usr/bin/env php85` 且可执行。

### D3 · `Room` 与调用点的 API 对齐

`b0f6b5f`（状态机从 Room 外移）删掉了 `start()` / `finish()`，但**消费方全都没有同步**。  
本次按「状态机由业务注入」的既定设计对齐，而不是把旧方法加回去（加回去等于把 start/finish  
语义重新焊进 Room，正是那次重构要拆掉的东西）。

| 文件                                 | 改动                                                                                               |
| :--------------------------------- | :----------------------------------------------------------------------------------------------- |
| `tsf/pkg/room/src/Room.php`        | 补 `uids()`（纯成员表委托）；`toArray()` 带 `maxPlayers`；新增静态工厂 `fromArray(array $d, ?Machine $fsm = null)` |
| `tsf/pkg/room/src/RoomService.php` | `MSG_START` / `MSG_FINISH` 改走 `fireRoom()` → `fsm()->fire()`                                     |
| `tsf/pkg/room/src/RoomHost.php`    | `OP_START` / `OP_FINISH` 同上                                                                      |
| `demo/duel/src/DuelRoom.php`       | 新建房间改为 `ThreeStage::room()`（原来是不带状态机的裸 `Room`）；`ready()` 与 3 处结算改走 `fire()`；`fromArray()` 传入状态机  |

两个顺带修掉的*真问题：*

- ***快照丢容量**\*\*：`toArray()` 原先不带 `maxPlayers`，恢复时只能按默认 8 人重建，  
  一个 2 人房会变成"还能再进 6 个人"。现在带上并在 `fromArray()` 里读回。*
- ***静默失效**\*\*：`DuelRoom` 原先 `new Room($id, 2)` 不带状态机，`ready()` 走的是已*删除的方法；  
  就算只把调用改成 `fire()`，没有状态机也永远返回 false——所以必须同时改构造。

### D3 续 · `room-test` 重写时暴露的三处语义缺口

`tests/room-test` 是 D3 的同源受害者：它整套写在"状态机还在 `Room` 里"的年代，  
而且 `project.yml` 的源码路径指向 `bench/room-test/main.php`（该目录不存在），  
既编不过也没进 `tsf verify`——所以 `Room` 重构后它烂了半年没人发现。

重写它（并补 `run.sh`）时，三处不是改名字就能过的语义缺口被迫显形：

| #  | 缺口                                              | 现象                                                                                                                | 处理                                                             |
| :- | :---------------------------------------------- | :---------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------- |
| 1  | `Room::close()` 不触发状态机的 `close` 边               | `ThreeStage` 从 WAITING/PLAYING/SETTLED 都声明了 `close` 边，却没人 fire——三条边是死代码；而且"关闭"之后 `fire("start")` 仍然成功（状态机不知道房间关了） | `close()` 置标志后 `fsm->fire("close")`；重复调用早退                     |
| 2  | `loadFrom()` 不读回 `closed`                       | `toArray()` 写了 `closed`，恢复时忽略 → 已关闭的房间恢复后又能收人（快照往返丢字段）                                                            | 补读回                                                            |
| 3  | `RoomService::onFrame` / `RoomHost::tick` 无条件推进 | 旧版这层判断在 `Room::tick()` 里（它认状态）。状态机外移后 `Room::tick` 只管"已关闭/负 delta"，于是 WAITING 和 SETTLED 阶段也在涨帧、快照一直变脏             | 两处都改为**仅 PLAYING 推进**；但 `beginFrame()` 仍每帧调用，否则等待期间的时间会堆到开战第一帧 |

第 3 条的细节值得记：不能简单"跳过着不调 beginFrame"——`beginFrame()` 负责推进  
`lastMs`，跳过会让房间从 WAITING 进入 PLAYING 的第一帧拿到整段等待的 delta  
（虽被 `maxDeltaMs` 截断，但那一帧的位置推进是假的）。

同时修正了两处注释与实现不符：`DuelService::onStop` 里"close 会清空成员表"（现在不清），  
以及测试用例里"SETTLED 后拒收玩家"（`Room` 不再解释状态，业务需自己看 `state()`）。

### D4 · 为什么没在本仓库修

D4 的根因在 `tpc`：它对 `private Room $room;` 这种**已声明类型**的属性调用不做方法表校验，  
所以 `$this->room->start()` 编译零告警。修它要改 typephp 编译器（属性类型 → 类方法表 → 报错），  
属上游工程，本仓库改不动，硬改工具链只会让"本地能编、别人编不过"。

本仓库能做的替代是**运行期冒烟**：构建每个 demo 并启动 2 秒、扫日志里的

|                                                     |                                          |
| --------------------------------------------------- | ---------------------------------------- |

## 十三、P1 · Cluster 跨机传输 + 握手（2026-11-20）

### 做了什么

| `src/Cluster/Cluster.php` | 地址解析（裸路径 / `unix://` / `tcp://host:port`）；`listen/connect` 双传输；`poll()` 驱动握手；`hasPeer/peerNodes` 改为"握手完成才算通"；`closeAll` 只对 unix 删 socket 文件 |

### 握手协议

```
连接建立 → 双方各发: "TSFC\x01" + Packet(msgId=0, payload="node\x1Fcodec\x1Fnonce\x1Fmac")
校验: 节点号范围 / 不是自己 / codec 一致 / mac = HMAC-SHA256(secret, node|codec|nonce)
通过 → 认这条链路；不过 → 断开 + 记 hs_fail + 日志带原因
```

为什么值得做：旧版靠"第一个包里的 src 节点位"认身份。Unix socket 时代意味着  
"本机任意进程都能自称 node 7"；到了 TCP 就是"任意人可冒充"。握手把身份从  
**数据里声明**变成**连接时证明**。

三条拒绝原因给的是可操作信息，而不是一个布尔：  
`bad-magic`（对方不是 TSF）/ `bad-mac`（密钥配错）/ `codec-mismatch:json!=raw`（两端协议不一致）。  
这三者的处理方式完全不同——只回一个 false，排障时只能猜。

### 兼容性

**裸路径仍是 unix**，所以 `tests/{breaker,shard-router}-test`、`bench/{rpc-cluster,shard-cross,breaker-live,cluster-bench}`  
一行不用改。UDS 路径在新协议下实测 2000 次往返 p99 274 µs（阈值 500 µs）。

### 复验

```
PASS  cluster-chan   集群通道/握手（TCP 11 项 + UDS 2000 往返）   15.3s
通过 12 / 失败 0 / 跳过 0
```

TCP 侧断言覆盖：建链、双向认节点、传包与 `src` 带节点号、垃圾字节被魔数拦、  
密钥不符、codec 不符、重复节点号（dup）。

### 这次**没有**解决的

1. **服务发现仍是本机文件**（`Discovery\FileRegistry`）。所以现在只能说"传输能跨机"，  
   不能说"多机集群可用"——节点目录还没有中心化版本。
2. **只校验不加密**：payload 仍是明文，能监听链路的人照样能读。要更强得上 TLS。
3. **重放只防最近一次**：nonce 由 hrtime+pid+计数器派生，服务端不缓存历史，  
   拿到旧 hello 且对端恰好下线时仍可能重放成功。真要防要窗口缓存或 TLS。

## 十四、P1 · Redis 服务发现（2026-11-20）

传输层补完之后，"跨机寻址"还差最后一环：`Discovery\FileRegistry` 读的是**本地目录**，  
跨机器只能挂 NFS——而 NFS 的 mtime 精度与缓存一致性不是给"每秒一次心跳"设计的。

### 新增包 `pkg/registry`（`TSF\Registry`）

| 文件                      | 作用                                                    |
| :---------------------- | :---------------------------------------------------- |
| `src/Resp.php`          | 极简 RESP 客户端（`stream_socket_*`，同步阻塞）                   |
| `src/RedisRegistry.php` | 实现 `Discovery\Contract\Registry`，与 `FileRegistry` 同契约 |

键布局：

```
tsf:node:{id}  →  JSON 身份（含 seen 毫秒时间戳），PX ttlMs
tsf:nodes      →  SET，成员是活跃过的节点号
```

### 为什么不用 `pkg/redis`


这是本次最值得记的一条：**php-redis 扩展类在 AOT 产物里不存在**。

实测：用 `pkg/redis` 的 `Client` 写一个最小工程，`tsf build` 报"Successfully compiled 66 files"，  
运行时却 `Uncaught Error: class 'TSF\Redis\Client' is undefined`。  
编译器把源码编进去了，但 `new \Redis()` 在产物里没有绑定——swoole 能用是因为 phpx  
给它做了绑定，redis 没有。

所以新包自带 RESP，走 `stream_socket_*`——和 Cluster 同一批原语，AOT 下已验证。  
这条也再次印证 D4：**"编译成功"不等于"类可用"**，编译期不校验类解析。

### 存活判定：两条机制各管一半

| 机制                | 管什么                         | 失效场景     |
| :---------------- | :-------------------------- | :------- |
| 键 TTL（`PX ttlMs`） | 进程被 `kill -9` 后**自动消失**，无残留 | —        |
| JSON 里的 `seen`    | 支持调用方传更小 ttl 做精细判定          | 依赖两端时钟同源 |

只靠 TTL，就只能回答"键在不在"；只靠 seen，崩溃进程的键会永久残留要另做 GC。

**心跳 1 次往返**：不读改写，而是用本地缓存的 `NodeInfo` 重写整个值（一百多字节），  
省掉一次 GET。缓存缺失（进程重启后接手旧键）时才退化成读改写。

### 两个踩到的工程坑

1. **新包必须在 `project.json` 的 `packages` 里声明**。手写进 `project.yml` 的  
   `sources` 会被 `tsf build` **静默改写掉**——表现是"文件明明在，编译却不报错，  
   运行时类不存在"。这个坑和 D4 叠加后极难查：没有任何一处报错。
2. `tests/registry-test` 的断言一开始写的是"节点总数 === 1"，但前面用例注册的节点  
   还在有效期内。**计数型断言在共享存储上天然脆弱**，改成"列表里有没有这个节点"。

### 阻塞语义（部署时必须知道）

每条命令一个 RTT，同步阻塞。在 `Service::onMessage` 里调它，整个 worker 会被挡住  
（本机 ~0.2ms，跨机看网络）。所以：

- 单机：`refresh()` 放 1s 低频定时器，影响可忽略；
- 跨机：先开 `Scheduler::setCoroutine(true)` + `Runtime::enableCoroutine`。

### 复验

```
PASS  registry    Redis 注册表（25 项，无 Redis 则 SKIP）   15.5s
通过 13 / 失败 0 / 跳过 0
```

覆盖：注册可见、字段往返（endpoint/codec/tags/entry）、跨连接一致、`refresh()` 只对  
身份变化回调（心跳不算）、注销立即收敛、TTL 过期（模拟 kill -9）、心跳续命、  
调用方传更小 ttl 时按 `seen` 精判。

没有 Redis 时脚本打 `SKIP` 并返回 0——环境没装不该判红，但也别假装测过。

### 还没做的

1. **没有 watch/订阅**：变更仍是调用方定时 `refresh()` 轮询，Redis 的 keyspace  
   notification 没用上（AOT 下要长连接 + 推送解析，复杂度不低）。
2. **没有 pipeline**：`alive()` 是 `SMEMBERS` + `MGET` 两次往返，节点多时可以合并。
3. **无 TLS / 无哨兵**：连的是单点 Redis，挂了注册表就不可用。
4. **分区与迁移仍未做**：现在能"找到节点"，但还不能"决定谁搬到哪、搬的时候玩家怎么办"——  
   那是上层调度策略，也是下一步真正的工作量。

## 十五、P1 · 状态交接 handoff（2026-11-20）

### 先厘清"分区"到底缺什么

翻了 `src/Shard/`：`Ring`（一致性哈希 + 150 虚拟节点）和 `Router::ownerOf()` 都在，  
**"这个 key 该归谁"已经能算了**。缺的是后半步：归属变了，数据还在老节点上。

所以这一步不是"实现分区"，是"把状态交出去且不丢"。

### 新增包 `pkg/handoff`（`TSF\Handoff`）

```
源                                   目标
 |  begin(key, ver, state)             |
 |---- MIGRATE(key, ver, state) ------>|
 |                                    |  install(key, state, ver)
 |<--- ACCEPT(key, ver) --------------|  成功 → 源侧 onCommit（可删本地）
 |<--- REJECT(key, ver) --------------|  拒绝 → 源侧 onRollback（必须恢复）
 |  超时未回复 → 源侧 onRollback         |
```

三条不变量，测试就是照它们写的：

1. **失败必须能回滚**。`begin()` 只代表"已发出"、源侧仍持有状态；REJECT 或超时  
   把拥有权收回。**交接失败不能等于数据丢失。**
2. **重复投递不重复安装**。目标侧记 `installed[key] = version`，同版本再来只回 ACK。  
   这条不只是省事：重发时若重新安装，正在跑的对局会被覆盖回旧状态。
3. **同 key 同时只有一次在飞**。第二次 `begin()` 直接 false，不排队——排队会让  
   先后顺序依赖调度，排障时看不出来。

### 四个设计取舍

- **状态进出用闭包，不定义接口**。状态是房间快照还是玩家存档只有业务知道，  
  逼它实现 `MigrationPayload` 等于强改继承链；闭包只需在装配处写两个函数。  
  与 `pkg/script`、`pkg/snapshot` 一致。
- **`Transport` 是窄接口**（只有 `sendRaw`）。迁移的可测性全押在这一层：测试里  
  塞假实现就能测协议，不必起进程；以后换传输也只改一个类。
- **`expire()` 由调用方驱动**，不内置定时器。扫描频率取决于业务对"卡多久算失败"  
  的容忍度，框架不该替它决定（同 `FrameLoop` 的取舍）。
- **拒绝用返回值而不是异常**。拒绝是正常路径（对方版本更新、我这正忙），  
  用异常会把正常拒绝写进错误日志，把真故障淹掉。

### 踩到的两个坑

**① 协议号超过 65535 会被静默截断。**  
第一版把 msgId 写成 69001，落线上变成 3465：发送端 `send` 返回 true、接收端  
`handle` 里 msgId 对不上、两边日志都干净，只是"什么都没发生"。  
`Packet` 头的 msgId 只有 2 字节（18 字节头里最后两个），而 `Packet::encode()`  
当时直接 `chr(($msgId >> 8) & 0xFF)`——越界部分被悄悄丢掉。

修复分两处：协议号改到 64101–64103；`Packet::encode()` 增加越界检查并抛错  
（把静默数据损坏换成明确异常，代价是一次比较）。`cluster-test` 补了对应断言。

**② 命名撞车。**  
第一版包叫 `pkg/migrate`、类叫 `Migrator`，而 `pkg/db` 已经有一个做**表结构迁移**  
的 `Migrator`，`tests/migrate-test` 也是它的。改成 `handoff`——这个词更准确  
（状态换宿主），也让 grep 不互相污染。

### 复验

```
PASS  handoff    状态交接（120 项：含版本落后调度）               20.9s
PASS  rpc        RPC（50 项）                                    17.3s
PASS  checkpoint 事件日志检查点（23 项）                        17.7s
通过 14 / 失败 0 / 跳过 0
```

测试在**一个进程里**起两个 Cluster（各监听一个 TCP 端口）+ 两个 Handoff，手工驱动  
poll/flush。这样能精确控制"谁没收到包"——超时回滚只能这么测。

其中一条是刻意保留的"分叉点"断言：**目标侧装成功了，但源侧超时回滚了**。  
迟到的 ACCEPT 必须被忽略（否则源侧以为交接完成、把本地状态删掉），  
而目标侧那份可能已经被业务改过。这个分叉协议层消化不了，只能由业务按版本号裁定。

### 闸门 Gate：交接期间的请求去哪

协议层之上还差一环：交接要花一个 RTT 到几秒，这期间打到这个 key 的请求怎么办。  
三种做法里只有一种安全：

| 做法                 | 结果                           |
| :----------------- | :--------------------------- |
| 直接转发给新宿主           | **错的**：新宿主状态还是老的，这次改动会被交接覆盖掉 |
| 丢弃 / 让客户端重试        | 能用，但丢一次写，且要与幂等配套             |
| **本地排队、交接完成后按序补交** | 正确：队列与快照同一时刻，谁最终拥有谁消费        |

`Gate` 实现第三种。四态返回 `pass / queued / overflow / forward`，由调用方分别处理：  
本地处理、等结果、显式拒绝、转给新宿主。

**顺序不能反：先 `freeze()` 再 `export()` 快照。** 反了就有窗口——快照之后、冻结之前  
到达的请求既不在快照里也不在队列里，交接完成后凭空消失。这条写进了 README 和测试。

队列满返回 `overflow` 而不是静默丢弃：游戏服里静默丢一次操作，玩家只会觉得  
"点了没反应"，比报错难查得多。

### 测试怎么覆盖"联调"

除了协议本身的 26 项，还加了 9 项把 Handoff 与 Gate 接起来跑：  
冻结 → 排队两条 → 发起交接 → 成功则队列**按原序**交给新宿主、闸门转 FORWARD；  
拒绝则队列**按原序**回本地、闸门回 OPEN。这两条正是 README 让人照抄的装配方式，  
装配错了测试会直接红。

### Rebalancer：把三者串起来的编排层

`Ownership` 决定该归谁、`Handoff` 搬、`Gate` 挡请求，`Rebalancer` 只做**调度**：  
扫差异 → 限并发 → 收口结果。它自身没有业务语义，不知道 key 是房间还是玩家。

两个设计点值得记：

1. **结果用轮询而不是回调**。`Handoff` 的 `onCommit/onRollback` 只有一个槽位，业务已经  
   占了（它要自己删本地状态），调度器再抢同一个槽位就会互相覆盖。所以 `Handoff` 额外  
   留了 `lastResult()`，`Rebalancer` 每轮自己收口。
2. **失败要退避**。写测试时发现的：目标持续拒绝时，下一轮 scan 立刻重试，等于每轮把  
   同一份快照往链路上打一次。加了 `retryMs`（默认 1s）后才收敛。

限流不是优化而是必须：一次扩容可能牵动几千个 key，全量并发会吃满带宽，并让目标端同时  
收到几千份快照。`limit` 是同时在飞的上限，**背压比吞吐重要**。

### 还没做的（这条边界要说清）

覆盖到**协议 + 闸门 + 编排**了。还缺的都在"谁来触发、怎么保证不重复"这一层：

1. **与 Ring 变更的自动联动**：`scan()` 仍需外部周期调用。谁负责发现"成员变了"、  
   变更窗口内要不要暂停、扩容时先加节点还是先搬数据，这些都还没有默认答案。
2. ~~**多节点同时判定同一 key**~~：已由 §16 的归属租约解决（`Lease` + `RedisLease`）。  
   ~~残留：在飞交接不会被打断~~ —— 也已做：`Rebalancer::renewTracked()` 在 `scan()`  
   开头给在飞的交接续租，续不上就 `abort()`，目标侧卸掉已装的部分。  
   （这条曾长期标注"没做"，实际代码和测试都在，属于文档滞后。）
3. **跨 key 的一致性**：一个玩家的房间和他的背包分属不同 key 时，分开搬会出现短暂  
   "房间在新节点、背包还在旧节点"。要么按玩家分片（同 key），要么加迁移批次。这是业务  
   建模问题，框架只能提供 `limit` 和观察指标。

所以现在的状态是：**单键交接、闸门、限流编排都可信；"集群级再平衡策略"仍要业务自己定**。

## 十六、归属租约 Lease（2026-11-20）

### 补的是"谁实际在跑"

`Ring` 算出来的是**推导值**：同样的环、同样的 key，每个节点算出同一个答案。但推导  
只说明"应该归谁"，不证明"实际是谁在跑"。两种情况下两者会分叉：

1. 业务在两个节点上都 `own()` 同一个 key（代码 bug，或上次交接没清理干净）；
2. 交接途中老节点还没删、新节点已经装好，两个都认为自己持有。

分叉之后两边会同时发起交接，把同一份状态往两个方向搬——**这是最难恢复的一类数据错乱**，  
因为它不报错、只是数据分家。租约的作用是动手之前先"举手"：只有拿到租约的节点才有资格搬。

### 三个动作都必须原子

| 动作 | 非原子写法的后果                                 |
| :- | :--------------------------------------- |
| 取  | 两个节点同时 GET 到 nil，然后都 SET，双方都以为拿到了        |
| 续  | A 过期后被 B 拿走，A 的 `SET XX PX` 会把**别人的**锁续上 |
| 放  | A 过期后 B 拿到，A 直接 DEL 会删掉**别人的**锁          |

续和放看起来只是善后，其实比取更危险：取错了立刻能看出来（两边同时搬），  
续/放错了要等下一次事故才暴露。所以三个都走 `RedisLease` 里的 Lua 脚本"值是我的才动"。

值用 `节点号:进程号` 而不是节点号：同一节点重启一次，老进程的续期请求不该被认成新进程的。

### 两档实现，边界写在类型上

| 实现            | 位置             | 能力                        |
| :------------ | :------------- | :------------------------ |
| `MemoryLease` | `pkg/handoff`  | **只在进程内有效**，给单机部署与确定性测试用  |
| `RedisLease`  | `pkg/registry` | 跨节点真互斥（`SET NX PX` + Lua） |

`Rebalancer::useLease()` 是可选的：不配就退回"只信 Ring"（单机不该被迫起一个 Redis）。  
持有期间每轮 scan 在**剩余不足一半**时续期——每轮都续会把 Redis 变成每键每轮的写放大。

`RedisLease` 放在 `pkg/registry` 而不是 `pkg/handoff`，是为了不让 handoff 引入 Redis 依赖：  
handoff 的默认形态是"纯协议 + 纯编排"，能跑在没有任何外部存储的单机上。

### 撤销 abort：把"反悔"这一步补齐

租约有 TTL，就有"租约丢了"这个状态。此时在飞的交接如果继续走完，就会和已经接手的新  
持有者形成两份状态——这比失败更糟。所以补了撤销：

```
源                              目标
 |-- ABORT(key, ver) ---------->|
 |                             |  装过就 onUninstall + 记墓碑
 |<-- ABORTED(key, ver) --------|
 |  收到才真正回滚本地            |
```

两个必须做对的点：

1. **目标侧必须实现 `onUninstall`**。撤销若只做"本地不认"，目标侧那份还在——数据分家  
   比不撤销更糟。所以 `ABORTED` 的语义是"我这边已经清干净了"，不是"我收到了"。
2. **目标侧要有墓碑**（`key → 被撤销的最大版本`）。`ABORT` 和 `MIGRATE` 走两条独立链路，  
   可能乱序；没有墓碑的话，迟到的 `MIGRATE` 会把状态又装回去，而源侧已经回滚成"我持有"。

撤销等不到 `ABORTED`（对端崩了）时超时收敛，回滚原因是 `abort-timeout`——此时"目标侧  
可能还留着那份状态"是已知代价，比永远卡在 aborting 好。

### 复验

```
PASS  registry   Redis 注册表+租约（38 项，无 Redis 则 SKIP）   29.3s
PASS  handoff    状态交接（120 项：含版本落后调度）               20.9s
PASS  rpc        RPC（50 项）                                    17.3s
通过 14 / 失败 0 / 跳过 0
```

租约侧覆盖：互斥（第二个实例拿不到）、`holds` 一致、别人的续不了、释放后可再取、  
TTL 过期后别人能拿且原持有者续不上（这四条是"过期即失效"的核心，缺一条就可能锁死 key）。  
编排侧覆盖：拿不到租约时不发起、被拒的 key 不会被冻结、交接成功后释放租约。  
撤销侧覆盖：装完再撤销（目标卸掉）、撤销后同版本重发被墓碑拦住、撤销前的 ACK 不产生  
commit、无在飞时 abort 空操作、等不到 ABORTED 时超时收敛。

还有一条端到端的：`LoseLease` 模拟"续不上租约"，断言在飞交接**被撤销**而不是硬走完——  
这正是这次要解决的问题。

### 仍没做的

1. **撤销后的墓碑永久保留**：每个被撤销过的 key 在目标侧留一条记录（`key → ver`）。  
   key 空间有界时无所谓，玩家 ID 这种无界 key 需要按时间清理。
2. **租约与 Ring 的成员变更没有联动**：节点被剔除后它的租约只能等 TTL 过期，  
   没有"主动清理离场节点租约"的路径。
3. **`ABORTED` 没有重试**：对端短暂不可达时只能靠超时收敛，收敛后两边状态可能不一致  
   （目标侧还留着），需要业务按版本号做一次对账才能彻底消除。

## 十七、P2 · 事件日志检查点（2026-11-20）

### 问题：启动时间随日志线性增长

`EventLog` 只追加，恢复 = 从头重放。账本跑三个月就是几十万条事件，**每次启动都重算  
一遍已经确定的历史**。这不是"慢一点"的问题：重启窗口里服务不可用，故障恢复时间  
直接和日志长度挂钩。

### 做法：检查点 + 截断

```
事件日志:  [1 ......................... 100000 ]
检查点:                         ^ 80000（state 已含 1..80000 的效果）
恢复:            读 80000 的 state → 重放 80001..100000
```

`Checkpoint` 把"折叠后的状态"和"折到哪一条"一起落盘，`saveAndPrune()` 顺手把老日志截掉。

**顺序不能反：先写检查点，再截断日志。** 反过来的话，进程崩在两步之间时唯一的旧状态  
副本已经被删了——这是不可恢复的数据丢失。所以顺序不是靠注释约束，而是固化在  
`saveAndPrune()` 的实现里；单独调 `EventLog::truncate()` 是危险动作。

检查点写失败（磁盘满/权限）时返回 `-1` 且**不截断**：宁可日志涨着，也不能在没有退路  
的情况下删历史。

### 三个细节

1. **原子写**：临时文件 + `rename()`。同文件系统内 `rename` 是原子的，进程任意时刻被杀  
   磁盘上要么旧要么新，不会有半截文件。
2. **crc32 校验**：文件被外部工具改坏时拒绝加载，退回从头重放。**读一个坏检查点比不读  
   更危险**——它会把错误的余额当起点，而日志里对不上的部分已经被截掉了。
3. **越界拒绝**：`saveAndPrune()` 拒绝"折到日志里还不存在的序号"，那种情况说明调用方  
   算错了，截断会把没处理的事件删掉。

### 复验

```
PASS  checkpoint  事件日志检查点（45 项）                         15.1s
PASS  schema      状态版本迁移链（19 项）                          14.6s
PASS  prom        Prometheus 导出（22 项）                          24.0s
恢复耗时          全量=81449 µs，检查点+尾巴=1856 µs
```

23 项里最关键的不是"文件写出来了"，而是**恢复等价**：3 万条事件下，  
"检查点 + 尾巴"折叠出的余额与"全量重放"逐项相同。检查点最大的风险就是"少折一段"  
或"多折一段"，两者都只体现在结果里，不看这个断言根本发现不了。

还覆盖了：垃圾文件/被篡改文件必须加载失败且不留残留状态、越界与 `seq=0` 被拒且日志  
没被截断、重复保存覆盖旧检查点。

这样"环境冲突"和"代码坏了"在输出里一眼可分——之前它们长得一模一样。

### 还没做的

3. ~~`truncate()` 仍是整文件重写~~ —— 整段截断已走 O(1) 删除；部分截断保留原始行。  
   分段滚动文件仍没做，但实际使用路径（折到水位再截）已不经过它。

### 接入 `demo/duel`：从"包就位"到"真的生效"

包做好不等于业务用上。`Settle` 构造时仍是 `rebuildFrom(1)`，所以这次把两端接起来：

```php
$ckpt = new Checkpoint("/data/settle/ledger.ckpt");
$st = new Settle($log, null, [], $ckpt, 10000);   // 每 1 万条压一次
```

三处改动：

1. **构造**：`load()` 成功就 `restoreState()` + `rebuildFrom(seq+1, false)`  
   （不能 reset——state 本身就是 reset 之后的起点）；失败则退回全量重放。
2. **导出形状**：`Checkpoint` 只收标量，所以摊平成 `w:<uid>` 余额、`s:<id>` 去重表、  
   `r:<room>` 房间号，再加 `m`/`n` 两个计数。塞进同一个扁平 map 是为了让检查点只有  
   **一次 rename**——分多段写就要保证多段同时生效，而原子性正是它最要紧的东西。
3. **触发**：`settle()` / `credit()` / `debit()` 成功后调 `maybeCheckpoint()`，  
   攒够 `ckptEvery` 条压一次。压太勤会把去重表反复全量序列化变成写放大。

**多节点必须关掉检查点**（`count($readers) > 1` 时 `ckptActive = false`）：  
检查点里的 seq 只是自己那份日志的坐标，拿它当全局水位会把别的节点还没折的事件跳过去。

### 顺手抓到的 bug：截空日志会让序号回退

`truncate()` 把日志截空后，文件里一个序号都没有，`scan()` 于是把 `nextSeq` 退回 **1**。  
后果是连锁的：

- `replay($fromSeq)` 的坐标失效；
- 检查点说"折到 100"，新事件却从 1 开始 → 重启时 `replay(101)` 一条都读不到 → **静默丢数据**。

根因是把"序号"当成了可以从文件里推导的东西。序号是一次性资源，只能单调递增，  
不能因为删了历史就回收。修法是加一个高水位侧车 `{path}.seq`：`scan()` 取  
`max(文件最大序号, 侧车)`，`truncate()` 先把高水位写进侧车再重写文件。

测试里专门验了这条：截空后 `lastSeq()` 仍是 30、下一条是 31、重开实例仍接 31。

> 这类 bug 只在"截断 + 重启"的组合下暴露，单看任何一步都正常——也正是为什么  
> 检查点必须有"恢复等价"的断言，而不只是"文件写出来了"。

### 又一个假绿

|                                                        |                       |
| ------------------------------------------------------ | --------------------- |
| `tests/settle-test/run.sh` 原来是 \`tsf build .           | grep ...\` 然后**无条件**跑 |
| `./settle_test`。build 失败时 grep 吞掉非零退出码，跑的是上一次的产物——改了代码 |                       |
| 却显示全绿。已改成 build 失败直接 `exit 1`。                         |                       |

这与 D1/D5 是同一类问题：**脚本对失败的容忍度比人高**。凡是"先构建再运行"的地方，  
都要显式检查构建退出码。

### 去重表的有界裁剪

检查点解决了"重放多久"，没解决"去重表多大"：`seen` 每个事件一条字符串键，  
跑一年就是几十万条，检查点跟着一起膨胀。

改法是让 `seen` 存**事件序号**而不是 `true`，压检查点时按序号裁掉窗口外的：

```php
$st = new Settle($log, null, [], $ckpt, 10000, 200000);   // 保留最近 20 万个 id
```

安全性来自截断本身：被裁掉的那些事件已经从日志里删了（`saveAndPrune` 先写检查点  
再截断），不会重放，忘掉 id 也就不会重复入账。

**代价必须写清楚**：把一个很久以前的房间号再结算一次，会被当成新的一局。  
游戏里房间号单调递增，这个风险可接受；要做"补发历史奖励"就得绕过这条路径，  
或者先用日志对账。测试里专门断言了这个行为（`isSettled(1)` 为 false），  
免得以后有人以为它坏了。

实测 400 局 + 窗口 100 时，去重表稳定在 100 上下而不是 400，余额与笔数完全不变。

### 截断的 O(n) 读放大

`truncate()` 原来是 `file_get_contents` + 逐行 `json_decode` 整个文件，只为得出  
"哪些行要留"。检查点场景下水位永远等于最后一条，也就是说**每次都白读几十 MB 才得出  
"一条都不留"的结论**。

改了两处：

1. **整段截断走快速路径**：判断出"留空"就直接 `unlink`，O(1)。  
   实测 3 万条 380 µs（之前是读满文件 + 解码，量级是几十毫秒）。
2. **部分截断保留原始行**：不再 `replay()` 后 `json_encode` 回去。重新编码会规范化  
   字段（丢未知字段、改转义），而日志是事实记录，不该因为一次归档被改写。  
   测试里塞了一条带 `extra` 字段的历史行，截断后它必须原样还在。

真正的根治是分段滚动文件（按大小切、按段删），但会牵动 `MergedLog` 与所有按路径  
打开日志的调用方。当前这套（检查点 + 整段删除）在实际使用路径上已经不再有 O(n)，  
分段留到真需要"保留窗口内历史"时再做。

### 增量检查点：把写入量从 O(状态) 变成 O(变化)

全量检查点的写入量与状态大小成正比。状态里有两块会一直长：余额表（随账号数）、  
去重表（随事件数，已裁剪到 20 万）。每 1 万条事件写一次几十 MB 的全量，是从  
"能跑"变成"跑久了会痛"的那一步。

改成 **基座 + 增量**：

```
ledger.ckpt        ← 基座（全量状态 + 序号）
ledger.ckpt.d20    ← 增量：这次变了什么
ledger.ckpt.d30
```

- 每次检查点只写**脏键**（改动发生时顺手记下来，不是导出时比对——比对是一百万次  
  比较，和全量写一样贵）
- 攒够 `compactEvery`（默认 20）个增量就压实回基座：写新基座、删旧增量。  
  不压实的话恢复要叠加几十个文件
- **第一个检查点必须是基座**：没有基座时写增量，恢复时无从叠加
- **坏增量导致整体加载失败**，而不是"只用基座"——半旧的状态比加载不出来更危险

顺序仍然是先写后截：`saveDeltaAndPrune` 把"写增量 → 截断日志"固化在一起。

测试覆盖：基座+多个增量叠加、增量删除键、压实清空增量、坏增量整体失败，  
以及 `Settle` 维度的"200 局 / 每 10 条一个检查点 / 每 5 个增量压实"后余额一致、  
增量个数被压在阈值内。

## 十八、P2 · 状态版本迁移链（2026-11-20）

### 补的是 T2 缺的那一环

类不可在进程内重定义，所以改逻辑只能滚动重启。但重启前后的**状态结构**经常不同：  
老二进制写的快照里没有 `hp`，新代码默认它有，读出来就是缺字段的"半坏"对象——  
而且不会在读取处报错，会在几十行之后以莫名其妙的错误爆出来。

Erlang 用 `code_change(OldVsn, State, Extra)` 解决。机制抄不了（没有两版本模块共存），  
**协议可以抄**：

```
快照里带 _v → 缺失视为 0 → 按登记顺序逐级升级 → 最终 _v = 当前版本
```

### 用"阈值步骤"而不是"逐版本"

登记的是"把 < N 的都升到 N"（`$schema->step(5, fn)`、`step(7, fn)`），  
不是 0→1、1→2 每级一个函数。理由很实际：结构改动是稀疏的，v1→v4 之间可能什么都没变，  
逼着写三个恒等函数只会让人偷懒合并成一个大函数，反而丢掉可追溯性。

登记器只保证两件事：**按阈值升序执行**，以及**漏到当前版本以下的直接报错**。

### 四条纪律（这套东西的全部价值）

1. **纯函数**：不读时间、不读全局。否则"重放同一份快照两次结果不同"，没法对拍。
2. **只向前**：`_v` 比代码新时**拒绝**，不尽力而为。硬读会把不认识的字段丢掉再写回，  
   等于静默降级。这条同时让"回滚到老二进制"变安全——它读不了新快照，会跳过而不是读错。
3. **破坏性变更分两步**：先双写新旧字段 → 滚动重启 → 再清理旧字段。滚动窗口内  
   新旧二进制都能读，等价于 Erlang 的两版本共存。这条代码强制不了，只能写进文档。
4. **迁移不了就当坏数据**：`Restorer` 把迁移失败计入 `migrate_failed` 并按 `dropBad`  
   处理，而不是"照原样交给业务"。

### 接入点

`Restorer::restore()` 增加可选的 `?Schema`，在 `$rebuild()` 之前对每个块做迁移——  
业务侧看到的永远是当前结构，不用在每个 `rebuild` 里写 `if (isset(xxx))`。

demo 里也接上了（`DuelManager`），当前 `v1` 只引入版本标记本身（步骤是恒等的）。  
这不是凑数：**第一次真改结构时新步骤登记在这里**，而 v0 的老快照必须在滚动窗口内仍可读。

### 复验

```
PASS  schema      状态版本迁移链（19 项）                          14.6s
PASS  prom        Prometheus 导出（22 项）                          24.0s
通过 16 / 失败 0 / 跳过 0
```

覆盖：缺 `_v` 走完整链、中间版本只跑缺的步骤（已有字段不被覆盖）、旧字段保留（两阶段  
中间态）、幂等、入参不被修改、版本超前拒绝、链缺一段拒绝、登记超版本拒绝、  
多块分别迁移、`Restorer` 集成（业务拿到补好的字段、未来版本不交给业务且被删）。

### 还没做的

1. **没有"快照样本对拍"**：纪律里说迁移函数要可对拍，但仓库里还没有把老快照样本入库  
   做回归的机制。真上线前应该有——迁移函数改错了，只有靠这批样本能发现。
2. **迁移链是手写的，没有生成器**：字段改名/类型变更靠人记得登记步骤。  
   再往后可以考虑从 schema 定义生成（但那是另一个量级的工程）。
3. ~~**跨节点迁移时的版本协商**~~：已补（§20）。`MIGRATE` 载荷带状态版本，  
   目标比自己旧就拒绝，源侧保留状态而不是"交出去以后读不懂"。

## 十九、P3 · Prometheus 指标导出（2026-11-20）

### 补的是"日志能看、但没法算"

`Metrics` 早就在热路径上记了计数/仪表/直方图，`Metrics::table()` 也能打成人看的表格。  
但日志表格没法做速率、分位数趋势、告警——`grep` 出来的数字是快照，不是时间序列。

所以这一步只做**翻译**：把 `snapshot()` 渲染成 exposition 文本（version=0.0.4），  
配一个一行的 HTTP 路由。不新增状态、不改热路径、不依赖网络库：  
导出失败最多是这次抓不到，不影响业务。

### 直方图导出成 summary，而不是 histogram

Prometheus 的 `histogram` 需要**桶边界**（`le="0.1"`）。我们的 `Histogram` 只保留分位数  
和均值——桶要预定义边界，业务侧定不准，内存也不可控。硬造 `le` 等于编数据。

`summary` 恰好接受分位数，语义对得上："这段时间 90% 的请求快于 X"。  
代价要说清：**summary 的分位不能跨实例聚合**（各算各的）。多实例想看全局 p99，  
只能用 `_sum/_count` 算均值，或者以后真做桶。

### 一个踩到的坑：计数器的值不在 `count` 里

`MetricSnapshot` 对计数器把 `count` 固定成 1（`count` 表示"样本条数"，只对直方图有意义），  
真正的值在 `value`。第一版渲染用 `count`，结果**所有计数器都输出 1**。  
测试立刻抓住了——这也是"断言要断言值，不要断言格式"的例子：只检查有 `# TYPE` 是发现不了的。

### 名字合法性：错了是整批失败

抓取端只认 `[a-zA-Z0-9_:]`。我们的名字习惯点分层（`room.settle.us`），直接输出会被拒，  
而且拒绝方式是**整批 400**——一个名字写错，整个进程的指标全丢。所以渲染前统一 sanitize，  
首字符是数字时补下划线。

HELP 里保留**原始名**（带点），便于和日志对照；样本行里必须是合法名。

### 复验

```
PASS  prom        Prometheus 导出（22 项）                          24.0s
通过 17 / 失败 0 / 跳过 0
```

覆盖：计数器/仪表/summary 三种格式、分位数与 `_sum`/`_count`、名字 sanitize、  
TYPE/HELP 只声明一次（重复声明同样会让整批失败）、进程内存指标可关、  
Content-Type 带版本号、路由直连（`Router::dispatch`，不启服务）、空指标表渲染为空串。

### 还没做的

1. **没有 histogram 桶**：要做需要业务侧给边界，或者改成固定指数桶（精度换内存）。
2. ~~没有内网隔离的强制~~ —— 已做（§24）：`MetricsRoute` 默认只放行回环与  
   RFC1918 网段，越界返回 403，放开要显式传 `["*"]`。
3. **没有 pushgateway / 多实例聚合**：summary 的局限仍在，多实例只能看均值。

## 二十、跨节点迁移的版本协商（2026-11-20）

### 一句话：搬之前先确认对方读得懂

`handoff` 搬的是不透明字节，协议里原本没有"这份状态是哪个版本"。  
滚动升级窗口里两边代码版本不同时，会出现最难处理的一种故障：

> 交接成功了，状态到了新宿主，但新宿主读不懂 → 重建出半坏的对象。  
> 源侧以为自己已经交出去了（本地状态可以删），目标侧那边是一堆缺字段的数据。  
> **两边都没有完整的一份。**

`Snapshot\Schema`（§18）解决的是"同一份代码能读旧快照"，解决不了"对方代码更旧"。

### 做法：载荷带版本，目标侧设闸门

```
MIGRATE = M2 \x1f key \x1f 交接序号 \x1f 状态版本 \x1f 状态字节
                                    ^^^^^^^^^^
目标侧：peerState > 本地 stateVersion → REJECT(reason="version")
```

- **目标比自己旧就拒绝**，源侧保留状态（`onRollback`，`why="version"`）
- **目标比自己新就放行**——旧状态搬到新代码上正是升级路径，目标用 `Schema` 迁上去
- 拒绝原因随 `REJECT` 回传，源侧能区分"对方忙/满了"（可重试）和"对方版本太旧"  
  （重试没用）。`Rebalancer` 对后者给 10 倍退避，避免每秒打一次

### 为什么要一个格式标签 `M2`

状态是二进制，**可能包含分隔符本身**。靠"数段数"区分新旧格式会误判：  
老格式的 `state` 里出现一个 `\x1f`，就会被当成"新格式的版本段"。3 个字节换一个  
不会猜错的分支，值得。

老报文（没有 `M2`）按"版本未知"放行——滚动升级窗口里旧二进制还在发这种，  
不放行会让升级卡死在第一阶段。这个取舍写进了注释：宁可短暂容忍未知版本，  
也不能让滚动升级无法推进。

### 复验

```
PASS  handoff    状态交接（120 项：含版本落后调度）               20.9s
PASS  rpc        RPC（50 项）                                    17.3s
通过 17 / 失败 0 / 跳过 0
```

覆盖：源 8/目标 7 时目标不安装且源侧以 `version` 回滚、反向（源 7/目标 8）能搬、  
`version_denied` 计数、老格式三段载荷仍被接受且状态字节不截断。

### 还没做的

1. ~~**`Rebalancer` 没有"换目标"策略**~~：想清楚了——**换目标是错的**。  
   `Ownership` 指出的 owner 是契约，搬到非 owner 会造出所有权分家。  
   已改成"按节点记住版本落后、暂时跳过、到期再探"（见下）。
2. **版本只在 MIGRATE 里协商**：`/metrics`、RPC 等其它跨节点接口还没带版本，  
   混版本部署时字段不兼容仍会出错。

### 补一段：版本落后时怎么调度（2026-11-20）

原本我写的是"版本拒绝后应该换环上的下一个节点"。想清楚之后否了：

**`Ownership` 指出的 owner 是契约。** 把状态搬到非 owner 节点，会造出两个节点都认为  
自己该持有的局面——那比"晚一点再搬"糟得多。滚动升级期间唯一正确的行为是**等对方升上来**。

但也不能每轮都去撞：对方没升级，试一次被拒一次，白占限流槽位、还刷日志。  
所以调度器按**节点**记住"它版本落后"，TTL 内跳过这个目标上的所有 key：

```php
$rb->setStaleTtl(30000);   // 30s 后再探一次
```

按节点记而不是按 key 记是关键的：同一个目标上所有 key 都会被拒，  
逐个 key 退避等于每轮把每个 key 撞一遍。

拒绝时还会 `Metrics::inc("rebalance.version_blocked")`——**这正是一个该被告警的数字**：  
它持续增长说明"扩容被卡住了，因为某个节点还没升级"，而不是"系统在正常搬运"。

复验：`handoff` 120 项。覆盖首轮发起 1 个、收口后标记落后、同目标上的下一个 key 被跳过  
（`skew_skipped`）、试探期过后重新尝试。

## 二十一、RPC 载荷版本协商（2026-11-20）

### 先说不能做什么

最自然的做法是"在握手里带版本"。但 hello 是**硬校验**：

```php
$parts = explode("\x1f", $p->payload);
if (count($parts) !== 4) { $this->fail("bad-hello"); return; }
```

加第 5 段 → 旧节点直接判 `bad-hello` → **链路起不来**。滚动升级当场断，  
正是"版本协商"要防的事。同理，MAC 覆盖 `node\x1fcodec\x1fnonce`，改字段也会让 MAC 对不上。

结论：**版本不能进握手，只能进 RPC 载荷本身。**

### 做法：标签 + 乐观协商 + 一次降级

```
请求 = V1 \x1f 版本 \x1f <codec 载荷>
响应 = V1 \x1f 版本 \x1f <codec 载荷>   （风格跟请求走）
```

关键在"老对端会怎么反应"：旧二进制的 `codec->unpackRequest()` 拿到带标签的字节  
会**立刻**返回 null，Router 随即回 `bad-request`——**不是超时**。这是一条干净的信道：  
一个往返就能确定对方是旧二进制。

于是：

1. 新客户端默认发版本化请求
2. 收到 `bad-request` → 记 `legacy[node]=true`，**用同一 session 重发一次旧格式**（超时不重置）
3. 之后对这个节点直接用旧格式

反向（客户端旧、服务端新）不需要额外处理：老客户端发老格式，新服务端照旧处理并回老格式。

### 服务端比客户端新/旧，行为不同

| 情形        | 行为                                                         |
| :-------- | :--------------------------------------------------------- |
| 请求版本 ≤ 本地 | 正常处理，响应里带**本地版本**（调用方借此学到 `peerVersion(node)`）             |
| 请求版本 > 本地 | 回 `version-mismatch`，handler **不执行**，计数 `version_rejected` |

`version-mismatch` 不算对端不健康（`blamesPeer` 为 false）：对端明明活着、读懂了请求、  
还回了话，只是代码旧。算进去会在滚动升级期间把一批健康节点熔断——

### 顺带发现：27 个测试目录根本没接进 verify

`tests/` 下有 27 个目录只有 `main.php`、没有 `run.sh`，因此从没被 `verify` 跑过  
（`rpc-test` 就是其中之一——它写的 41 个断言一直是"绿的"，只是没人执行）。  
这次给 `rpc-test` 补了 `run.sh` 并接入（现在 18 个套件 / 644 项断言）。

其余 26 个要不要接，取决于它们是否需要外部依赖（MySQL/Postgres/Redis）。  
**建议**：给 `tsf test` 加一个"发现式"模式——遍历 `tests/*/main.php`，  
有 `run.sh` 的跑脚本，没有的直接 build+run 并统一退出码。  
在那之前，这 26 个目录里的断言只能当"参考代码"看，不能当"验证过"。

### 复验

```
PASS  rpc        RPC（50 项：调用/超时/并发/codec/载荷版本协商）    17.3s
通过 18 / 失败 0 / 跳过 0
```


新增 9 项：正常版本化调用并学到对端版本、服务端更旧时回 `version-mismatch` 且 handler 不执行、  
旧二进制场景下自动降级重发并成功、对端被标记 legacy。

### 还没做的

1. ~~降级是永久的~~ —— 已做（§24）：`legacy[node]` 带 TTL（默认 60s），  
   到期自动重新试探，成功即恢复新格式。
2. **只覆盖 RPC 一种跨节点接口**：`handoff` 有自己的版本段（§20），  
   `/metrics`、自定义消息还没有统一约定。

## 二十二、发现式测试与一个被掩盖的工具链 bug（2026-11-20）

### 为什么需要 `tsf test`

`verify` 的清单是**手写**的：只有登记过的套件才算数。于是仓库里长期躺着另一批测试——  
有 `main.php`、没有 `run.sh`——**二十六个目录，从没被执行过**。

它们的断言"一直是绿的"，只是没人跑。这不是假绿，是**根本没人看**。

`tsf test` 不维护清单：遍历 `tests/*/main.php`，有 `run.sh` 交给脚本，  
没有就直接 `build` + 跑产物。`--unwired` 只看没接线的那批。

跳过约定沿用 verify：退出码 `77`；另外加了 `skip-auto` 标记文件——  
用例自己声明"我依赖外部服务/是交互式探测"，理由和用例放在一起，一眼能看到。

### 第一次跑就撞出一个真 bug

26 个用例里 27 个报"编译失败"，每个只花 0.2 秒。根因不在用例，在 `tsf` 自己：

```php
// 旧实现
chdir($cwd);
$p = proc_open($cmd, $desc, $pipes);
```

**实测（PHP 8.5 ZTS）：`proc_open` 的子进程不继承 `chdir()` 的结果。**  
`chdir(X); proc_open("pwd")` 输出的还是**原目录**。

这个 bug 之所以活了这么久，是因为所有调用方（`run.sh`）都是"先 `cd` 到目标目录再 build"，  
父进程本来就在那儿，chdir 没生效也看不出来。一旦从别处调用（`tsf test` 从仓库根遍历），  
就变成"tpc 说 project.yml 不存在，而文件好好躺在目标目录里"。

修法是把目录交给 `proc_open` 的第 4 个参数：

```php
$p = proc_open($cmd, $desc, $pipes, $cwd);
```

**教训**：`chdir()` 影响的是本进程，能不能传给子进程要实测，不能靠直觉。

### 结果：22 通过 / 0 失败 / 4 跳过

| 用例                                               | 结论                                                                  |
| :----------------------------------------------- | :------------------------------------------------------------------ |
| 22 个                                             | 一直是对的，只是从没被跑过                                                       |
| `db-mysql-test` / `db-shards-test` / `mail-test` | 需要 MySQL → 已用 `scripts/dev-mysql.sh` 起容器跑通（**25 通过 / 0 失败 / 1 跳过**） |
| `http-probe`                                     | 交互式常驻探测程序，不属于自动集合 → `skip-auto`                                     |

`db-pg-test` 能过、`db-mysql-test` 不能，正好说明这台机器装了 Postgres 没装 MySQL——  
这个事实以前没人知道，因为没人跑过。

### 两个入口的分工

| 命令                   | 跑什么           |      耗时 | 用在哪       |
| :------------------- | :------------ | ------: | :-------- |
| `tsf verify`         | 注册过的 19 个套件   |  ~5 min | 提交前、CI 门禁 |
| `tsf test --unwired` | 发现式，26 个未接线用例 | ~15 min | 定期体检      |

`tsf test` 不进 `verify`：15 分钟的门禁没人会等。但它是**一次性还清技术债**的工具——  
现在这 26 个用例有了明确的结论，而不是"大概能跑"。

### 还没做的

1. ~~`tsf test` 没有并行~~ —— 结论改了（§23）：本机 4 核而 tpc 内部已 `-j4`，  
   并行只会超售（实测更慢）。改用 `--shard i/N` 分到多机/多容器。
2. **`skip-auto` 是静态的**：本机装了 MySQL 之后要手动删文件。理想情况是

3. **仍有 3 个套件只在 `verify` 里**，没有 `main.php` 形态（纯脚本），

## 二十三、并行构建这件事：先证伪，再定位（2026-11-20）

### 起点：一个被归错的因果

之前 `verify` 里偶发"编译失败"，归因是"本机有别的任务在并行编译，共用增量缓存"。  
这个归因**方向对、机制错**：真正的原因不是并发竞争，而是**跨工程缓存污染**。

证据（`timer-test` 构建失败时的真实报错）：

```
Rpc.o: undefined reference to `typephp_project_shard_test::get_str(unsigned int)'
```

`timer-test` 链接到了**为 `shard-test` 编译的 `Rpc.o`**。共用缓存里的目标文件带着  
**工程名符号**（`typephp_project_shard_test`），所以：

- 串行也会红，只是位置随机——谁先编译谁污染，红的是后面那个；
- 并行会放大：交错构建多个工程，污染面更大，于是"看起来像并发问题"。

### 修法：每个工程一个构建目录

`project.yml` 的 `build-dir` 本来就是配置项，`tsf` 之前没生成它，于是所有工程挤在  
`~/.tsf/toolchain/typephp/build/cache` 里。现在按工程生成：

```yaml
build-dir: /home/hhr/.tsf/proj/timer-test-a99fdef5/build
```

代价是每个工程各有一份缓存（首轮冷编译 ~22s），换来的是**构建结果只取决于本工程**。

### 并行本身呢：能做，但在这台机器上不划算

我先按"容器隔离"的思路做了一版：每个 worker 一个 `TSF_BUILD_DIR`，4 路并行，  
**26 个用例 0 失败**——说明隔离方案成立，容器也不是必需的。

但耗时没有变好：

| 方式    |   墙钟 | CPU 时间 |
| :---- | ---: | -----: |
| 串行    | 6:00 |  17:5x |
| 4 路并行 | 6:56 |  22:0x |

原因很直接：这台机器 **4 核**，而 `tpc` **每个构建内部已经 `-j4`**。  
再开 4 个 worker 只是把 4 核超售成 16 线程，CPU 时间多烧 5 分钟，墙钟更慢。

所以"用 Docker 起多个容器并行"能解决**隔离**（缓存不再打架），但解决不了**核数**。  
容器不创造 CPU。真要扩规模，路径是 **`--shard i/N` 分到多台 runner**：

```bash
# runner 0
tsf test --unwired --shard 0/4
# runner 1
tsf test --unwired --shard 1/4
```

分片在过滤之后、按目录名排序之后切片，所以同一片在不同机器上稳定对应同一批用例。

### 落下什么

- `tsf test --shard i/N`：给多机/多容器用，唯一能线性扩展的维度
- `tsf test --list`：打印将要跑哪些用例（配合分片做 CI matrix 的展开）
- `tsf test --one <dir>`：内部用，父进程/脚本可单跑一个目录
- 每个工程独立 `build-dir`：**顺带修掉了那个随机 ld 失败**

`--jobs` 明确移除，并在传入时打印原因——留一个"能跑但更慢"的开关只会误导人。

### 教训

1. **"随机失败"先找确定性解释**。这里看着像竞态，实际是缓存键缺了工程维度。  
   一旦拿到真实的 ld 报错（而不是被我 `tail -3` 截掉的堆栈），原因一眼可见。
2. **归因要落到机制**。"并行编译导致失败"解释不了串行也红这件事——  
   如果当时追问一句"为什么并行会红"，能早几轮发现真因。
3. **并行不是免费的**：先看 `nproc`，再看每个任务内部的并行度。

## 二十四、两处"文档说要做、代码没做"的收口（2026-11-20）

这两条都不是新发现，是**早就该做但一直挂着**的项。它们的共同点是：  
风险清楚、实现不大、但一直被更"有意思"的东西插队。

### 1. `/metrics` 的来源限制：从"文档建议"变成"代码强制"

原来只在 README 里写"挂内网"。这不够——部署时没人回头读文档，而默认暴露的代价是  
一次疏忽就把在线人数、结算金额、进程内存公开。

现在 `MetricsRoute::register()` 默认只放行回环与 RFC1918 网段（`IpFilter::PRIVATE_ONLY`），  
越界返回 **403**（不是 404：让运维一眼看出"是被拒了"，不至于怀疑路由没注册）。  
放开要显式传 `["*"]`。

三个实现细节：

- **不看 `X-Forwarded-For`**：客户端可伪造，用它做访问控制等于没有控制。  
  真要经代理就在代理层限制，或把代理地址加白名单、由代理保证边界。
- **拿不到来源 IP 时拒绝**，不是放行。"不知道是谁"不该等于"谁都可以"。
- **IPv6 只做精确匹配**（`::1`），不做 CIDR——前缀比较出错的风险远大于收益。

### 2. RPC 的 `legacy` 标记：从"永久降级"变成"到期重试"

上一轮做完乐观降级后留了个尾巴：`legacy[node]` 一旦置位就永不清除。对方升级之后，  
我们仍然一直用旧格式跟它说话——能用，但永远拿不到 `peerVersion`、用不上新字段，  
而且**没有自愈能力**，只能重启进程。

现在标记带 TTL（默认 60s）：

```php
$client->setLegacyTtl(60000);   // 到期后按新格式再试一次
```

成功的代价是每 TTL 一次多余往返；失败的代价是再标记一段。两种都比"永久降级"好。

测试里用一个会"升级"的对端验证：第一次返回 `bad-request` → 客户端降级成功；  
TTL 到期后再调 → 自动走新格式、学到 `peerVersion=8`、标记清除。

## 二十五、把 MySQL 真的跑起来（2026-11-20）

§22 里 `db-mysql-test` / `db-shards-test` / `mail-test` 一直是"需要本机 MySQL"而跳过。

### 做法：容器 + 自动 SKIP

`scripts/dev-mysql.sh` 起一个 `mysql:8.0`（端口 52315，和用例 DSN 对齐；认证插件用  
`mysql_native_password`，避开 MySQL 8 默认 `caching_sha2` 在部分驱动组合下的握手问题）。  
`stop` / `reset` 各一行。

用例侧改成"连不上就 SKIP"：

```php
requireMysql("127.0.0.1", 52315);   // 端口探测，不通就 exit(77)
```

**为什么用端口探测而不是 try/catch**：AOT 下 `catch (\Throwable $e)` 接不住 PDO 构造  
抛的 `PDOException`——实测异常直接冒成 `Fatal error`，而且内联后行号还是错的  
（报在 `connectOrSkip` 那一行）。探测 socket 不涉及异常类型，而且"端口没人监听"  
本来就是这里要判断的事。

只探测可达性、**不探测认证**：服务在但密码不对属于真配置问题，应该红，不该跳过。

### 结果

| 场景   | 结果                                          |
| :--- | :------------------------------------------ |
| 容器在跑 | 25 通过 / 0 失败 / **1 跳过**（只剩交互式 `http-probe`） |
| 容器停了 | 三个 DB 用例自动 SKIP，不是 FAIL                     |

顺带一个观察：这 26 个用例现在每个只要 5–7 秒（§23 的 per-project build-dir 之后  
缓存是真热的），全量 `--unwired` 从 15 分钟降到约 4 分钟。

### 这条为什么值得做

跳过和通过看起来都"不是红"，但它们的差别在于**验证过没有**。三个 DB 用例挂着  
`skip-auto` 的这段时间里，数据库层的 60 多项断言（字符集、严格模式、事务回滚、分片路由）  
一次都没跑过。它们恰好是"改了不容易被发现"的那一类。

### 还没做的

1. **`skip-auto` 机制本身还在**：`http-probe` 用着它。那是它该有的用法（交互式程序），  
   但如果有更多用例开始依赖它，就该改成"用例自己探测"的默认约定。
2. **PG/Redis 的跳过仍是 exit 77 写在脚本里**（`registry` 套件无 Redis 时 SKIP），

## 二十六、崩溃取证：补上"出事之后能不能查"（2026-11-20）

### 重新评估之后，下一个短板不再是功能

P0/P1/P2/P3 清完之后再看 §5.2 的九维度：分布式 7、热更 5、可观测 7、失效隔离 7。  
**功能面已经和 Pomelo/Nakama 这一档打平**，差距集中到三件改不动的事（生态、语言级的  
抢占式调度与 per-process heap、真热更）。

但还有一件**能改又一直没改**的：出事之后能不能查。

原来的崩溃处理只有一行日志：

```
service error, killing  svc=duel:1001 msgId=1001 err=...
```

知道它挂了，不知道挂之前在处理什么。于是"玩家说卡了一下""这局结算不对"这类问题  
只能靠时间戳在日志里猜——这正是文档 §10.5 把 crash report 列为 P0、  
又写着"最被低估"的原因。**列了 P0，但一直没做。**

### 做了什么

1. **每服务环形缓冲**（`Service::enableTrace(n)`）：保留最近 n 条消息的摘要  
   （时间 / 消息号 / 来源 / 会话 / 载荷长度）。默认**关闭**——基类里写过  
   "不要放 per-message 统计"，关闭时只有一次整数比较；打开后约 +100ns/条。
2. **崩溃落盘**（`Kernel\CrashDump`）：`Scheduler` 的 catch 里把现场写成 JSONL：

```json
{"t":1795165049580,"svc":"local:1","msgId":1003,"err":"boom-at-3","file":"...","line":...,"restarts":1}
{"recent":["...|1001|...","...|1002|...","...|1003|..."]}
{"state":"{\"room\":1001,\"hp\":{\"1001\":40},\"elapsedMs\":8200,\"winner\":0}"}
```

1. **业务侧状态摘要**（`Service::dumpState()`）：demo 的 `DuelService` 覆写后，  
   崩溃现场从"哪条消息出错"变成"这局打到第几秒、双方多少血、有没有结算"。
2. **保留上限**：默认 200 个文件，超了删最旧的。死循环崩溃几秒钟能写几千个文件，  
   写满磁盘之后连日志都写不进去。

### 两个实现上的取舍

**为什么是 JSONL 不是格式化文本**：崩溃现场最需要的是**能批量对比**（两次崩溃是不是  
同一个原因）。JSONL 能直接 `jq`，格式化表格只能人眼看。

**为什么同一毫秒要加后缀**：重启抖动时同一毫秒崩两次很常见，文件名只带毫秒会互相覆盖——  
**后一次把前一次的现场吃掉**，而前一次往往才是根因。测试里专门验了这点。

### 复验

```
PASS  service-test  （9 项新增：dump 内容 / 关闭仍落盘 / 保留上限 / 不覆盖）
通过 18 / 失败 0 / 跳过 0
```

### 还没做的

1. **没有 `__sys_state` 调试入口**（§10.5 的第二条）：线上不重启就想看某个服务的状态，  
   现在只能等它崩。要做得先想清楚权限与限流，否则就是个后门。
2. **dump 不会自动上报**：写本地磁盘，容器销毁就没了。生产上应该挂 volume 或者推 S3。
3. **没有"崩溃聚合"**：同一个根因崩 100 次会写 100 个文件，应该按 err+stack 聚合计数。

## 二十七、为什么是"单进程协作式"：多进程不等于多 worker（2026-11-20）

### 先纠正一个前提

"多进程"在 TSF 里的实现形态是 **一个进程 = 一个 node**，不是"一个进程四个 worker"。  
`run-cluster.sh` 起两个 `./duel` 进程，各自 `worker_num=1` + 不同 `node_id`，  
进程之间走 `Cluster`（unix socket / TCP）。

所以"单进程协作式"描述的是 **Actor 表的作用域**，不是"整个服务只有一个进程"。  
横向扩展靠加进程（加 node），不靠加 worker。

### 为什么不能"一个进程多个 worker"

`demo/duel/main.php` 直接拒绝 `worker_num > 1`（实测过，护栏有效）。原因是三处实测：

1. **快照被每个 worker 各扫一遍**。一个快照、两个 worker 启动，日志里出现两次  
   `rooms restored done=1`——同一个房间在两个调度器里各建一份，都往同一个 `.snap` 写，  
   后写覆盖先写，**一份进度静默丢失**。
2. **事件日志 `nextSeq` 从文件扫出来**。两个 worker 并发建，实测 120 条事件只有 61 个序号。
3. **房间号每个 worker 各自从 1 数**，跨 worker 必然重复；而结算幂等键是 `duel:<房间号>`，  
   重复就意味着**钱静默不发**。

三条的共同点：**Actor 的正确性依赖"单所有者"**。Swoole 的 worker 之间没有共享调度器  
（独立进程、独立内存），没法协调谁拥有哪个房间——这不是"改个数字"能解决的，缺的是  
"房间归属 + 重启认领 + 跨 worker 路由"这一整层。

### 协程和线程各自解决什么

**协程解决 I/O 并发，不提供 CPU 并行。** 它让"等数据库"的时间不占着线程，  
但同一时刻仍然只有一个协程在跑。而且 TSF 里 `enable_coroutine=false`——  
开着会破坏"同一服务的 `onMessage` 不并发"这条契约（同一服务的两个协程会交错）。

代价要写清楚：**在 `onMessage` 里做同步 I/O，会阻塞整个 worker 的所有服务。**  
这是当前架构的真实短板，比"没有协程"更准确——协程本身不是目的，**不被 I/O 阻塞**才是。

**线程是真并行，但和 PHP 的约束冲突。** ZTS 线程共享堆，引用计数要原子操作；  
而 Actor 的第一条规矩就是"服务之间不共享内存"。Swoole 的 thread 模式适合 CPU 密集  
任务池，不是给 Actor 表加速用的。

### 差距到底在哪（用实测数字）

| 路径                  |                                   成本 | 出处                            |
| :------------------ | -----------------------------------: | :---------------------------- |
| 进程内投递（同一 Scheduler） |            **870 ns/条**（115 万 msg/s） | §2.3                          |
| 跨进程 unix socket     |                       p99 **285 µs** | §13                           |
| 网络端 1 worker @32 连接 | **23 µs/条**（gateway=off，4.3 万 msg/s） | §33（§2.3 的 29µs 是 gateway=on） |
| 网络端 4 worker @64 连接 |           **5.8 万 msg/s**（1.7×，非 4×） | §2.3，4 核且压测端同机抢 CPU           |

结论：加进程**不是免费的线性扩展**——每跨一次进程就是序列化 + 系统调用（差 300 倍量级）。  
真正的差距在三处：

1. **每消息固定开销**（PHP 值语义 + 协议解析 + AOT 边界）→ 语言运行时问题，改不动
2. **跨进程必须序列化**（Actor 作用域 = 单进程）→ 架构选择，可以靠"减少跨进程"缓解
3. **同步 I/O 阻塞整个 worker** → **可以改**，见下

### 第 3 条是可改进的点

成熟做法（Skynet）是：socket 读写放在独立线程，回调进服务邮箱。  
服务照旧串行处理，但"等 I/O"这件事不再占住整个 worker。

对应到 TSF，可行的形态是 **I/O 卸载池**：`$db->query()` 变成"提交到 I/O 服务 + 回调消息"，  
`onMessage` 里不再阻塞。代价是业务代码从同步写法变成"两段式"，且要处理超时与取消。

这条比"加 worker"更对症：它不破坏"单所有者"，只是把等待挪走。

### 一句话回答

多进程已经实现，但它的单位是 **node**（一份独立的 Actor 世界 + 一套独立的房间号段），  
不是**同一张 Actor 表的并行执行**。协程和线程能改善的是"等待"与"CPU 并行"，  
而 TSF 现在的瓶颈是"每消息固定开销 + 跨进程序列化 + 同步 I/O 阻塞 worker"。

## 二十八、协程：能力早就有了，验证是假的（2026-11-20）

### 先纠正我上一轮的说法

上一轮我写"协程不提供 CPU 并行，所以用处有限"——这句话本身没错，但**暗示了"没做"**。  
事实是：`Scheduler::setCoroutine()` 早就实现了 actor-per-coroutine，  
`tests/coroutine-test` 也在。问题出在**那个测试从来没真正验证过**。

### 两个"假通过"

1. **连的是一台不存在的 redis**。测试里写死 `127.0.0.1:22379`（作者当年的公网代理，  
   RTT ~31ms）。换台机器连不上 → `conn()` 返回 null → 慢调用 0 次 → 判定 FAIL  
   "redis 不够慢"。这个 FAIL 被当成"环境问题"，于是**没人真正跑过这个对比**。
2. **两档都开了 hook**。`enableCoroutine(SWOOLE_HOOK_ALL)` 在同步模式也执行，  
   所以"同步模式"里的 `usleep` 同样被让出——测出来的不是"阻塞 vs 不阻塞"，  
   而是"有 hook 单协程 vs 有 hook 多协程"，当然看不出差别。

### 修完之后的数据

我把慢调用改成 `usleep(30000)`（由 hook 决定是否让出，语义等价于一次 30ms 的 DB/HTTP 调用），  
并且**只在协程模式开 hook**，然后各跑一次：

| 模式 |   别的服务的最大停顿时 | 慢调用           |
| :- | -----------: | :------------ |
| 同步 | **40.71 ms** | 14 次 × 30.3ms |
| 协程 | **10.85 ms** | 14 次 × 30.2ms |

同样的慢调用量，同步模式把整个 worker 卡住 40.7ms，协程模式只有 10.8ms  
（10.8ms 基本就是打点间隔本身，等于"没有可感知阻塞"）。**协程确实有效，4 倍级改善。**

### 代价：纯消息吞吐实测掉了 12%

上一轮我推断"纯消息吞吐基本不变"，**实测是错的**：

| 轮次  |                      同步 |                      协程 |    差距 |
| :-- | ----------------------: | ----------------------: | ----: |
| 第一次 | 888,960 msg/s（1,125 ns） | 782,132 msg/s（1,279 ns） |  −12% |
| 第二次 | 959,094 msg/s（1,043 ns） | 916,170 msg/s（1,092 ns） | −4.5% |

（`./service coro`，深队列 10 万条，同机，看门狗关闭）

**结论取区间而不是单点：协程的纯消息路径慢 5%–12%。** 差异来自协程创建与调度  
落在批边界上，受调度时机影响；两次都明显慢于同步，但不到让人放弃的程度。

多出来的是 `swoole_coroutine_create` + 协程调度 + 每批一次的闭包调用。  
这个代价在"有阻塞调用"的场景下可以忽略（它换掉的是 40.7ms 的停顿），  
但在**纯转发、纯内存玩法**上就是净亏损。

**这就是"按服开"的量化依据**，不是感觉。

测这个数字顺手抓到一个真 bug，见下。

### 顺带修掉：协程模式漏了"回队"

第一次跑协程吞吐，只处理了 **200 条**（正好一个 budget）就停了。原因是  
`dispatchAsync` 的 `finally` 只 `unset($busy[$id])`，**没有把还有积压的消息重新排进  
ready 队列**——同步路径一直有这段逻辑，协程路径照搬时漏了。


后果：一批（默认 200 条）处理完但信箱还有消息时，这个服务要等**下一条新消息**  
才会被再次调度。突发一批（上线结算、批量发奖）之后，剩下的消息就永远卡在信箱里，

现象是"没反应但日志干净"。`coroutine-test` 测不出来，因为它 200ms 才投一条。

修法就是在 `finally` 里补回队（先清 busy，再判非空、判未排队）。修完 10 万条全部处理完，  
`cluster` 在协程开启下 11 项、`verify` 18 套件全绿。

**这个 bug 只有在"用心跳驱动的测试之外还做吞吐测量"时才会暴露**——  
它也是"能力有了但没有压测覆盖"的典型后果。

### 补的开关

能力有了却接不到配置上——`setCoroutine` 只在 `tests/` 里被调用过。现在 duel 支持：

```json
{ "server": { "coroutine": true } }
```

启动时调 `Runtime::enableCoroutine(SWOOLE_HOOK_ALL)` + `Scheduler::setCoroutine(true)`  
（必须在 Server 启动前，之后开的 hook 不生效）。

复验：协程开启下 `cluster` 11 项、`rejoin` 6 项全过；默认关闭时 18 个套件全绿。

### 结论：默认该不该开

**按服开，不是全局开。** 有 DB/HTTP/RPC 调用的服（绝大多数业务服）应该开；  
纯转发、纯内存玩法可以不开。现在的默认值仍是 `false`，但理由已经从  
"协程没验证过"变成"看有没有阻塞调用"——这是两个完全不同的默认值依据。

### 还没做的

1. ~~纯消息吞吐未实测~~ —— 已测（`./service coro`）：协程慢 12%，见上表。
2. **看门狗在协程下的语义**：`watchdogNs` 只能事后记账，协程模式下"慢"的判定  
   应该改成"协程被挂起多久"，现在还是按消息处理耗时算。
3. **协程栈内存**：默认 2MB/协程，服务上万时是真实压力。开了协程的部署要重新算内存。

## 二十九、看门狗在协程模式下的语义（2026-11-20）

### 又一个"照搬时漏了"

`dispatchAsync` 里既没有回队（§28 已修），也**完全没有看门狗**——  
同步路径有 `$wdNs` 那段，协程路径整段没写。也就是说：**打开协程后，慢消息一条都报不出来**。

两个漏洞是同一个来源：协程路径是后加的，同步路径里的"非主流程能力"（回队、看门狗）  
在照搬时被跳过了。这类漏洞的共同特征是**只在特定负载下暴露**：  
回队要突发流量，看门狗要真的慢，而原有测试都是心跳驱动、200ms 一条。

### 但"慢"在两种模式下不是同一件事

这是这次真正的设计问题，不是补几行代码：

| 模式 | 单条消息的墙钟 =               | 慢意味着            |
| :- | :---------------------- | :-------------- |
| 同步 | **独占 worker 的时间**       | 真的卡住了所有人        |
| 协程 | 运行时间 + **等 I/O 被挂起的时间** | 可能只是在等数据库，没卡任何人 |

直接把同步的判定搬过去，结果是**每个 DB 查询都报慢**——那等于把告警废掉。

所以：

1. **协程模式下仍报墙钟超限**，但日志带 `blocking: false`，明确它不是阻塞。
2. **真正的阻塞信号换成"一轮调度花了多久"**：协程等 I/O 会让出，不会拖慢一轮；  
   只有**占着 CPU 不下来**才会。这个信号放在 `run()` 自循环里测。
3. 两种模式的 `max_msg_us` / `blocking` 字段都在，排障时一眼能分出是哪一类。

### 走了个弯路，记下来

第一版把"调度间隔"放在 `tick()` 开头测，测完就跑测试——结果日志里出现  
`round_us: 19580`（19.58ms），来源是测试自己的 `Coroutine::sleep(0.02)`。

看起来"指标生效了"，其实是**指标放错了位置**：`tick()` 由外部随时调用  
（定时器、HTTP 循环、测试各按各的节奏），在它里面测间隔，量到的是"两次调用隔了多久"，  
和"这一轮被谁卡住"根本不是一回事。

挪到 `run()` 自循环后语义才对：一轮 = 收消息 + 到期定时器 + 派发，它变慢只可能是  
有协程占着 CPU。测试也改成断言"外部 sleep **不该**被误报"（`slow_tick == 0`）——  
**一个指标的正确性，往往要用"它不该触发的时候不触发"来验证**。

### 复验

```
PASS  同步模式检出慢消息（blocking: true）
PASS  协程模式也检出了慢消息（blocking: false）   ← 原来检不出
PASS  外部 sleep 不被误报成调度卡顿（slow_tick = 0）
通过 18 / 失败 0 / 跳过 0
```

### 还没做的

1. **两条路径缺一致性约束**：回队、看门狗、崩溃取证都是"同步有、协程漏"。  
   应该给 `service-test` 加一组"同一行为在两种模式下都跑"的用例，  
   而不是靠人记得两边都写。
2. **`kill` 动作在协程模式下更粗暴**：杀掉服务时它的协程还在跑，现在靠 `busy` 标记  
   和后续 `isset($services[$id])` 挡住，但协程内部状态没清理。

## 三十、补强计划（对着 §5.2 那张表）

### 先纠一个直觉：分数低 ≠ 该补

表里 TSF 最低的是**生态与人才 2**。这一格补不了——它取决于"市面上有多少 PHP 游戏服务端  
工程师"，不是代码能改的。硬要投钱进去，唯一有效的方式是降低门槛（脚手架、错误可读性），

所以排序依据不是分数，是**单位成本能提升多少分**，以及**是否卡住上生产**。

### S1 · 两周当量（先把"用起来"和"查得到"补齐）

**S1-1 链路追踪（可观测 7 → 8.5）**

目标：一条玩家操作能从"收到包"串到"结算落盘"，跨 node 也不断。

- `Message` 增加 8 字节 `traceId`（不占 `session`：`session` 是请求-响应配对用的，  
  语义不同，混用会让 RPC 回包路由出错）
- `Cluster` 的 Packet 带上它；跨机自然延续
- `Logger` 自动注入，`eventlog` 记账时也落一份
- 采样率可配（默认全采，压测时按 1/1000）

验收：`run-cluster.sh` 里加一条断言——**同一个 traceId 出现在两个 node 的日志里**，  
且能从 `var/log` 里把一次交战的完整链路 grep 出来。

**S1-2 上手成本（5 → 6.5）**

- AOT 子集报错**给出改法**：`mixed` 参数、动态属性、`switch` fallthrough 三类最常见，  
  报错后面直接附"改成什么"
- `tsf new` 生成**可跑的房间服骨架**（含一个房间、一个匹配器、一个 HTTP 健康检查），  
  目标：`tsf new foo && cd foo && tsf run` 五分钟内能连上
- `tsf doctor` 增加"你的 PHP 代码里有哪些地方会被 AOT 拒绝"的预检

验收：故意写一个 `mixed` 参数，编译报错里直接出现修改建议；新骨架 5 分钟内跑通 echo。

### S2 · 结构性投入（先测量，再决定投多少）

**S2-1 网络路径：先把 29µs 拆开（5 → 6.5，或明确停在 5）**

29µs 是个总数，没有拆解就无法判断能优化多少。第一步不是优化，是**分段计时**：

| 段                  | 预期占比 | 可优化性                  |
| :----------------- | :--- | :-------------------- |
| Swoole 回调进入 + 闭包调用 | 高    | 不可优化（框架边界）            |
| 帧解码（`Protocol`）    | 中    | **可**（零拷贝、避免中间 array） |
| 分发到 Mailbox        | 低    | 已优化（870ns）            |
| 编码 + 写回            | 中    | **可**（批量写、复用缓冲）       |
|                    |      |                       |

- 若可优化部分 ≥ 40%，投入做零拷贝解帧 + 批量写，目标 **29 → 20µs**
- 若可优化部分 < 20%，**停在这里**，把"5 分是语言边界"写清楚，不再投入

验收：bench 输出分段占比；优化后单条 ≤ 22µs 且 p99 不退化。  
**这一项的价值有一半在"敢停"——先测再投，避免无底洞。**

**S2-2 跨 key 一致性（分布式 7 → 7.5）**

同一个玩家的"房间"和"背包"若分属不同 key，分开迁移会有"人在新节点、背包在旧节点"的窗口。

- 引入**玩家分片键**：一个玩家的所有状态按 uid 归到同一个 key（或同一迁移批次）
- `Ownership` 支持"组"：组成员一起迁，迁完才切流量
- 闸门（`Gate`）已有冻结能力，扩展成"组级冻结"

验收：构造"房间 + 背包分属两 key"的场景，迁移过程中读到的数据必须同代。

### S3 · 长期（可选，按运营需要）

- **热更增强（5 → 6）**：T1 支持"服务级替换 + 保留状态"的窄场景（例如只换纯函数逻辑）
- **灰度/流量染色**：按 uid 前缀把 1% 流量导到新版本节点
- **火焰图**：perf 采样接入，补上"知道慢但不知道为什么慢"

### 不做清单（写下来，避免反复讨论）

| 项                | 为什么不做                                  |
| :--------------- | :------------------------------------- |
| 生态与人才            | 不是代码问题                                 |
| per-process heap | PHP 单进程共享堆，做不了"进程级 GC 隔离"              |
| 抢占式调度            | `Coroutine::cancel()` 打不断 CPU 循环，已实测   |
| 两版本代码共存          | AOT 是静态链接，类表只增不减                       |
| 30 Hz 状态同步       | 3.4 万 msg/s/worker 撑不住百人同屏，属选型问题不是优化问题 |

## 三十一、S1-1 链路追踪：进程内先通，跨进程不硬来（2026-11-20）

### 先做减法：跨进程这一步不能照搬

第一反应是给 `Packet` 加 8 字节 traceId。看线格式就停下了：

```
| len(4B) | dst(4B) | src(4B) | session(4B) | msgId(2B) | payload |
```

头是**定长 18 字节**，`tryDecode` 按固定偏移切字段。加 8 字节之后，老节点会把  
traceId 的前 2 字节当成 `msgId`——**消息投错服务，而且不报错**。  
这比"断链"糟得多：断链你会立刻发现，投错服务只会表现为"某个功能偶尔不工作"。

RPC 那次能加版本是因为"解不出来会回 `bad-request`"，有干净的失败信号；  
`Packet` 没有这个性质。所以这一轮**不动线格式**。

### 做了什么

1. `Message::$traceId`——和 `from`/`session` 一样的框架字段。
2. `Scheduler` 在批处理时设置它、在 `deliver()` 时**自动写进消息**：  
   业务代码里没有一行是"传 trace"的。**不用记得带，才有人用。**
3. 协程模式下放进**协程上下文**（`sched_trace`），和 `current` 一样——  
   否则并发协程会互相覆盖，日志里出现"A 的 trace 粘到 B 的链路"，  
   那比没有链路更误导。
4. `Logger` 自动带 `trace` 字段；通过 `setTraceProvider` 注册，避免  
   Kernel 反向依赖 Service（§3.3 的分层约束）。
5. 入口 API：`beginTrace()` / `currentTrace()` / `setTrace()`。  
   **不放在传输层自动生成**：一个客户端包是不是一条链路，只有业务知道  
   （心跳不值得建，扇出几十条消息的包更该建）。

### 边界说清楚

- **进程内完整**：Gateway → 房间 → 匹配 → 结算，一条链全带得上。
- **跨进程会断**：两条消息各自带自己的 trace，跨 node 之后不再连续。  
  在日志里表现为"两条不同 trace 的记录时间相邻"。
- 这是**刻意的取舍**，不是遗漏：跨进程要改线格式，代价见上。

所以要真正跨机追踪，需要一次"全集群同版本"的窗口，做法和 §21 的 RPC 版本协商一致  
（新增字段 + 双写过渡期）。那是下一步，不是这一轮。

### 复验

```
PASS  B 收到了 A 转发来的同一条链路（trace 原样传递）
PASS  没有 trace 的消息不该凭空获得一个
PASS  批处理结束后 trace 已恢复（不泄漏到下一条）
通过 18 / 失败 0 / 跳过 0
```

### 续：把"钱"这条链补上（同日）

上一轮的三个遗留里，第 3 条最影响实用价值——能查到"谁点了什么"，但查不到  
"这笔钱对应哪次操作"。补它不需要动线格式，成本最低，所以先做这条。

**① `eventlog` 落 trace**

`append()` 自动取当前链路写进账本（`"tr"` 字段），只在有链路时写——避免每条后台  
事件都挂 `tr:0` 撑大日志。读取默认给 0，**老文件不需要迁移**：升级不能要求停服搬账。

取值走 `Logger::trace()` 而不是直接调 `Scheduler::instance()`：可选包依赖核心是允许的，  
但让每个包都认识调度器，等于把它们绑死在一种运行方式上。

**② 结算的 trace 不是"当前"的**

这里有个语义坑：结算由**定时器 tick** 触发，那条消息的 `traceId` 是 0。  
直接用"当前 trace"的话账上永远是 0——功能形同虚设。

修法是让房间自己记：`DuelService::$lastTrace` 在 `onMessage` 里更新（只记 >0 的），  
`settleMatch()` 时临时切到它。语义变成"这笔钱归到最后一次玩家操作上"。

**③ 入口开关：默认关，但要真的能打开**

`Server::traceFrames(true)`：打开后 `feed()` 每切出一帧就 `beginTrace()`，  
之后业务 deliver 出去的消息全都自动继承，**不改任何业务代码**。

默认关不是保守，是成本：心跳 10Hz × 数千连接时，每帧建一个 id 是纯浪费；  
而"一次点击换一局结算"这种包才是追踪要覆盖的。选择权交给部署方。

**端到端证据**（`run-cluster.sh` 跑完的真实账本）：

```json
{"s":1,"id":"duel:1","k":"duel.settled","t":1795168973881,
 "d":{"room":1,"winner":1002,"amount":100},"tr":104304817995827}
```

两个节点各一条，都带 `tr`。

### 还没做的

1. **跨 node 连续**：需要 Packet 版本化（见上）。
2. **采样**：`traceFrames(true)` 之后高频玩法需要 `1/1000` 采样，否则 id 生成 + 日志字段是净成本。
3. **没有"按 trace 查账"的工具**：现在得 `grep '"tr":xxx'`。理想是一条命令  
   `tsf trace <id>` 把跨文件、跨套件的记录拼成时间线。

## 三十二、两处短板，一处放弃、一处动手（2026-11-23）

回到 §5.2 那张表，相对最强对手差距最大的四项是：网络吞吐（−4）、热更（−5）、  
上手成本（−3）、生态（−7）。生态补不了，上手成本只影响新团队——所以真正值得投的是前两个。  
这一节把两个都处理了，一个用数据否掉，一个动手补。

### 网络吞吐 5 分：**放弃投入**（有数据）

§30 里给这一格定的规则是"先测再投，可优化部分 <20% 就停"。测完了：

| 项                |         成本 |  占 29 µs |
| :--------------- | ---------: | -------: |
| `encode`（64B 载荷） |     555 ns |     1.9% |
| `decode` + 消费缓冲  |   1,351 ns |     4.7% |
| **可优化合计**        | **1.9 µs** | **6.6%** |

（`./service frame`，20 万次 encode、50 万帧 decode）

也就是说：**把编解码优化到零，网络端也只能从 29 µs 降到 27 µs。**  
剩下 27 µs 在 Swoole 回调、socket 系统调用、事件循环——不是这个仓库的代码。

所以这一格的分不是代码质量造成的，是运行时边界。要提高只有换栈（原生扩展解析、  
或上 UDP/KCP 自己管收发）。**结论是停，并且把结论写下来，避免半年后有人再来一遍。**

顺带一个小发现：`feed()` 里每帧 `substr($buf, $consumed)` 是 O(n²) 行为，  
但实测单次 113 ns（7.2KB 缓冲）——在一帧 29 µs 的尺度下不值得改。  
**"看起来是性能杀手"和"实际是性能杀手"是两件事。**

### 热更 5 分：**动手补**（成因和想的不一样）

一直以为热更的短板是"没有脚本引擎"。读代码才发现不是：`pkg/script` 有完整的  
加载、热重载、异常隔离、版本计数。真正的问题是 **`Context` 只能读写白名单字段**——  
脚本能改数字，但**发不了奖**。

而活动玩法要的恰恰是发奖。于是"热更"停在"调数值"，一到"做活动"就得重启。  
这就是 5 分的具体成因：**脚本没有做事的通道**。

补法：给 `Context` 加减副作用能力，由宿主显式授予。

```php
// 宿主侧
$ctx = new Context($player, ["uid", "gold"], ["gold"]);
$ctx->bindReward(function (int $amount, string $reason): bool {
    $settle->grant($uid, $amount, $reason);
    return true;
});
$ctx->bindLog(function (string $msg): void { Logger::info("script", ["m" => $msg]); });

// 脚本侧（改完 reload 即生效，不重启）
return [
    "daily" => function ($ctx) {
        if ($ctx->getInt("gold") < 500) {
            $ctx->reward(350, "daily_first_win");
        }
    },
];
```

三条设计约束：

1. **未绑定就拒绝**。`reward()` 是脚本在要求发钱；宿主没授予能力时静默成功  
   等于"脚本能给自己发钱"，静默失败等于"活动悄悄不生效"——都比抛异常糟。
2. **`log` 是唯一例外**：未绑定时静默丢弃。日志失败不该把活动逻辑打挂。
3. **能力由宿主实现，不由框架实现**。`Context` 只提供"申请"通道，发不发、发多少、  
   走不走 `Settle`，是业务决定。框架不替业务定义经济系统。

测试 8 项：未授权抛错、授权后拿到金额与理由、脚本里的 `if` 真的在跑（不满足条件不发）、  
日志未绑定不抛错。

### 补完之后：5 → 6，不是 8

| 能力                  | 之前   | 现在              |
| :------------------ | :--- | :-------------- |
| 改数值 / 掉落倍率          | ✅    | ✅               |
| 活动玩法（读状态→判断→发奖→记日志） | ❌    | ✅               |
| 换核心玩法逻辑（改类结构、加状态字段） | ❌    | ❌               |
| 脚本内注册定时器 / 跨服务发消息   | ❌    | ❌               |
| 性能                  | 解释执行 | 解释执行（慢 10–50 倍） |

到 8 分需要的是"不丢状态换类定义"，那是 AOT 静态链接与生俱来的限制（§4.2），  
不在这一格的射程内。所以**热更的天花板是 6.5，不是 8**——这个要认。

### 这一轮的方法论

两处短板，一处用 6.6% 否掉，一处用"读懂代码"找到真实成因（而不是想当然的"缺引擎"）。  
共同点：**先定位再投入**。前者省下一个无底洞，后者把一个"以为要造引擎"的问题  
变成了 60 行代码。

## 三十三、网络吞吐重新测量：29 µs 是口径，不是能力（2026-11-23）

### 起因：3.4 万 msg/s 对不上 Swoole 的常识

Swoole 的公开基准里，单 worker TCP echo 是几十万 QPS 量级；我们记的是 3.4 万。  
差一个数量级，这不像是"Swoole 慢"，更像是**测法或口径**的问题。

而且 §2.3 里那条数字自带矛盾：1 连接时 p50 = 0.24 ms。回环 TCP 的 RTT 应该是  
几十微秒——0.24 ms 意味着瓶颈在往返路径上，不在服务端计算里。

### 三组同环境对照（C 压测端 closed-loop，WSL2，4 核）

| 场景                            |            1 连接 |            32 连接 | p50 @32 |
| :---------------------------- | --------------: | ---------------: | ------: |
| Swoole 原生 echo（裸 PHP，无 TSF）   |     3,434 msg/s | **53,195 msg/s** | 0.53 ms |
| TSF `gateway=off`（直连 onFrame） | **4,120 msg/s** |     43,333 msg/s | 0.65 ms |
| TSF `gateway=on`（会话/鉴权/限流全开）  |     3,526 msg/s |     30,058 msg/s | 0.87 ms |

（`bench/probes/swoole-baseline/echo.php` + `bench/load_tsf`，同一台机器、同一次会话）

### 三个结论

**① TSF 的网络层没有额外负担。**

1 连接时 TSF（4,120）**比原生 Swoole echo（3,434）还快 20%**——AOT 在这里是净收益。  
32 连接时 TSF 慢 18%（43.3k vs 53.2k），这部分才是拆包/编码的真实开销。

**② 原来记的 29 µs 是 `gateway=on` 的数字，不能当作"TSF 的网络能力"。**

会话查找 + 限流计数 + 鉴权让 32 连接从 43.3k 掉到 30.1k（**−31%**）。  
这是**功能成本**，不是浪费——但那 29 µs 里塞了三件事（拆包 + Gateway + closed-loop RTT），  
用它给"网络吞吐"打分是低估。

**③ 剩下的差距是运行时，不是设计。**

即便裸路径的 43.3k（23 µs/条），也远高于 Skynet 的 5–10 µs。这个差距来自  
PHP 值语义 + 每帧一次 syscall + Swoole 回调，不是代码质量问题。

### 修正 §32 的一个判断

§32 我写"编解码只占 6.6%，所以放弃投入"。那个对比**口径错了**：  
拿 microbench 的 `encode+decode`（1.9 µs）去比端到端 29 µs，分母里混着客户端和内核。

真实可优化空间是 **TSF 43.3k vs Swoole 53.2k 的 18%（约 4.3 µs/帧）**，  
而不是 6.6%。结论方向没变（不值得大规模重构），但**理由要对**：  
不是"没空间"，而是"空间只有 18%，且要动拆包契约才拿得到"。

### 可优化项：`feed()` 的拆包

现在每帧 `substr($buf, $consumed)` 重建剩余缓冲，并把子串交给 `decode()`。  
在 32 并发下这是 4.3 µs 里的主要部分。改法是把 `FrameCodec` 扩展成"带偏移解码"：

```php
public function decodeAt(string $buf, int $offset): ?DecodedFrame;   // 新
```

代价：Contract 变更 + `HeaderFrame` 与 C++ 版 `NativeHeaderFrame` 同步 + 逐字节比对。  
收益上限 18%（43.3k → 53k）。

**判断：值得做，但不是现在。** 它不改变定位（6.5 分还是 6.5 分），  
而 §32 已确认"补 0.5 分不如把结论收口"。真要冲吞吐，优先项应该是  
"减少 syscall 次数"（批量写、`sendfile`/`writev` 合并），而不是省几次 `substr`。

### 评分修正

| 维度    |  原 |       现 | 依据                                                |
| :---- | -: | ------: | :------------------------------------------------ |
| 网络端吞吐 |  5 | **6.5** | 与 Swoole 基线同档（1 连接更快、32 连接 −18%）；与 Skynet 的差距是运行时 |

加权体感 5.8 → **6.0**。

### 一条方法论

**"端到端数字"不能直接归因给被测组件。** 29 µs 里有客户端 syscall、内核回环、  
Swoole 事件循环、Gateway 三道功能、拆包、编码——把它整体记成"网络的性能"，  
既高估了问题，也指错了优化方向。**先建基线，再谈差距。**

## 三十四、网络瓶颈是真的：换口径之后差 13 倍（2026-11-23）

§33 的结论是"29µs 是口径问题"。这话对了一半——**closed-loop 口径确实低估了吞吐**，  
但换成 pipeline 之后，TSF 与 Swoole 原生的差距**不是缩小而是暴露**。

### 压测端升级：同一份代码两种口径

`bench/load_tsf.c` 加了 `WINDOW` 宏：

- `WINDOW=1`（默认）：closed-loop，收一帧发一帧，**测 RTT**
- `WINDOW=16/64`：pipelined，不等回包继续发，**测吞吐**

关键实现细节：pipeline 下**一次 `send` 拼多帧**。否则每帧一次 write，  
省下的 syscall 又还回去了，测出来的是客户端而不是服务端。

### 四组数据（32 连接，WSL2 4 核）

| 服务端                         | closed-loop |  pipe16 |        pipe64 | 每帧成本@pipe64 |
| :-------------------------- | ----------: | ------: | ------------: | ----------: |
| Swoole 原生 echo              |      49,942 | 806,484 | **1,965,840** | **0.51 µs** |
| TSF `gateway=off`（native 帧） |      38,339 | 117,791 |       153,764 | **6.50 µs** |
| TSF `gateway=off`（PHP 帧）    |           — |       — |        98,143 |    10.19 µs |
| TSF `gateway=on`            |      30,058 |       — |             — |           — |

### 三个判断

**① closed-loop 掩盖了真实差距。**

closed-loop 下 TSF 只比 Swoole 慢 23%（38k vs 50k），看着"差不多"；  
pipeline 下差 **12.8 倍**（154k vs 1966k）。因为 closed-loop 的吞吐被  
RTT 锁死（= 连接数 / RTT），两边都远没跑到自己的上限。

**§33 里"TSF 网络层没有额外负担"这个结论，在吞吐口径下是错的**，必须收回。

**② C++ 帧解析已经起作用，但不够。**

PHP 帧版 98k → native 版 154k（**+57%**）。说明逐字节操作下沉到 C++ 是对的，  
但剩下的 6.5 µs 已经不在帧解析里了。

**③ 瓶颈在用户态代码，不是 syscall。**

推理而非猜测：Swoole 原生 echo 与 TSF **每帧都只有一次 `send`**（syscall 数量相同），  
却有 12.8 倍差距。所以差的不是内核路径，是 TSF 在 `feed()` 到 `sendFrame()`  
之间多出来的用户态工作：

| 环节                              |          估算 | 依据                        |
| :------------------------------ | ----------: | :------------------------ |
| `decode`（native）                |     ~0.3 µs | C++ 版比 PHP 版快 57% 反推      |
| `encode`                        |     ~0.5 µs | microbench 555 ns         |
| `feed` 循环（`substr` + 数组 + 对象分配） |     ~1.5 µs | microbench 1.35 µs + 数组开销 |
| **剩余、未定位**                      | **~4.2 µs** | 差值                        |

那 4.2 µs 最可能在：**`new DecodedFrame()` 每帧一次分配**、  
**`onFrame` 闭包调用（AOT 下的参数装箱）**、**`FrameCodec` 接口虚调用**。  
这三项单看都是"几百纳秒"，但每帧各来一次，累加起来正好是这个量级。

（strace 在 WSL 下 attach 被 Yama 拦，父进程包裹又只能统计 master 进程，  
所以 syscall 占比这条是用"次数相同"推理排除的，不是测出来的。）

### 优化方案清单（按收益/成本排序）

| #  | 方案                                    | 预期             | 成本 | 风险                            |
| :- | :------------------------------------ | :------------- | :- | :---------------------------- |
| 1  | `feed` 改 offset 解析，去掉每帧 `substr`      | 中              | 低  | 要扩 `FrameCodec` 接口 + 同步 C++ 版 |
| 2  | `DecodedFrame` 复用（每帧不再 `new`）         | 中              | 低  | 要改接口语义（传出参 or 池），调用方都受影响      |
| 3  | `onFrame` 从 `callable` 改具体函数签名        | 中高             | 中  | 破坏 API；要给现有多处注册点改写法           |
| 4  | 批量写：一轮处理多帧后合并 `send`                  | 高（pipeline 场景） | 中  | 延迟略增；要处理部分写                   |
| 5  | 让 Swoole 在 C 层拆包（`open_length_check`） | 高              | 中  | 失去"一次读多帧"的批处理机会，需实测           |
| 6  | 把 `feed`+`sendFrame` 整段下沉到 ext/codec  | 最高             | 高  | 业务回调仍在 PHP，边界收益有限             |

**下一步建议先做 1 + 2**（低风险、可测），拿到数据再决定 3/4/5。  
如果 1+2 能把 6.5 µs 降到 4 µs，吞吐就是 154k → 250k，接近 Swoole 的一半——  
这已经足以支撑"百人同屏 30Hz"这类场景。

### 教训

**"口径"能同时制造两个方向的错误**：closed-loop 让我以为"网络没那么差"（§33），  
而 pipeline 又证明"差得很远"。真正可靠的做法是**同时跑两种口径**：  
RTT 看交互体验，吞吐看容量上限，两者不能互相替代。

## 三十五、网络优化落地：批量写，+127%（2026-11-23）

### 先定位，再动手

§34 测出 TSF 每帧 6.5 µs、Swoole 原生 0.51 µs，但不知道钱花在哪。加了采样计时  
（`Server::setProfile`，环境变量开关，关闭时只有一次布尔判断）后：

| 段                               |      占比 | 说明           |
| :------------------------------ | ------: | :----------- |
| `decode`                        |     19% | C++ 帧解析，已经很快 |
| `substr` 重建缓冲                   |      6% | 每帧拷剩余字节      |
| **回调段**（闭包 + `encode` + `send`） | **64%** | 大头           |

再用 A/B 排除两个嫌疑：

- **闭包调用**：把 `$onFrame` 从无类型属性改成 `?\Closure`，吞吐**一模一样**（153,764 → 153,764）
- **encode**：555 ns，占 8%，不是主因

排完之后只剩一个解释：**每帧一次 `send` 的 syscall + 内核缓冲进出**。  
pipeline 下客户端一次灌 64 帧，服务端逐帧回调逐帧写，内核缓冲反复满/空。

### 做法：按连接合并本批回包

`Server::enableBatchSend(true)` 打开后：

1. `feed()` 内 `sendFrame()` 不再立即写，而是按 fd 追加到 `$pending`
2. `feed()` 结束时对每个 fd **一次 `send`** 写出整块
3. `feed()` 之外的调用（定时器广播、`onConnect` 回包）**不进 pending**，立即发

第 3 条是关键：如果一个定时器广播进了 pending 却永远等不到 flush，  
消息会**静默不发**——比慢严重得多。用 `$inFeed` 标记显式区分。

### 效果（32 连接，WSL2 4 核）

| 口径              |     优化前 |         优化后 |        变化 |
| :-------------- | ------: | ----------: | --------: |
| pipeline64      | 153,764 | **348,506** | **+127%** |
| pipeline16      | 117,791 |     233,210 |      +98% |
| closed-loop     |  38,339 |      37,204 |   −3%（持平） |
| 8 连接 pipeline64 |       — |     386,283 |         — |

与 Swoole 原生（1,965,840）的差距：**12.8 倍 → 5.6 倍**。  
每帧成本 6.5 µs → 2.87 µs，**已经优于 §7 里给 Skynet 记的 5–10 µs 区间**  
（口径不完全可比，参考意义有限，但方向明确）。

closed-loop 基本持平是符合预期的：一问一答只有一帧，没有可合并的东西。

### 三个正确性坑（都补了）

1. **feed 外调用会丢消息** → 用 `$inFeed` 区分，外部调用走立即发送。
2. **业务回调抛异常会让 `$inFeed` 卡在 true**，之后所有 `sendFrame` 都进 pending  
   且永不 flush——"服务还在跑，但再也发不出消息"。修法不是包 try（实测热路径  
   try 约 300 ns/帧，pipe64 从 367k 掉到 331k），而是**下一次 `feed()` 开头自愈**：  
   发现标记还在就复位并 flush。零成本，窗口只有一次 tick。
3. **发完就 close**（业务常见写法："回一个错误包然后断开"）→ 在 `closeConn()`  
   里先把该 fd 的 pending 冲掉，否则最后一条消息永远收不到。

### 怎么开

```json
{ "server": { "batch_send": true } }
```

```php
if (Config::getBool("server.batch_send", false)) {
    $server->enableBatchSend(true);
}
```

**默认关**。判断依据是"这个服会不会一次处理多帧"：

- 开：广播型（房间服一次 tick 给 N 个玩家发）、批量结算、高频同屏同步
- 不开：纯一问一答的命令型服务（收益为零，还多一次数组操作）

### 复验

```
verify     18 / 0 / 0
batch-send-test  8 连接 pipeline64 386k，丢包 0‰，无 bad frame，closed-loop 正常
```

### 还剩什么

1. **`decode` + `substr` 那 25%（约 1.6 µs）**：offset 解析能省掉 `substr`，  
   但 `decode` 要改成"带偏移解码"，得同步 C++ 版并逐字节比对。预期再提 10–15%。
2. **Swoole 回调本身的固定成本**：这部分在框架控制之外。
3. **真实业务路径未测**：以上都是 echo。房间服每帧要走 `deliver → onMessage`，  
   那层的成本（Actor 调度约 870 ns）会叠加进来，需要单独一组基准。

## 三十六、批量写对真实业务路径的收益：+33%，但要显式接（2026-11-23）

### 一个被 echo 基准掩盖的问题

§35 的 +127% 是在 **echo 直连**下测的（`onFrame` 里直接 `sendFrame`）。  
但游戏服的每一帧都要走 Actor：`feed → deliver → tick → onMessage → sendFrame`。

**回包发生在 `tick` 里，不在 `feed` 里**。而 `inFeed` 只覆盖 feed——  
也就是说：**批量写对真实业务路径一开始完全不生效**。

这不是小疏漏：如果按 §35 的结论直接上线，房间服会发现自己一点没变快，  
然后怀疑"是不是这个优化没用"。

### 补法：批窗口成对钩子

`Scheduler` 加 `onBatchBegin` / `onBatchEnd`，`tick()` 的首尾各调一次；  
应用把它们接到 `Server::beginBatch()` / `endBatch()`：

```php
$sched->onBatchBegin(function () use ($server): void { $server->beginBatch(); });
$sched->onBatchEnd(function () use ($server): void { $server->endBatch(); });   // 内部 flush
```

为什么用闭包注入而不是让 Scheduler 直接持有 Server：分层方向不能反  
（Service 不依赖 Transport）。

### 三组数据（32 连接，WSL2 4 核，pipeline64）

| 路径                                         |     批量关 |         批量开 |       提升 |
| :----------------------------------------- | ------: | ----------: | -------: |
| echo 直连（`onFrame` 里回包）                     | 153,764 | **348,506** |    +127% |
| **Actor 路径（`deliver → tick → onMessage`）** | 166,943 | **222,746** | **+33%** |

Actor 路径每帧：批量关 6.0 µs → 批量开 **4.5 µs**。  
框架侧开销（deliver + 调度 + `onMessage` + Message 分配）约 1.6 µs，  
这部分不受批量写影响——它是 Actor 模型的固有成本。

### 结论：收益是真的，但比 echo 小得多

+127% 是"传输层上限"，+33% 才是**业务实际能拿到的**。  
两者差这么多，是因为 Actor 路径本身的固定成本稀释了合并收益。

对外说数字时应该说 33%，不是 127%——后者会让业务方产生错误预期。

### 接入检查清单

- [ ] `server.batch_send = true`
- [ ] `onBatchBegin` / `onBatchEnd` 都挂上（只挂 end 不够：没有 begin 就没有窗口）
- [ ] 确认没有"发完立刻 close"的逻辑（`closeConn` 已兜底，但语义上仍应避免）
- [ ] 纯问答型服务不要开（收益为零）

### 复验

```
verify  18 / 0 / 0
echo    直连 pipeline64  348,506
actor   pipeline64       222,746（批量关 166,943）
```

### 下一个瓶颈

Actor 路径的 4.5 µs 里，框架侧 1.6 µs 是**调度 + 消息对象分配**。  
再往下压就要动 `deliver` 的对象分配（每帧一个 `Message`），  
或让"单帧直达服务"跳过 mailbox——但那是**改变 Actor 语义**的事，  
不属于优化，属于重新设计。到这一步应该停下，把结论收口。

## 三十七、热更：为什么"不如 Lua"是个伪命题（2026-11-23）

### 先纠正一个前提

"PHP 比 Lua 快，为什么热更反而不如"——这句话里混了两个维度。

**PHP 快，恰恰是因为它不快。** 更准确地说：TSF 快是因为 **AOT 把代码固化进二进制**，  
而"代码不可替换"是这个选择的**直接后果**，不是缺陷：

|                   | 代码在哪         | 能不能换           | 状态在哪     | 性能 |
| :---------------- | :----------- | :------------- | :------- | :- |
| PHP-FPM           | 每次请求重新加载     | **能**（天然热更）    | 无（每请求重建） | 慢  |
| **PHP AOT (TSF)** | 二进制里         | **不能**         | 进程堆      | 快  |
| Lua + C++         | chunk 在 VM 里 | **能**（换 chunk） | Lua 堆    | 中  |

**性能与"代码可替换"是同一根轴的两端。** TSF 明确选了性能这一端，  
所以"热更弱"不是能力缺陷，是**已支付的代价**。

Lua 那 8 分不是因为它快（它比 AOT 慢一个量级），是因为**解释器常驻 + 代码即数据**。  
传统 PHP 也能做到同样的事——只要放弃 AOT。

至于"方便"：PHP 确实赢。不用写 C++ ↔ Lua 绑定层、不用管 GC 交互、类型转换。  
但那是**开发期**收益，不影响运行期的热更能力。

### 但业务要的不是"换 chunk"

运营真正要的是：**不停服地把新版本换上去**。达成这个目标不必走"换函数"这条路。

上一轮我按"扩大脚本层"算天花板，得到 6 → 6.5。那个判断**只对一条路线成立**。  
换一条路，结论不同：

| 路线            | 能做到             | 成本       |       天花板 |
| :------------ | :-------------- | :------- | --------: |
| 扩大脚本层（§32 已做） | 改配置 / 活动规则 / 发奖 | 低        |       6.5 |
| **滚动迁移（本节）**  | **不停服换版本，玩家无感** | 中        | **7.5–8** |
| 原地换函数（Lua 式）  | 不重启改任意代码        | 不可能（AOT） |         — |

### 机制其实早就齐了

这是这轮最重要的发现：**缺的不是引擎，是编排**。

| 零件                             | 作用                   | 位置               |
| :----------------------------- | :------------------- | :--------------- |
| `Ring::remove()` / `rebuild()` | 退役节点退出环，归属立刻重算       | `src/Shard/Ring` |
| `Rebalancer::scan()`           | 发现"我不该管这个 key"→ 交接出去 | `pkg/handoff`    |
| `Handoff` + `Gate`             | 冻结 → 暂存 → 提交；失败回滚    | `pkg/handoff`    |
| 状态版本协商（§20）                    | 目标版本太旧就拒绝，不制造半坏对象    | `pkg/handoff`    |
| `NodeInfo::$tags`              | 可放版本/构建指纹            | `src/Discovery`  |
| `drain`                        | 优雅退役标记               | `demo/duel`      |

只缺一个"谁在什么时候调 `remove`、等空了再杀"的指挥官。

### 已经验证：状态能跟着归属走

`tests/handoff-test` 新增 8 项（128 项全过）：

```
PASS  找到 6 个归 node2 的 key
PASS  node2 持有 6 个 key
PASS  环里只剩 node1
PASS  这 6 个 key 的归属全部转到 node1
PASS  node1 装下全部 6 份状态
PASS  node2 全部交接完成
PASS  node2 已无归属（可以安全退出）
PASS  统计里记录迁移 6 次
```

流程就是：`ring->remove(2)` → 归属重算 → `Rebalancer::scan` 发起交接 →  
下一轮 scan 收口（`collect` 在 scan 开头跑，这是周期扫描的正常语义，不是漏处理）。

### 还差什么

1. **编排**：`tsf rollout` —— 起新版本节点 → 等注册 → 旧节点 drain → 摘环 →  
   等 `ownCount == 0` → 退进程。现在这些步骤都得手工敲。
2. **版本进环**：`NodeInfo.tags` 已经能带版本，但 `Ring` 不认——需要"只把最新版本的  
   节点算进环"的策略，否则新旧节点会被同时分配。
3. **迁移期的延迟尖峰**：一次交接要冻结 → 传状态 → 提交，单房间大约几十毫秒。  
   白天的滚动更新会让部分玩家感到一次卡顿，需要"低峰期执行"或"限速迁移"。
4. **跨版本协议兼容**：滚动窗口里两版本同时在跑，包格式必须双向兼容  
   （RPC 载荷版本协商 §21 已做，业务消息还没有）。

### 结论

**"PHP 不如 Lua"在热更这一维上不成立**，成立的说法是：  
"**AOT 换来了性能，代价是代码不可原地替换；但用滚动迁移可以达成同一个业务目标  
（不停服更新），只是手段不同**。"

按这条路，热更可以从 6 提到 **7.5**，而不是我上一轮说的 6.5 封顶。

## 三十八、热更的正确层次：AOT 就是 C++，脚本层才是 Lua 位（2026-11-23）

### 先纠正我自己的框架错误

前几节（§32、§37）讨论"热更"时，我把两个层次混在一起了。正确的是：

```
AOT 二进制（等价于 C++）  ← 不该热更，也不该指望能热更
   └── ext/interp + pkg/script（Zend 解释执行）  ← 这才是"Lua 位"
```

**"PHP 热更"从来不是指"改 AOT 编译进去的那些 PHP"**，而是指走 Zend 动态解析的脚本。  
它和 Lua 在 C++ 宿主里的地位完全一致：

|      | C++ / Lua 方案 | TSF             |
| :--- | :----------- | :-------------- |
| 引擎层  | C++（编译）      | AOT PHP（编译）     |
| 逻辑层  | Lua（解释）      | PHP 脚本（Zend 解释） |
| 热更对象 | Lua chunk    | PHP 脚本文件        |

所以问"AOT 能不能热更"本身就是错的问题。**该问的是：脚本层这个"Lua 位"够不够强。**

`ext/interp` 的 README 早就写对了这一点（"AOT 管性能，脚本管可热更的逻辑"），  
是我在评估时跑偏了。

### §37 的"滚动迁移"不算热更

上一节我提了用 `Ring::remove` + `Rebalancer` 做不停服换版本，并给了"7.5 分"。  
**那个能力是有价值的，但它属于核心层（运维手段），不是脚本层热更**——按这个分类，  
它不该计入"热更能力"这一格。本节收回那个评分。

### 脚本层 vs Lua：差在能力面，不在语言

Lua 在游戏服里之所以强，不是因为 Lua 语法好，是因为宿主任册了几十个 C 函数：  
发消息、定时器、读配置、DB、日志、场景查询。脚本能"做事"。

TSF 的 `Context` 之前只有：**字段白名单读写 + 发奖 + 日志**。  
能改数字、能发奖，但：

- 立不了"30 秒后结算"（没有定时器）
- 通知不了别人（没有发消息）
- 读不到活动参数（没有配置访问）

这三样缺一个，"脚本能写玩法"就不成立。

### 本次补的三项

统一成"能力注册表"（`bind($cap, $fn)`），不再一个个加成员字段：

| 能力           | 签名                                                   | 未授权时  |
| :----------- | :--------------------------------------------------- | :---- |
| `reward`     | `fn(int $amount, string $reason): bool`              | 抛错    |
| `log`        | `fn(string $msg): void`                              | 静默    |
| **`timer`**  | `fn(int $ms, string $entry): void`                   | 抛错    |
| **`send`**   | `fn(string $target, int $msgId, string $data): bool` | 抛错    |
| **`config`** | `fn(string $key): string`                            | 返回默认值 |

脚本侧：

```php
"activity" => function ($ctx) {
    if ($ctx->configInt("activity.enabled") === 0) {
        return 0;
    }
    $ctx->timer(30000, "onActivitySettle");   // 30 秒后回调
    $ctx->send("player:1001", 9001, "join");  // 通知
    return 1;
},
```

`$target` 的解析交给宿主（uid / `room:123` / 服务名），框架不把地址空间的细节漏给脚本。

为什么 `config` 未授权时返回默认值而不是抛错：配置是只读的，读不到就按默认走，  
不该让活动因为"没接配置"直接崩；而发奖/定时/发消息是**有副作用的**，必须显式授权。

### 复验

```
[玩法能力] 9 项全过
  未绑定 timer/send 时抛错 / can() 如实反映 / 未绑定 config 返回默认
  开关打开：挂号 30 秒回调 / 发出消息 / 读到配置 / 返回 1
  开关关闭：不挂号、不发消息、返回 0
script-test 33 项全过
```

### 评分

| 维度   | 之前 |      现在 | 依据                               |
| :--- | -: | ------: | :------------------------------- |
| 热更能力 |  6 | **6.5** | 脚本能写"活动玩法"的最小闭环（读配置→判断→挂号→通知→发奖） |

**天花板是 7，不是 8**，差的四样都在脚本层内部，跟 AOT 无关：

1. **脚本间调用**：活动 A 想调活动 B 的入口，现在只能由宿主转一手
2. **脚本私有状态**：reload 后 `static` 变量重置，需要宿主做"状态外置 + 注入"
3. **沙箱**：脚本里写个死循环会卡死整个 worker（`Coroutine::cancel` 也打不断）
4. **错误定位**：`interp_invoke` 返回结构化错误，但没有行号/堆栈

这四项都能补，都是脚本层的工作，**不需要动核心**。

## 三十九、沙箱：能打断死循环，才敢把脚本交给运营（2026-11-23）

### 为什么这条最关键

前面补齐了脚本层的能力面（发奖/定时/发消息/配置），但有一个更前置的问题没解决：

**脚本写错了会怎样？**

一个 `while (true)` 就足以让整个 worker 停止处理消息——不是崩溃，是**不再往后跑**。  
所有玩家一起掉线，日志里什么都没有。而且 §29 已经实测过：`Coroutine::cancel`  
打不断纯 CPU 循环，协程调度也救不了。

在这种前提下，"热更"只能由开发自己用。要让运营改脚本，先得保证他们写错不会拖垮全服。

### 基础设施其实是现成的

读 `interp.c` 才发现 `interp_invoke` 早就用 `zend_try / zend_catch` 捕获 bailout，  
注释里甚至明确写了 "fatal error / **timeout** / oom"——只差没有人去设超时。

所以改动只有一个点：调用前设执行预算，调用后恢复。

```c
if (timeout_ms > 0) {
    zend_set_timeout((timeout_ms + 999) / 1000, 0);
}
zend_try { rc = call_user_function(...); } zend_catch { bailed_out = 1; } zend_end_try();
if (timeout_ms > 0) {
    zend_set_timeout(0, 0);   // 不恢复的话，后面的 AOT 代码也会被同一个超时掐掉
}
```

PHP 8 的 VM 在**每个 opcode** 检查 `vm_interrupt`，所以纯 CPU 死循环也能打断，  
走的是 bailout 路径，正好被已有的 `zend_catch` 接住。

返回结构里加了一个 `timeout: true` 标记，让调用方能区分"脚本写错超时"和  
"其它 fatal（进程状态可能已不可信）"——这两种情况的处置完全不同。

### 默认预算 1 秒，这是兜底不是承诺

`zend_set_timeout` 只接受**秒**。1 秒对游戏服仍然是明显的停顿（心跳、掉帧），  
所以要说清楚：

- **它防的是"永久卡死"，不是"卡顿"**
- 真要"不卡顿"，得在 opcode 层做指令数预算（改 VM handler），属于另一个量级的工程
- 日常防线仍然是脚本审计 + 灰度 + 快速回滚

不夸大这一层的作用，比假装"沙箱很安全"有用。

### 附带解决了一半"错误定位"

超时的那条 Fatal 直接带出了文件和行号：

```
PHP Fatal error: Maximum execution time of 1 second exceeded
  in /data/TypeServer/tests/script-test/loop.php on line 6
```

§38 列的"没有行号/堆栈"这一条，至少 Fatal 类已经能定位到行。  
普通 `throw` 返回的结构化错误里还没有行号，那是下一步。

### 复验

```
[沙箱：执行预算]
  死循环被中断（返回结构化错误）
  在预算附近返回，没有永久卡死（elapsed ≈ 1.0s）
  标记为 timeout（可与其它 fatal 区分）
  再次调用仍返回错误而不是崩溃进程
script-test 37 项全过
```

最后一条尤其重要：**同一个坏脚本再调一次，仍然是被预算打断**，  
而不是"第一次打断了、第二次把进程带走"。

### 评分

| 维度   |  之前 |    现在 | 依据                                     |
| :--- | --: | ----: | :------------------------------------- |
| 热更能力 | 6.5 | **7** | 脚本能写活动闭环 + 写错不会拖垮全服（执行预算 + 结构化错误 + 行号） |

**天花板仍是 7.5**，剩两样：

1. **脚本间调用**：活动 A 调活动 B 的入口，现在只能宿主转一手
2. **脚本私有状态**：reload 后 `static` 重置，需要"状态外置 + 注入"

这两样都是"能写多复杂"的问题，不是"敢不敢用"的问题——后者已经解决了。

## 四十、脚本私有状态：热更不丢计数（2026-11-23）

### 问题：reload 必然重置

热更的本质是**重新 require 一遍文件**——新代码、新闭包、新 `static`。  
这不是 PHP 的毛病，Lua 换 chunk 完全一样。

但玩法偏偏需要跨 reload 活下来的东西：

- 活动已发奖名单（reload 后不能重复发）
- 本轮累计计数（reload 后不能清零）
- 冷却时间戳

### 解法：状态外置，宿主保管

新增 `State`（挂在 `Script` 上），`Context` 暴露读写方法：

```php
"counter" => function ($ctx) {
    return $ctx->addStateInt("hits", 1);   // 跨 reload 累计
},
```

```php
$ctx->stateInt($key, $default) / setStateInt / addStateInt
$ctx->stateString(...) / stateBool(...)
```

**为什么状态挂在 Script 而不是 Context**：Context 是每次调用新建的。  
`Script::load()` 只替换 `exports` / mtime / hash / versions，不碰 `state`——  
所以"改脚本"不丢状态，这是白拿的。

**为什么用对象而不是数组**：PHP 数组是值语义，`Context` 拿到的是副本，写回去就丢了。  
必须用一个对象持有，所有 Context 共享同一引用。

### 生命周期说清楚

| 事件               | 状态     |
| :--------------- | :----- |
| 同一 Script 多次调用   | 保留     |
| `reload()`（热更）   | **保留** |
| 进程重启 / 新建 Script | **丢失** |

跨进程要自己落：`state()->export()` 出 `array`，重启后 `import()` 回去。  
放 Redis 还是文件由业务决定——框架不替业务选持久化介质。

只允许标量（int/string/float/bool）：脚本状态是"计数器/时间戳/开关"这类，  
复杂结构该落库，不该在内存里堆。

### 复验

```
[脚本私有状态]
  第一次调用计数 1 / 第二次 2（跨调用累计）
  reload 成功 / 版本号递增
  reload 后计数继续（3），没有清零        ← 关键
  state() 能导出当前值 / 宿主写入的也能被读到
  新实例从 1 开始（状态不跨进程）
  导出/导入可以恢复状态 / 字符串字段也恢复
script-test 47 项全过
```

`import()` 只接受标量，非法值直接丢弃而不是报错——恢复数据时不该因为一个  
脏字段让整个脚本起不来。

### 评分

| 维度   | 之前 |      现在 | 依据                              |
| :--- | -: | ------: | :------------------------------ |
| 热更能力 |  7 | **7.5** | 能力面齐（发奖/定时/发消息/配置）+ 执行预算 + 私有状态 |

**离 8 还差两样**：

1. **脚本间调用**：活动 A 调活动 B 的入口，现在只能宿主转一手
2. **能操作的业务对象面**：现在 `Context` 是白名单字段，Lua 宿主任意给表。  
   这是"安全 vs 表达力"的取舍——TSF 选了安全，代价是复杂玩法仍需 AOT。

第 2 条是设计取向，补不了也不需要补；第 1 条是纯工程，做完脚本层就基本对标 Lua 了。

## 四十一、脚本间调用：脚本层的最后一块（2026-11-23）

### 设计上有两个必须防的东西

**① 不能随便调**。脚本 A 如果能调任意脚本，沙箱就形同虚设——  
它可以让 B 去干 A 不该干的事。所以 `callScript` 收的是**逻辑名**  
（`"activity"`、`"mail"`），由 `Manager` 的注册表映射到文件；脚本不知道路径。

**② 不能成环**。A→B→A 是很容易写出来的错误，必须由宿主兜底：  
`Manager::MAX_DEPTH = 8`，超过就抛错，且用 `finally` 保证深度计数复位  
（否则一次失败的递归会毒化后续所有调用）。

### 一个被测试逼出来的设计修正

第一版让业务在每处调用点手动 `bind("callScript", ...)`。测试"循环调用"直接失败：

```
script self:loopCall failed: script: 没有脚本间调用能力（宿主未 bind("callScript")）
```

原因是 `Manager::invoke` 新建的 Context **没有绑自己的能力**——  
A→B 能通（外层绑了），B→C 就断。这类"第二层才暴露"的缺陷，  
只有真的构造嵌套调用才能发现。

修法：`invoke` 里自动绑定 `callScript` 指向自己。  
判断依据是**这个能力属于脚本层自身**（`Manager` 就是它的实现），  
而 `reward`/`send`/`timer` 属于业务，Manager 不知道实现，所以只能靠业务绑。

### 另一个修正：失败不能静默变 null

目标脚本出错时 `interp` 返回 `{ok:false,...}`。第一版把它转成 `null` 返回——  
调用方会以为"对方返回空"，而不是"对方炸了"。这类问题最难查。

现在改成抛 `RuntimeException`，沿调用链上抛，最终由最外层的  
`interp_invoke` 收成结构化错误。**错误要有归属，不能被类型转换吃掉。**

### 复验

```
[脚本间调用]
  未 bind callScript 时抛错
  A 调到 B、传参、拿到返回值（pong:hello）
  入参存在 Context 上，不碰业务字段
  循环调用在第 8 层被拦下（不拖死进程）
  递归失败后深度已复位，正常调用不受影响
script-test 52 项全过
```

### 到这里，脚本层的能力面对标 Lua 了

| 能力            | 状态               |
| :------------ | :--------------- |
| 定义逻辑、被宿主任意调用  | ✅                |
| 读写宿主状态（受控）    | ✅ 白名单字段          |
| 副作用（发奖/通知/定时） | ✅ 显式授权           |
| 私有状态跨 reload  | ✅                |
| 脚本间调用         | ✅ 带深度限制          |
| 死循环保护         | ✅ 秒级             |
| 任意操作业务对象      | ❌ **刻意不做**（安全优先） |

最后一条是有意为之的取舍，不是遗漏。

### 文档

`docs/guide/12-hot-reload.md` 第六节已按现状重写（原来是"只能改白名单字段"的旧说明），  
新增能力表、活动脚本示例、生命周期表、安全边界表、与 Lua 的逐项对照。

判据：**同一件事只留一份权威描述**。评审记录（本文档）讲"为什么"，  
指南（`12-hot-reload.md`）讲"怎么用"。

## 四十二、上手成本：先让报错说人话（2026-11-23）

### 定位方法：拿自己当样本

"上手成本 5 分"是个笼统的说法。要改，先要找出**具体卡在哪一步**。

最省力的取样方式：**看我这一周自己踩了什么坑**。一个已经熟悉框架的人（还带着完整  
文档和 AI 辅助）都会卡的地方，新人必然更卡。

结果很集中——三次都卡在 AOT 类型系统上：

| 坑      | 报错                                                                       | 为什么看不懂                                            |
| :----- | :----------------------------------------------------------------------- | :------------------------------------------------ |
| 变量名复用  | `Cannot assign value to variable $k of type php::Str with type php::Var` | `php::Str` / `php::Var` 是编译器内部类型名，跟"我写的哪一行"没有对应关系 |
| 顶层调用函数 | `All execution code must be within a function, found stray code`         | 普通 PHP 完全合法的写法                                    |
| 变量定义顺序 | `The variable $profOn is undefined`                                      | 明明上面写了赋值，只是顺序在后                                   |

共同点：**报错是"编译器视角"，不是"作者视角"**。它告诉你违反了哪条规则，  
但不告诉你"这在你眼里长什么样、该怎么改"。

### 顺带发现：错误会被淹掉

`tsf build` 是把 tpc 的输出原样透传的。一次失败刷 30+ 行，其中 `Fatal error:`  
只占一行，夹在 `prepare: ...` 和 `#0 /home/hhr/.tsf/toolchain/...` 的调用栈中间。

我自己的做法是"再跑一次 grep Fatal"——这不是新人会想到的操作。

### 做了两件事

**① 提炼**：失败后把 `Fatal error:` / `error:` / `Compilation failed` 开头的行  
单独列一遍（最多 5 条），放在输出的最后。

**② 给修法**：按已知模式匹配，附一条 `hint:`。现在覆盖 8 条：

```
关键错误：
Fatal error: Cannot assign value to variable $k of type php::Str with type php::Var in .../main.php:7

hint: 同一个变量先后承担了两种类型。AOT 在编译期就确定变量的类型，不能像 PHP 那样动态变。
  改法：换个变量名（推荐），或在首次赋值处就保证类型一致。
  典型来源：循环里先 `$k = "prefix" . $i;`，后面又 `foreach ($list as $k)`。

类型相关的完整规则：docs/guide/08-aot-types.md
```

覆盖的 8 条：变量类型冲突 / 变量未定义 / 顶层执行代码 / 闭包未 capture /  
typed object 重赋值 / mixed 禁用 / 链接符号缺失 / project.yml 找不到。

**原则是不试图覆盖所有错误**，只覆盖"看过一次就懂、但第一次必踩"的那些。

### 复验

```
scripts/check-hints.sh
  PASS  提炼出了关键错误（没有淹没在日志里）
  PASS  给出了修法提示
  PASS  提示是可操作的（不是复述错误）
```

### P0-2：Cron 二选一 —— 只做到"可安全合并"，没有合并

**先做对拍，再谈合并。** 写了一个交叉验证用例（`tests/schedule-test`，16 项）：

```
用核心 Timer\Cron::next() 算出未来 5 次触发时刻
再用 Schedule\Cron::matches() 逐分钟验证：
  - 这 5 个时刻必须全部 matches=true
  - 它们之间的每一分钟必须 matches=false
```

8 个表达式全部一致，包括最容易错的两类：

- `0 0 1 * 1`（每月 1 号**或**每周一）
- `30 2 * * 0` / `0 9 * * 1-5`（跨周范围）

### 为什么没在这一轮合并

查清之后发现"重复"比想象的深一层：

|      | `Timer\Cron`（核心）        | `Schedule\Cron`（包）                  |
| :--- | :---------------------- | :---------------------------------- |
| 字段   | 5（无秒）                   | 5 或 **6**（带秒）                       |
| API  | `parse()` 对象 + `next()` | `parse()` 数组 + `matches($expr,$ts)` |
| 解析缓存 | 有（表达式→对象）               | **无**（每次 matches 都重新解析）             |
| 能力   | 算下次触发                   | 判当前是否匹配                             |

真正的重复是**解析逻辑**（正则切分、范围/步长、掩码构造）各写了一遍，  
而不是语义不同。合并只有一条正确路径：把"表达式 → 掩码"抽成核心的一份，  
两个类都消费它。

**但直接让包委托核心不行**：核心只认 5 字段，包支持秒级，委托会直接打断  
6 字段的用法（`tests/schedule-test` 里有 6 段表达式的用例）。

所以合并 = 核心 Cron 支持秒 + 抽出共享解析器 + 改两处消费方。  
这是**核心定时器路径**的改动——Scheduler 的每日重置这类任务都走它。

**判断：不做半成品。** 对拍已经把"能不能合"验证清楚了，  
剩下的是"怎么合"，需要独立一轮 + 全量回归保护。硬塞进本轮只会留下一个  
既没合并干净、又动了核心的中间状态。

### 更正：§45 里「Schedule\Cron 没有解析缓存」是错的

我上一节写「`Schedule\Cron::matches` 每次调用都重新解析」，这是**只看接口签名**  
得出的错误结论（`matches($expr, $ts)` 收字符串，看起来像每次都要解析）。

实际读实现：`Schedule\Cron` 第 33 行就有 `private static array $cache`，  
解析结果按表达式缓存，和核心一样。**没有性能问题，这条作废。**

记下来是因为它暴露了一个方法问题：**从签名推断实现，比不推断更危险**——  
它会产出一个听起来很具体、其实不成立的建议。

## 四十六、Cron 合并完成：一份实现，两种字段（2026-11-23）

### 改动

核心 `Timer\Cron` 现在同时支持 5 字段（分时日月周）和 6 字段（秒分时日月周），  
并新增 `matches()` / `match()`。`pkg/schedule/src/Cron.php` **删除**。

```php
Cron::parse("0 5 * * *")->matches($ts)      // 5 字段
Cron::match("0/5 * * * * *", $ts)           // 6 字段，静态便捷
Cron::next("0 5 * * *", $fromTs)            // 下次触发（不变）
```

### 关键约束：支持秒，但不能让 5 字段变慢

`nextRun` 最坏要遍历 1461 天 × 24 小时 × 60 分钟。如果在最内层再加一层 60 次的  
秒循环，就是 **60 倍开销**——这是"统一实现"最容易踩的坑。

做法是把秒掩码单独存（`$secMask`，默认 1 = 只有第 0 秒），然后：

```php
if ($this->secMask === 1) {          // 5 字段：整层跳过
    if ($base >= $start) return $base;
    continue;
}
for ($sec = 0; $sec < 60; $sec++) {  // 6 字段：才进秒循环
    ...
}
```

起点对齐也分开：5 字段从"下一分钟边界"，6 字段从"下一秒"。

### 一致性：matches 与 next 必须共用同一套规则

`matches()` 复用 `dayMatches()`（日/周取或那段），**没有另写一份判断**。  
否则会出现"`next()` 算出来的时刻，`matches()` 判定不匹配"这种自相矛盾——  
这类 bug 极难发现，因为两边单独看都"对"。

对拍用例（`tests/schedule-test` 的 16 项）正好覆盖这一点：  
核心算出 5 个时刻 → 旧包内实现判定全部匹配 → 间隙无一匹配。合并后这套对拍  
变成了"新实现与历史行为一致"的回归。

### 顺手发现：两个测试从没进过回归

改完之后跑 `verify timer` / `verify schedule`，返回 **"通过 0 / 失败 0"**——  
这两个 id 根本不在套件列表里。

`tests/timer-test` 和 `tests/schedule-test` 一直有 `main.php`，但没有 `run.sh`，  
所以 `tsf verify` 从来没跑过它们。**我改的是核心定时器逻辑，而它的测试在裸奔。**

已补两个 `run.sh` 并接入：verify 21 → **23 个套件**。

这条比 Cron 合并本身更值得记：**"有测试文件"和"测试在跑"是两件事**。  
判断一个模块有没有保护，要看 `verify --list` 里有没有它，不是看 `tests/` 有没有目录。

## 四十八、P2：demo 脚本是"没进回归的验证"，不是垃圾（2026-11-23）

### 盘点结论推翻了我的预设

上一节我把 `demo/` 根目录那 9 个脚本描述成"没有说明的一次性脚本"。逐个读头部  
注释之后发现它们**都是有明确目的的手工验证工具**：

| 组         | 脚本                                | 验证什么                               |
| :-------- | :-------------------------------- | :--------------------------------- |
| 拆包/粘包     | `frame-test.php`                  | 分段发送、两帧合并、非法帧断开、异常后恢复              |
| 背压        | `bp-run.sh` + `bp-test.php`       | 客户端只发不读时，服务端发送缓冲堆满应断开它             |
| 网关        | `m1-run.sh` + `m1-test.php`       | 鉴权、顶号、心跳、限流                        |
| 协议切换      | `proto-run.sh` + `proto-test.php` | 只改 `protocol.payload` 跑 raw / json |
| WebSocket | `ws-run.sh` + `ws-test.php`       | WS 传输收发                            |

**而 `tsf verify` 里一个都没有。** 也就是说：拆包/粘包、背压、顶号、限流这些  
关键路径，长期只靠"想起来就手工跑一次"。

问题不是"脚本冗余"，是**这批验证没进回归**。

### 做了一个，其余留手工（有理由）

`frame-test` 转成了正式套件（`tests/frame-test`）：

```
PASS  case1 分段发送
PASS  case2 粘包
PASS  case3 非法帧被断开
PASS  case4 异常后仍可用
```

它值得每次回归都跑：拆包写错的表现是"偶发丢消息"，非法帧处理错是"一条坏连接  
拖垮整个 worker"——都不崩，但都致命。

**其余四组没转**，原因是它们需要**改运行时配置**：proto 要切 payload、m1 要调限流、  
bp 要关限流并调小发送阈值。而 `verify` 套件的隐含约定是"不改共享配置、不抢固定端口"，  
硬转会让套件之间互相污染（它们改的都是同一个 `demo-echo/config/tsf.json`）。

所以采取的是：**加 `demo/SCRIPTS.md`**，写清每组验证什么、前置条件、跑完要检查配置  
是否复位，并在 `demo/README.md` 里链过去。

### 归位尝试失败，退回原位

我本来想把它们移进 `demo/scripts/`。移完发现每个脚本内部都写着  
`cd "$(dirname "$0")"` + `./demo_echo`——移动会同时打断相对路径。

改成 `$HERE/../demo-echo` 是可行的，但**要逐个验证能跑**（每个都要改配置、起服务、  
看输出）。收益（目录清爽）远小于风险（改动后没人会立刻发现脚本坏了）。

**退回归位。** 用 `SCRIPTS.md` 解决可发现性，比动一个没人持续验证的脚本安全。

这条判断值得记：**"整理"类改动如果无法验证，就不要做**——它不会立刻出错，  
但会在半年后某个人想用的时候出错，而那时没人记得是被整理过。

## 四十九、领域复盘（db）：一个静默数据污染 + 一个"假绿"机制（2026-11-23）

领域复盘换了方法：不看"有没有调用"，看**出错时会不会静默出错**。  
第一个对象是 `pkg/db`（1717 行，最大的包，也是唯一管数据一致性的）。

### 问题一：嵌套事务内层失败被吞 → 外层照常提交

`transaction()` 的嵌套用"深度"而不是 SAVEPOINT，注释里的理由是：  
业务里"函数 A 开事务、A 里调了也会开事务的 B"语义上就该是一个事务。这个判断是对的。

但它漏了一种写法——**很常见的一种**：

```php
$db->transaction(function ($db) {
    $db->insert(甲);
    try {
        $db->transaction(function ($db) {
            $db->insert(乙);
            throw new RuntimeException("内层失败");
        });
    } catch (RuntimeException $e) {
        $log->warn("内层失败，忽略");     // ← 业务吞掉，继续
    }
    // 外层正常结束 → commit
});
```

内层抛异常时 `txDepth` 从 2 减到 1，异常抛出；外层业务把它吞掉，闭包正常返回；  
`txDepth === 1` → **commit**。结果：甲、乙都被提交。

**内层失败 = 整个事务不可能有正确结果**，但代码照常提交了。而且是静默的：  
没有报错、没有日志，库里的数据就是脏的。

### 修法：rollback-only 标记

任何一层失败都给事务打标记，外层 commit 前检查：有标记就把 commit 降级成 rollback，  
再抛出来告诉调用方"你以为提交了，其实没有"。

```php
$failed = false;
try {
    $fn($this);
} catch (\Throwable $e) {
    $failed = true;
    $err = $e;
    $this->txRollbackOnly = true;    // 内层失败也打标记
}

if ($isOuter) {
    if ($this->txRollbackOnly) {
        $this->txRollbackOnly = false;
        $pdo->rollBack();
        $failed = true;               // 内层吞掉的异常，只能给补偿提示
    } else {
        $pdo->commit();
    }
}
$this->txDepth--;
if ($failed) { throw $err ?? new RuntimeException("...内层失败已被吞掉..."); }
```

**改的时候我自己先踩了一个坑**：第一版把 `throw` 写在 `try` 里，被自己的 `catch`  
接住，`txDepth` 减了两次，事务深度变负——之后**所有事务静默失效**。  
这类改动必须在同一个出口统一收尾（先收集失败、再统一处理），不能在中间抛。

### 问题二：测试报了 FAIL，`tsf test` 报 PASS

改完之后跑测试，`tsf test db` 显示 **"通过 2 / 失败 0"**。但直接跑二进制：

```
结果: 87 通过 / 2 失败
```

两个 FAIL 明明在输出里。原因是 `runOneTest()` 只判退出码（`$rc === 0 ? "PASS"`），  
而**大部分 `tests` 下的 main.php 结尾没有 `exit(非零)`**——测试自己报了 FAIL，  
进程仍然返回 0。

**这是"假绿"，比没有测试更危险**：它会让人相信这块有保护。

修法：判退出码之外，再解析一遍输出——出现 `FAIL` 行或 `failed=N`（N>0）也判失败。  
改完用一条临时失败断言验证过（`FAIL db-test ... 89 通过 / 1 失败`），确认真的能抓到。

### 顺带：db 的两个套件从没进过回归

`tests/db-test`（647 行）和 `tests/migrate-test`（324 行）都只有 main.php、没有 run.sh，  
`verify` 里也没有它们。加上问题二的假绿，等于**db 包长期在"看起来有测试"的状态下裸奔**。

已补两个 `run.sh` 并接入：verify 24 → **26 个套件**。

`db-mysql-test` / `db-pg-test` / `db-shards-test` 仍然不进 verify——它们要真实 MySQL /  
PostgreSQL / 多库实例，属于手工验证。

### 复验

```
db-test        89 / 0（修前是 87 / 2）
migrate        PASS
verify         26 / 0 / 0
```

### 这条经验

**领域复盘要看"出错时的行为"，不是"有没有被调用"。**  
§47 用调用计数盘点，结论是"只有 1 个死代码"；这次用"失败路径"盘点 db，  
立刻挖出一个会静默污染数据的问题——**它不是死代码，它在热路径上，而且测试也就差一条断言**。

## 五十、领域复盘（handoff）：双写窗口是"已知代价"，但没人验证过（2026-11-23）

继续用同一套方法：**找"出错时会静默发生什么"**。handoff 管跨节点状态迁移，  
失败就是数据分家，比 db 更难查（涉及网络、两个进程、时钟）。

### 先确认幂等性做得很好

逐个看了五条路径，都在：

| 场景                | 处理                                  |
| :---------------- | :---------------------------------- |
| 重复 MIGRATE（已装同版本） | 回 ACCEPT 但**不重装**（否则会把正在跑的对局覆盖成旧状态） |
| 迟到的 ACCEPT（已超时回滚） | **忽略**（此时业务已本地继续，认了会把状态凭空删掉）        |
| 撤销后迟到的 MIGRATE    | 查 `aborted` 墓碑 → 拒绝                 |
| 目标版本更旧            | 回 REJECT(version)，源侧按节点退避           |
| 重复移除              | 返回 false，不抛异常                       |

这部分设计密度很高，注释里也写清了"为什么不用异常表示拒绝"  
（正常路径不该进错误日志，会把真故障淹掉）。

### 缺口：协议里没有"最终确认"

`expire()` 的注释自己承认了一个代价：

> 撤销也可能等不到 ABORTED。超时后照样回滚本地：此时"目标侧可能还留着那份状态"  
> 是已知代价，比永远卡在 aborting 好。

顺着这条查下去，发现它比注释说的更严重——**源的超时回滚不主动发 ABORT**：

```
expire() 里只有：$this->fire($this->onRollback, $key, ...)
没有：reply(MSG_ABORT)
```

而 Rebalancer 收到 rolledback 也只是 `gate->rollback()` + 设 `retryAt` 重试。

于是完整的双写窗口是：

1. 源 `begin()` 发出 MIGRATE
2. 目标 `onInstall()` 成功（状态已落在目标）
3. 目标回 ACCEPT，**ACK 在网络上丢了**
4. 源 `expire()` 超时 → 回滚 → **源继续托管这个 key**
5. 目标那份**还在**，没人清理（协议里没有 COMMIT 确认，也没有主动 ABORT）

**写了用例把它钉住**（`runLostAck`，6 项全过），关键三条：

```
PASS  目标侧已安装
PASS  源侧已超时回滚  (timeout)
PASS  目标侧状态仍在（双写窗口存在）
PASS  源侧没有发 ABORT，目标未清理
```

为什么值得写一个"验证缺陷存在"的用例：**"已知代价"如果只是一句注释，  
将来改协议的人不知道要验证什么**。钉成断言之后，一旦有人加了 COMMIT 确认  
或让 expire 主动发 ABORT，这条会变红，提醒他回来改注释。

### 补的是契约，不是协议

改协议（加 MSG_COMMITTED）风险高：滚动升级窗口里新旧二进制要共存，  
新消息旧版本不认。所以这一轮只做了一件零风险的事：**把隐含契约写进 `onInstall` 的注释**。

核心一句：

> **装载 ≠ 可以对外服务。** `onInstall` 里只做暂存——不要注册路由、  
> 不要让消息路由到这个 key、不要宣称归属。在 `onInstall` 里抢归属，  
> 一旦源侧回滚，就是两个节点同时服务同一个 key。

这条不说清楚，业务很容易在 `onInstall` 里就 `$registry->claim($key)`——  
那正是金币复制类事故的起点。

### 顺带抓到自己新写检查的一个误报

上节给 `tsf test` 加的"输出里出现 `failed=N` 也判失败"，在 handoff 上误报了：  
这个套件有个用例把 `failed=1` 当作**数据**打在输出里（验证计数器）。  
全绿的套件被判成 FAIL。

收紧成只认行首的两种格式：`^\s*FAIL\s` 和 `^passed=\d+ failed=[1-9]`。  
改完两边都验证过：handoff 恢复 PASS，db-test 注入一条假失败仍能抓到。

**误报的代价是让人开始无视红色，比漏报更糟**——这条在自己身上又验证了一次。

### 复验

```
handoff   134 项（新增 6 项双写窗口）
verify    26 / 0 / 0
```

### 领域复盘的结论

handoff 的**实现质量比预期高**（五条失败路径都有对应处理、幂等性完整），  
真正的缺口在**协议层**（没有最终确认），而它已经被注释承认为代价。

**这种"实现没问题、协议有缺口"的情况，不要在代码层硬补**（会引入新状态），  
要么改协议（要等一个允许不兼容的窗口），要么把契约写清让业务避开。  
这一轮选了后者。

## 五十一、领域复盘（room）：没找到严重缺陷，这本身是结论（2026-11-23）

第三个领域。前两个（db / handoff）都挖到了真问题，这次**没有**——值得如实记下来，  
因为"查了一圈没找到"和"没查"在文档里长得一样，区别只在过程。

### 查了三个高危点，都做对了

| 高危点  | 会静默出什么                             | 实际                                                                |
| :--- | :--------------------------------- | :---------------------------------------------------------------- |
| 座位回收 | remove 后 `bySeat` 没清 → 明明有空位却判"满员" | `remove()` 里 `unset($this->bySeat[$m->seat])` ✓                   |
| 宿主复用 | 每次开房都 spawn → Service 无限增长         | `ensureHost()` 复用 load 未满的宿主，上限 = 峰值房间 / maxRoomsPerHost ✓        |
| 销毁时序 | DROP 之后排队中的帧消息打到已删房间               | `dispatch()` 先查 `isset($this->rooms[$id])`；`tickAll` 遍历的是已摘表的数组 ✓ |

还验证了一条容易错的链路：`create()` 是**异步投递 ADD**，同一 tick 内连续  
`create` + `destroy` 时，`ADD` 与 `DROP` 的顺序靠 mailbox FIFO 保证——  
注释里明确写了这一点，实测也对。

### 两个小问题（会误导人，不影响正确性）

**① `Room::add()` 的注释与实际不符**

原文："只有房间已关闭时才拒绝 —— 其余状态由业务判断"

实际 `false` 有四种原因：已关闭、`uid <= 0`、**重复加入**、**席位已满**。  
业务按注释理解，会以为 `false` 只代表"房间关了"，然后去查 `isClosed()`  
发现是 false —— 困惑。

已改成列全四种，并补一句"要区分原因请自己查 `has()/isClosed()/playerCount()`，  
别猜 false 的含义"。

**② `closeIdleHosts()` 零调用、零测试**

注释写得很清楚："不自动回收……交给巡检定期调用更安全"，理由是自动 kill 会和  
"刚投了 ADD 还没被处理"产生竞态。

**但仓库里没有任何地方调它**，`demo/doudizhu`（唯一用 RoomManager 的示例）  
也没有。等于"提供了工具，但没人知道要用"。

不回收的后果不是泄漏（宿主会复用），而是**峰值过后不缩容**——空宿主还在转定时器  
（每秒 20 次）。要不要回收取决于业务态度，但至少该有测试证明它能用。

补了 5 项（`caseReapIdle`）：3 间房 / 每宿主 2 → 2 个宿主；全销毁后  
`closeIdleHosts()` 回收 2 个；回收后再开房正常，且只重建 1 个宿主  
（验证 `hostAddr` 被清 0，否则会把新房间投给已死的宿主）。

room-test 100 → **105 项**。

### 方法上的收获：先假设再验证，比直接读代码有效率

这轮我先列了三个"这类系统最容易静默出错的地方"（座位表 / 宿主表 / 销毁时序），  
然后逐个去代码里找对应处理，而不是从头读 1544 行。

三次都在——但**每一次都要打开代码确认**。如果哪次发现"这里没有清理"，  
就是一个真缺陷。这个流程比顺序阅读快得多，而且不容易漏。

反过来说：**如果某个模块查完没问题，不要硬凑一个问题出来。**  
把"查了哪三点、为什么认为没问题"写清楚，比编一个"优化建议"有价值。

## 五十二、领域复盘（eventlog）：实现很硬，但归并层零覆盖（2026-11-23）

第四个领域。eventlog 丢一条事件不会崩、不会报错，只在回放时少算数据——  
所以先看它的持久化保证。

### 核心路径的质量很高，而且每处都写着"为什么"

| 设计点       | 做法                                              | 注释里提到踩过的坑                                                 |
| :-------- | :---------------------------------------------- | :-------------------------------------------------------- |
| 两种模式      | `FLUSH`（抗 kill -9，1.2µs/条）/ `SYNC`（抗掉电，4.3ms/条） | 成本实测                                                      |
| **序号高水位** | 存 `{path}.seq`，不只依赖文件                           | "截断后序号退回 1 → 检查点说折到 100、新事件从 1 开始 → `replay(101)` 一条都读不到" |
| 写失败       | **抛异常且不回滚 seq**                                 | "宁可留个洞，也不要两条事件共用一个序号"                                     |
| 坏行        | `replay` 遇到坏行就 `break`，`repair()` 截到最后一个好行      | 代码注释                                                      |
| 增量检查点     | 先写 delta 再 trunk；临时文件 + rename                  | "反过来的话崩在中间等于把状态删了"                                        |

这四处判断都对，尤其是"写失败不回滚 seq"和"高水位"——两个都是典型的  
"看起来能省事、实际会静默丢数据"的地方。

### 缺口：MergedLog（多节点归并）零测试

81 行的归并逻辑——排序键 `(t, 文件序号, s)`、内部字段 `_f` 的清理、  
`fromSeq` 的跨文件语义——**一条测试都没有**。

补了 5 项（`caseMerged`），其中一项钉住了一个**容易被误用的语义**：

```php
// fromSeq 是"每个文件各自的 seq"，不是全局位置
$m3 = MergedLog::replay([$a, $b], 4);   // A 有 3 条、B 有 2 条 → 返回 0 条
```

**为什么这条值得写**：不同节点的序号各自从 1 开始。如果谁把它当"全局第 N 条"  
拿去做增量对账，传一个 100，会把所有条数不足 100 的节点**整体跳过**——  
静默漏掉一个节点的全部事件。这不是 bug（语义如此），但是一个必须显式记录的陷阱。

其余四项：归并结果确定性（两次跑一致）、`_f` 不泄漏、`fromSeq=2` 的过滤边界。

### 更大的发现：21 个测试目录没有 run.sh

## 五十四、领域复盘（registry）：挖到 AOT 的退出码黑洞（2026-11-23）

第五个领域。registry 管节点租约，错了会脑裂（两个节点都认为自己是 owner），  
所以先看它的互斥实现——结果那部分是对的，问题在别处。

### registry 本体：三处 Lua 都是教科书写法

| 动作 | 实现                        | 注释里的判断                                |
| :- | :------------------------ | :------------------------------------ |
| 取  | `SET key token NX PX ttl` | 原子，"两个节点同时 GET 到 nil 再都 SET"不会发生      |
| 续  | Lua：值是我的才 `PEXPIRE`       | **"续比取更危险：A 过期后 B 拿到，A 的续期会把别人的锁续上"** |
| 放  | Lua：值是我的才 `DEL`           | 同上                                    |

"续和放比取更危险"这句判断很到位——取错了立刻能看出来（两边同时搬），  
续/放错了要等下一次事故才暴露。

### 一个真 bug：release 的返回值漏了 `> 0`

```php
// 改前
$out = ...EVAL LUA_RELEASE...;
return is_int($out);          // ← 0 也返回 true

// 改后（与 renew 的口径一致）
return is_int($out) && $out > 0;
```

Lua 的 `DEL` 返回 0 表示**值不是我的**（租约已过期或被别人拿走），什么都没删。  
但 `is_int(0)` 是 true。后果：调用方以为"我释放了"，接着做善后  
（通知别的节点接管、删本地状态），而它早就不是 owner 了。

测试只覆盖了 release 的**正向**（"释放成功"），负向一条都没有——所以一直没暴露。

### 然后发现这个套件是"假绿"

顺手看 `verify registry` 的输出：

```
PASS  registry       Redis 注册表+租约（38 项，无 Redis 则 SKIP）   2.2s
```

本机**没有 Redis**。直接跑产物：

```
SKIP 连不上 Redis（127.0.0.1:6379）—— 跳过而不是判失败
```

一条断言都没跑，verify 显示绿色 PASS。原因在 `run.sh` 第 28 行：

```bash
case "$OUT" in
    *SKIP*) exit 0 ;;      # ← 环境没装不该判红
esac
```

作者的注释写着"别假装测过（SKIP 字样会出现在 verify 的输出里）"——  
但**输出里有 SKIP 字样，判定仍然是 PASS**。看到绿条的人不会去翻中间那一行。

改成 `exit 77`（verify 约定的 SKIP）后：

```
SKIP  registry       Redis 注册表+租约（38 项，无 Redis 则 SKIP）   2.0s
```

### 顺着"SKIP 为什么传不出去"，挖到真正的黑洞

想给测试加 `exit(77)` 表达 SKIP，于是先验证 `exit` 在 AOT 产物里到底怎么工作：

```php
function main(): void { exit(77); }
```

编译、运行 → **退出码 0**。

再试 `exit(1)`、`exit(3)`、`\exit(3)` → **全是 0**。

**AOT 产物忽略 `exit()` 的参数，退出码恒为 0。**（TypePHP 0.9.x 实测）

这解释了一批"说不通"的现象：

| 位置                               | 意图                        | 实际                                                           |
| :------------------------------- | :------------------------ | :----------------------------------------------------------- |
| `Bootstrap::fatal()`             | 注释写"以非 0 退出，**避免静默死掉**"   | `exit(1)` → 退出码 0 → **正是静默死掉**：supervisor/k8s 认为正常退出，不重启、不告警 |
| `demo/duel` 的 migrate 分支         | `exit($code)`，让部署脚本知道迁移成败 | 失败也返回 0 → 部署继续启动一个没迁完的服务                                     |
| `demo/doudizhu` 的 migrate-status | 有 pending 时 `exit(1)`     | 恒为 0 → 脚本无法判断"还有未应用的迁移"                                      |
| 所有测试的 `exit(1)`                  | 表达失败                      | 恒为 0（好在 verify 走 run.sh 的 bash 退出码，不受影响）                     |

**最讽刺的是 `Bootstrap::fatal()`**：它的注释明确写着"避免静默死掉"，  
而它自己是整条链路上最典型的静默死掉。

### 修法：集中到一个 `exitWith()`

```php
public static function exitWith(int $code): void
{
    if ($code !== 0 && function_exists("posix_kill")) {
        posix_kill((int) getmypid(), 9);   // SIGKILL → 退出码 137
    }
    exit($code);
}
```

选 SIGKILL 而不是 SIGTERM：**SIGTERM 会被框架的优雅停机逻辑接住**，  
fatal 就变成了"优雅停机"——还是没达到目的。日志不会丢，因为 `Logger`  
是即时的 `file_put_contents(FILE_APPEND)`，调用 logger 时已经落盘。

验证过：`posix_kill(getmypid(), 9)` 让进程真的以非 0 结束（bash 的 `if` 判为假）。

配套改了 `demo/duel`、`demo/doudizhu` 的退出点；`tsf migrate` 另外加了一层  
**输出兜底**（正则认"失败 N 个"），因为它可能跑在别人的项目上，  
而别人不一定知道要用 `exitWith`。

### 第三次"空检查"，这次是"SKIP 被当成 PASS"

| 次数  | 空检查              | 表现                               |
| :-- | :--------------- | :------------------------------- |
| §49 | `tsf test` 只看退出码 | 输出 87 通过 / 2 失败，框架报"通过 2 / 失败 0" |
| §53 | lint 的测试归位检查     | `glob` 扫空目录，永远通过                 |
| §54 | registry 的 SKIP  | 打了一行 SKIP，但仍判 PASS               |

三者的共性是同一个：**"我知道这里有问题"的信号没有传递到判定层。**  
打印一行提示、写一个注释，都不等于判定逻辑知道。

所以还是要回到那条规矩：**任何"应该能失败"的检查，写完先让它失败一次。**

### 复验

```

```

跳过数从 1 变成 2，说明 registry 终于诚实地报告了"我没测"。

## 五十五、领域复盘（snapshot）：三道防线都在，缺的是"整份原子"（2026-11-23）

第六个领域。snapshot 管状态版本迁移，错了会**旧代码读到新快照后静默丢字段**。

### 版本纪律：三条防线都在，而且注释写清了为什么

`Schema` 的类注释直接列出三条纪律，实现逐条兑现：

| 纪律         | 实现                        | 违背的后果（注释原话）                |
| :--------- | :------------------------ | :------------------------- |
| 只向前，不降级    | `$from > $current` → 抛异常  | "硬读会把不认识的字段丢掉后再写回去，等于静默降级" |
| 迁移链不能漏段    | 迁移后 `$v < $current` → 抛异常 | "放过去就等于把旧结构当成新结构用"         |
| 迁移函数必须是纯函数 | （约定，代码无法强制）               | "重放同一个快照两次得到不同结果，排障时无法对拍"  |

还有一条只能写进注释的：**破坏性字段变更分两步**（先双写 → 滚动重启 → 再清理），  
对应 Erlang 的两版本共存窗口。

"用阈值而不是逐版本"（`step(5, fn)` 而不是 0→1→2）的理由也站得住：  
结构改动是稀疏的，逼着写恒等函数只会让人偷懒合并成一个大函数，反而丢了可追溯性。


### 缺口：`migrateSnapshot` 不是原子的

一份快照通常有好几块（房间 / 成员 / 牌堆）。原来的写法是**逐块迁移后立刻写回**：

```php
foreach ($snap->blocks() as $name) {
    $snap->put($name, $this->migrate(...));   // 逐块提交
}
```

第二块拒绝时，第一块已经升完并写回去了 —— 快照停在**半迁移**状态：  
一部分是当前结构、一部分是旧结构。

最坏的地方是**这种快照看起来合法**：`blocks()` 正常、`get()` 正常，  
业务如果在 `catch` 里做了"尽力恢复"，或者定时保存把它写回磁盘，  
下次启动就再也分不清哪些块升级过了。

修法：先算到临时数组，全部成功才写回。

```php
$done = [];
foreach ($snap->blocks() as $name) {
    $done[$name] = $this->migrate(...);   // 抛异常时 $done 还没写回
}
foreach ($done as $blockName => $blockData) {
    $snap->put((string) $blockName, $blockData);
}
```

失败时快照一个字节都不变，调用方可以放心把整条当坏数据丢掉  
（`Restorer` 本来就是这么做的——它的 `catch` 里是"计数 + 可选删除 + continue"，  
**从不把半成品交给业务**，这个设计是对的）。

补了两条断言（`ok._v === 0`）：如果实现退回逐块提交，第一条 put 就会让 `ok._v`  
变成 7，断言必然失败。

**诚实标注**：这两条断言我没有真的反向验证过（把实现改回逐块再跑一遍）。  
理由是改动它是确定性的——不是概率性检查，`ok._v` 要么 0 要么 7，没有中间态。  
但按本轮的规矩（§54），"应该能失败的检查"最好都实际跑红一次，这条是欠着的。

### 顺带：AOT 的变量类型冲突又踩了两次

改 `migrateSnapshot` 时连续编译失败两次：

```
Cannot assign value to variable $name of type php::String with type php::Var
Cannot assign value to variable $block of type php::Array with type php::Var
```

原因都是**同一个函数里前后两个 `foreach` 复用了变量名**：第一个 `foreach ($blocks as $name)`  
把 `$name` 推成 string，第二个 `foreach ($done as $name => $x)` 的 key 是 `Var`。

这是本轮第三次踩（前两次在 aoi/frame 的测试里）。共性很清楚：  
**AOT 下变量类型是第一次赋值的类型，之后不能换**。规避方式就是不同用途用不同变量名，  
不要为了"省事"复用 `$name`/`$block`/`$k`。

### 复验

```

verify   43 套件：41 通过 / 0 失败 / 2 跳过
```

## 五十六、面向不可信输入的面：三个"不崩、不报错、只丢数据"的缺陷（2026-11-25）

前 55 节是按领域复盘。这次换一个切法：**按不可信输入能打到的面**逐个通读源码——  
Gateway、Transport、Protocol、Cluster、Rpc、Gm、HTTP、Discovery、Kernel、Timer——  
把每个"这里如果出错会怎样"的假设列出来，再逐条拿到 WSL 上实测。

这样切的理由：§44–§55 已经把"功能对不对"查得很细，但漏掉的恰好都是**错误路径**。

环境同 §2.1：WSL2 4 核，AOT v0.12.0；`/data/ts-audit` 下五个独立小工程，都链接 v0.12.0 的 `tsf/src`。

### 五个假设的实测结果

| #  | 假设                            | 实测结果                                                                                                                                                  | 结论                     |
| :- | :---------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| T1 | Gateway 的业务 handler 抛异常时影响面多大 | 进程存活，但**同一次收包里排在后面的帧全部静默丢失**；每抛一次往 stderr 刷一行 `PHP Fatal error`（不经 Logger、无 fd/uid/msgId、无计数）                                                         | 缺陷，**已修**              |
| T2 | 集群通道被坏包打穿后节点还转不转              | 节点不停摆。但坏头堵在读缓冲队首之后，对端再发 **25.6 万个合法包无一被处理**，而 `hasPeer()` 仍为 true、`send()` 仍返回 true；读缓冲无界增长（实测涨到 8.7 MB）；每来一次新数据刷一行 Fatal（2 秒 1028 行）                 | 缺陷，**已修**              |
| T3 | 服务 id 会不会用尽                   | 会。**16,777,215 次 spawn + kill（22.3 秒）**&#x4E4B;后 `本地服务 id 用尽`，此后 spawn 永久失败——id 不回收                                                                   | 缺陷，**未修**（要先定方案，见 §58） |

| T5 | SIGTERM 之后进程能不能体面退出           | 不能。**空闲进程**也要 2.53 秒才退出，日志是 `Worker_reactor_try_to_exit() ERRNO 9101 worker exit timeout, forced termination`；持久定时器阻止 worker 退出，`Service::onStop` 不执行 | 缺陷，**未修**（设计项，见 §58）   |

### 两个被实测否定的推断

读代码时我有两个推断，实测都不成立。记在这里，免得下次再凭代码想象：

1. **"集群坏包会饿死调度"**——不会。Ticker 每 200ms 的 TICK 稳定增长，TCP 入口的 echo 一直有回包。  
   异常只打断**当轮** tick，下一轮照常。
2. **"坏包之后每个 tick 都抛一次"**——只在**有新数据到达**的 tick 抛。对端沉默，链路就是个安静的黑洞。

所以 T2 的真实严重度不是"节点挂了"，而是**一条链路静默失效、内存慢慢涨、日志被刷**——三种都不触发告警。

### 修了什么

| 文件                                                    | 改动                                                                                                                                                                                                                     | 取舍                                                                                                                   |
| :---------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------- |
| `src/Gateway/Gateway.php`                             | 新增 `dispatch()`：解码 + 调 handler 包在 `try/catch (\Throwable)` 里；计数 `handler_errors`、记一行带 fd/uid/msgId 的 error、回 `Msg::ERR`、**不断开连接**                                                                                      | `Rpc\Router`、`Gm\Registry`、`Http\App` 都有这层兜底，唯独面向客户端的入口没有。不断开是因为 handler 抛异常只说明这一条没处理成，帧边界是好的；真正的状态不一致在业务对象里，断开恢复不了它 |
| `src/Cluster/Cluster.php`<br />`src/Cluster/Link.php` | `poll()` 里握手 / 取包 / 解包整体包在 `try` 里；解不开即**废弃链路**（`badLink`：计数 `bad_pkt` + error 日志 + close + 摘除）；`Link::MAX_IN`（8 MB）读缓冲上限；`MAX_OUT`（16 MB）写缓冲上限，满则丢弃并返回 false；握手 mac 改 `hash_equals`；`dropLink` 记一行 warn（之前断链是**静默**的） | 帧头非法时坏字节永远留在队首，没法在字节流里重新对齐，只能断开。与 `Transport\Server::feed()` 对客户端坏帧"关连接"一致                                           |
| `src/Transport/Server.php`                            | `feed()` 撞到 1000 帧上限后调 `resumeLater()`：1ms 定时器回调里继续 `feed()`。每轮仍限 1000 帧（积压 1 万帧 = 10 轮，轮间其它连接的事件能插进来）；连接已关则直接返回                                                                                                       | 让位是为了"给别人机会"，不是"停止服务这条连接"                                                                                            |

成本：Gateway 每帧多进一次 `try`（AOT 实测约 300 ns，按网关路径每帧约 29 µs 算约 1%）。  
续处理给单连接加了一个上限：1000 帧/ms，远高于任何真实业务。

修后复测：T1 `[throw,p2,p3]` → `400, p2, p3`；T2 Fatal 0 行、链路被丢弃并记一行 error；  
T4 3000 帧 32 ms 内全部回包，12000 帧 127 ms。

### 过程里踩到的两个 Swoole 契约

`resumeLater()` 第一版在 AOT 产物里每轮续处理都抛一次 `ArgumentCountError`，第二版定时器根本不触发：

| 写法                                               | 实际行为                                                                        |
| :----------------------------------------------- | :-------------------------------------------------------------------------- |
| `Timer::after(1, function (int $timerId) {...})` | `expects exactly 1 argument, 0 given`——**`after` 的回调不传参数**（`tick` 才传定时器 id） |
| `Timer::after(0, ...)`                           | 返回 false + `Timer must be greater than or equal to 1`，不触发                   |

框架源码里此前只出现过 `Timer::tick`，于是"定时器闭包声明 `int $timerId`"被当成了通用规则。  
两条都钉进了 `tests/swoole-contract`（6 项 → 10 项），其中"带参回调会崩"那条**本来就应该崩**。

### 先定义门槛

"1.0"不等于"没 bug"，而是：**一个没读过源码的人，照文档能在半天内把一个带登录、房间、支付回调的服务跑起来并上生产；  
出了问题能查到、能体面重启、不会静默丢消息。** 按这个定义：

- **功能集**：够了。

### P0：不做就不能叫 1.0

### P1：上线后很快会被追着要

- **内置指标**：Scheduler / Gateway / Cluster / RPC 的统计接进现有的 Prometheus 导出（约 1 天）。  
  现在有导出器，没有数据。
- **连接准入**：未登录连接没有独立握手超时（靠 120 秒空闲清扫，一个连接能占着名额 2 分钟）；  
  限流只按 fd，换连接就绕过；token 无过期 / 吊销，旧格式仍然接受。

  集群端口绝不能暴露在公网——文档里应写明。
- **Gateway 装配样板**：每个应用的 `main.php` 都要手写 `TcpServer + SessionManager + TokenAuth + RateLimiter + Gateway`，

- **零散但该修**：`WsServer` 缺 `buffer_output_size` / `enable_coroutine=false`；批量写模式下背压检测失效；

  `Gm\Task::gc` 无人调用；`Cluster::connect()` 阻塞 2 秒；nodeId 重复无检测；心跳时间戳依赖各机时钟。
- **CI**：`verify` 只能手动触发（自托管 runner），PR 上没有门禁；CI 注释里的"197 项"早已过期。

### P2：ROADMAP 上原有的

| 无持久定时器                       | 23 ms    | 是                | —               |
| 有 1ms tick，`max_wait_time=1` | ~0.9 s   | 等满后触发（带 9101 警告） | 是               |
| 有 1ms tick，`max_wait_time=0` | 23 ms    | 立即触发（带 9101 警告）  | 是（30 ms 清理完整执行） |
| 同上，挂着一条连接                    | 29–44 ms | 是                | 是，不被连接拖住        |

另外两条：worker 里**接管不了 SIGTERM**（`signal [15] processor has been registered by the system`）；  
只要有持久定时器在，窗口**一定等满**，和忙不忙无关。所以 `WorkerStop` 是唯一可靠的落点——  
两条退出路径下它都会触发，且回调里的清理一定跑完进程才退出。

```
SIGTERM
  └─ WorkerStop
       1. Server::onShutdown() 钩子          服务还活着：广播"即将重启"
       2. 停定时器，排空就绪队列（有预算）    已收到的请求尽量处理完
       3. 逆创建顺序逐个 Service::onStop()    房间依赖世界，所以先停房间
       4. Scheduler::onShutdown() 钩子       所有服务都停了：进程级落盘
       5. 冲掉没写出的回包和跨节点消息
```

| 项    | 数据                                                       |
| :--- | :------------------------------------------------------- |
| 回归   | `tests/shutdown-guard`，3 个场景 16 项：排空 / 不排空（丢弃计数可见）/ 窗口路径 |
| 修之前  | 一个 `onStop` 都不执行；`max_wait_time=0` 现在空闲进程 22 ms 退出       |
| 变异检查 | 摘掉停机钩子 → **红 8 条**；恢复后 16 项全绿                            |
| 额外保证 | `onStop` 抛异常不影响别的服务；停机后投递被拒、不能再建服务、定时器注册返回 0             |

`max_wait_time` 默认保持 Swoole 的 3 秒（滚动重启时让在途请求跑完），可配。  
那一行 `ERRNO 9101` 仍会出现：它只说明"窗口到期时定时器还在"，不代表有东西没处理完。

### 59.3 服务 id 回收（T3）

**选了"回绕"，没选"空闲表"。** 直觉的做法是把杀掉的 id 放进空闲表、下次优先取——那是最糟的：  
低号 id 被反复复用，一个服务死后几毫秒 id 就给了别人，别处存的旧地址会指向新服务（ABA），  
而且没有任何报错。回绕没有这个问题：id 仍然只增，到顶才绕回 1。一个 id 从"死"到"被复用"隔着  
一整轮地址空间——每秒 1000 次 spawn 约 4.6 小时，每秒 100 次约 46 小时。

外加一道最小宽限期（默认 5 秒，4096 项的小环）兜住极端高频。

| 项     | 数据                                                                             |
| :---- | :----------------------------------------------------------------------------- |
| 回归    | `tests/id-recycle`：`IdAllocator` 单元 44 项（12 个 id 的小空间）+ **真的绕一轮 24 位地址空间** 9 项 |
| 修之前   | 第 16,777,215 次 spawn 抛 `本地服务 id 用尽`（变异检查里复现）                                   |
| 变异检查  | 退回旧 `Scheduler` → full 段红 3 条；恢复后 53 项全绿                                       |
| 验证的性质 | 绕一圈之后，从头活到尾的那个服务**还在原地址上、还是同一个实例**、照常收消息                                       |
| 可观测   | `stats()["ids_left"]` / `["id_wraps"]`；首次回绕记一行 warn                            |

**代价要说清楚**：绕回之后同一个 id 会是另一个服务。需要长期持有对方地址的地方应该按名字重新解析，  
而不是把地址存起来——这条以前不成立（id 永不复用），现在成立了，写进了教程。

### 59.4 集群断线重连

`Cluster::watchPeer()` 登记、指数退避（0.5 s 起翻倍封顶 15 s，带抖动）、TCP 拨号改非阻塞。

| 场景                | 修之前                        | 实测（修之后）                             |
| :---------------- | :------------------------- | :---------------------------------- |
| 对端重启（短暂不可用）       | 永久失联                       | 6 ms 重连成功，又能传包                      |
| 对端不可达时单次 `poll()` | 同步 connect 最长挡住 worker 2 秒 | **775 µs**（变异检查里同步版实测 2,001,891 µs） |
| 对端一直起不来（3 秒内）     | —                          | 拨号 7 次，退避在涨、有封顶，不空转                 |
| 稳定过的链路再断          | —                          | 62 ms 回来（退避从头算）；没稳定过就断的继续翻倍         |
| 两端同时互拨            | 两条出站互相被对端关掉，谁也不剩           | 按节点号裁决只留一条，2 秒内零抖动                  |

| 项    | 数据                                         |
| :--- | :----------------------------------------- |
| 回归   | `tests/cluster-reconnect`，30 项             |
| 变异 A | 关掉 `reconcile()` → **红 7 条**               |
| 变异 B | 拨号改回同步 → **红 2 条**，其中一条正是"对不可达地址 poll 不阻塞" |

**双向互拨的裁决是这一节新加的。** 以前双方都关掉"收到的"、保留"发起的"，结果是两条出站都被对端关掉。  
没有重连时这只是"同时拨号就连不上"；有了重连，两边按同一套退避节奏会反复撞在一起。  
现在两条都还没握手时，保留**节点号小的一方**发起的那条，两端判断必然一致。

**"对不可达地址不阻塞"这条断言是补出来的。** 第一版变异 B 只红 1 条，而且不是被它抓到的：  
本机回环上对没人监听的端口同步 connect 其实返回得很快，第一版断言等于没测到东西。  
真正会卡住的是**不可达地址**——对端机器关机、网络分区。加上它之后，同步版才现形。

**没做的**：注册表成员变更 → `watchPeer()` 的联动。谁该被 watch 仍由业务决定，核心不依赖可选包。

### 59.5 日志轮转与通道

单文件 64 MB × 5 份，多进程安全（`rename` + 锁文件，追加写靠 `O_APPEND` 不加锁）；  
大小检查按"已经写了多少字节"计数，攒够 `max_bytes / 16` 才查真实大小（每行 `filesize()` 比写日志本身还贵）。  
`Logger::to("gm", ...)` 具名通道；GM 审计默认落到独立的 `gm.log`，带操作人字段。

| 项    | 数据                                                 |
| :--- | :------------------------------------------------- |
| 回归   | `tests/log-rotate`：单元 24 + 经配置 14 + 两进程并发 4 = 42 项 |
| 变异检查 | 把上限强制成 0 → boot 段红 3 条；恢复后 42 项全绿                  |
| 并发验证 | 两个进程同时写一个文件，每一层都是满的（没有转出小文件），没有坏行                  |

### 60.1 三个套件在每一次"全量通过"里验证的都是十天前的代码

给 GM 加一人一个 token 的时候，新写的断言在输出里根本不出现。查下去：

- `tests/gm-test/run.sh` **没有编译步骤**，直接跑目录里的 `gm_test`；
- 那个产物的日期是 **11 月 16 日**；
- `fd-test`、`settle-crash` 同样。

也就是说从 11 月 16 日到 26 日，每一次"55 个套件全过"里，这三个套件跑的都是旧二进制。
期间框架改了调度器的停机、服务的 id 分配、集群的连接、网关的准入——它们一个字节都没验证到，
而输出里它们是绿的。`run.sh 自己负责 build` 是 README 里的约定，但**没有任何东西检查这一条**。

顺带查出来的还有：21 个套件的 `project.yml` 里源文件路径指向早已不存在的 `bench/<x>/main.php`
（WSL 那份已经是对的，本地副本是旧的）。

**修法**：三个 `run.sh` 补上编译；`tsf lint` 加一条规则——注册表里的 `run.sh` 不编译就判红
（认三种写法：显式 `build`、共用入口 `run-svc-test.sh`、`tsf run` / `tsf watch`；解释执行的套件豁免）。
重编之后三个套件对着当前代码都过：`fd-test` 10 项、`settle-crash` 14 项、`gm-test` 55 项。

这一条值得多写两句：它是 §53 讲的"空检查"的又一个变种，而且更隐蔽——
§53 是"断言恒真"，这里是"断言是真的，但被测的不是你以为的东西"。
前两轮我给全量回归的结论（"55 套件全过"）在表述上没错，但**对这三个套件来说它是空的**。
以后看"全绿"之前，先确认每个套件真的编译了。

### 60.3 内置指标

导出器此前只翻业务埋点，框架自己的统计全都看不到。

- **拉**：`Metrics::provide(前缀, fn, 计数器列表)`。调度器 / 网关 / 集群登记一个"导出时现取 `stats()`"的提供者，
  同前缀多个实例自动相加。不去事件点补 `inc`——那等于同一件事记两遍，还要动热路径。
- **推**：RPC 的 `Router` / `Client` 一个进程里可能有很多实例，所以在事件点上 `Metrics::inc`。
  此前 16 个计数点里只有 1 个进了导出。

`prom` 套件 34 → 51 项。变异检查：把 `provide()` 改成空操作 → 红 14 条。

### 60.4 连接准入与装配入口

| 策略 | 实测 |
|:--|:--|
| 登录时限 | 一直发心跳不登录的连接，在 2.6 秒（配置 2 秒）被断开；登录之后过了时限仍然连着 |
| 单连接失败上限 | 第 3 次失败（上限 3）之后连接被断开 |
| 来源封禁 | 同一来源多条连接累计失败到上限后，**正确的** token 也登录不了；3 秒（配置）之后恢复 |
| 未登录流量按来源限流 | 同一来源 6 条连接发 60 帧，0.4 秒内只回了 20 帧（桶容量） |

`Gateway::assemble()` 把会话 / 鉴权 / 限流 / 准入按 `server.*` 一次装好——此前每个 `main.php` 手写五件套，
后来加的准入策略在那些 `main.php` 里全部缺席，因为没有地方可配。

**一个只靠实测才发现的 bug**：来源限流桶建好之后**没人给它补令牌**——补充只在每连接限流器上调。
症状是"连上了但没有任何响应"：第一个 20 帧之后这个 IP 的未登录流量全被丢。
是登录超时场景里"收到 0 个心跳回复"这条旁证把它暴露出来的。

`admission` 套件 38 项。变异检查：关掉登录时限 / 关掉来源限流 / 去掉作废判定 → 各红 1 条（对准问题的那条）。

### 60.5 Token 作废

签发格式从 `uid.exp.sig` 改为 `uid.iat.exp.sig`。有了签发时刻才能说"这个玩家在某时刻之前签的 token 全部作废"。

| 能力 | 保证 | 边界 |
|:--|:--|:--|
| `revokeUid($uid)` | 该玩家当前所有 token 失效，重新登录拿到的不受影响 | 作废记录在**进程内**；多 worker / 多节点要全服生效，得每个进程都执行一次 |
| `revokeAll()` | 全部失效 | 不换 secret；攻击者拿着泄露的 secret 仍能签新 token |
| `addPreviousSecret()` | 轮换密钥时旧 token 在过期前继续有效 | — |
| `allowLegacy(false)` | 不再接受永不过期的 2 段 token | 生产应当关；默认仍开，不打断已有部署 |

签发时刻在未来的 token 一律拒——否则可以签一个"很久以后才生效"的，绕过之后所有的作废。

### 60.6 成员联动

`Discovery\Membership`（在核心里，只认核心的 `Registry` 接口）+ `LocalNode::afterBeat()`。
对账规则：注册表里活着、我没 watch 的 → `watchPeer`；watch 过、注册表里没了的 → `forgetPeer`（链路不主动断）。

实测 5 个场景：首次登记 6 ms 连上；幂等（反复对账不重复拨号）；节点过期后不再重连但链路保留；
换地址重启后旧链路断开、61 ms 连上新地址；同一节点号换地址。

`membership` 套件 38 项。变异检查：`sync()` 改空 → 红 19 条。

### 60.7 GM 一人一个 token

`setOperators()`。用操作人 token 发的指令，审计里的 `op` 来自 token，请求头自报的不起作用；
`removeOperator()` 立刻失效；共享 token 可以并存，也可以传空串彻底停用（只要至少有一个操作人 token 就允许启动）。

比对是定长的，而且**所有 token 都比完才返回**——命中了也不提前退出，否则"猜对了"比"猜错了"少花的时间就是提示。

`gm` 套件 39 → 55 项。
