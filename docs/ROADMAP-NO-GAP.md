> 更新：2026-11-26

> 与 `ROADMAP.md` 的关系：那份管"能不能叫 1.0"，这份管"能力面瘸不瘸腿"。两份有交叉，但不互相替代。

## 零、先记两条被推翻的结论

这两条曾经被当成"不要用 TSF"的理由，复核后都不成立。**记下来，因为错误的方法比错误的结论更容易再犯。**

### 0.1 "30 Hz 百人同屏撑不住" —— 口径错误

当时的算法：

```
348,000 msg/s ÷ (100 人 × 30 Hz) ≈ 116 人     ← 错
```

错在把 **入站 pipeline echo 吞吐** 当成了 **帧预算**。这两个量之间隔着"每帧处理多少条消息"，不能相除。

正确的口径是帧预算：

| 场景 | 单帧耗时 | 预算（30 Hz = 33 ms） | 占用 |
|:--|--:|--:|--:|
| 百人同屏：逻辑 | 0.10 ms | | |
| 百人同屏：广播（100 次 encode + send） | 0.26 ms | | |
| **合计** | **0.36 ms** | 33 ms | **1.1%** |
| 对照：万人世界 20 Hz | 21 ms | 50 ms | 42% |

**真天花板是带宽，不是框架**：100 人 × 2 KB × 30 Hz ≈ 6 MB/s ≈ 48 Mbps。8 个这样的人群吃满千兆，此时 CPU 仍只用个位数百分比。这个限制和用 PHP 还是 C++ 无关。

> 判据：**吞吐（msg/s）与帧预算（ms/frame）永远不要互相换算。** 要比较，先统一到"每帧要做多少事"。

### 0.2 "不停服改玩法是结构性缺失" —— 能力早在，缺的是分层

`pkg/script` + `ext/interp` 已经做到的四件事，与 Lua 完全对齐（`docs/guide/12-hot-reload.md` 有原始输出）：

| Lua 热更需要 | TSF | 证据 |
|:--|:--|:--|
| 同地址空间 | ✅ | AOT 产物动态链接 `libphp.so` |
| 脚本能改宿主对象 | ✅ | `before gold=500 → after gold=600`，改的是宿主那个对象 |
| 运行时换代码 | ✅ | 改文件 + `script.reload` |
| 状态跨重载保留 | ✅ | `Script\State` 与 `exports` 分离 |
| 双向调用 | ✅ | `interp_invoke` / `$ctx->bind()` |

真正差的只有**表达力**（白名单字段 vs 任意表），其余是工程编排。所以这项不是"补不了"，是"没设计完"。

## 二、P0：一周内消掉（3 项）

### P0-1 调度加时间预算 ✅ 已完成（2026-11-26）

**问题**：`Scheduler::setBudget(int $n)` 限的是**消息条数**，不是时间。一个服务处理一条消息花 200 ms，照样跑完，同一 tick 里其他几千个服务全部等它。这不是"慢"，是"全体停顿"。

**证据**：`src/Service/Scheduler.php` 的 `tick()` 用 `$handled < $limit` 控制条数；`setWatchdog()` 是**单条消息事后**检测，超时了才 `log`/`kill`，救不了当前这一帧。

**做法**（两层，缺一不可）：

1. **tick 总预算**。`setTickBudget(int $ms)`：循环内每 64 条消息检查一次 `hrtime` 累计，超了就置 `$stop` 连外层一起退出，剩下的下一个 tick 继续。
   - 每 64 条一次而不是每一条：单次 `hrtime` 约 236 ns，逐条测会吃掉 870 ns 单消息预算的 27%。
   - **检查点放在 `pop()` 之前**：取出消息再放弃就是丢消息。这个位置是第一次实现时搞错的地方（只在外层循环检查，一个服务把整批跑完，预算根本没机会生效），`slice` 套件的"一次没有处理完"就是钉这一条的。
2. **服务级时间片**。`setSlice(int $ms)`：单个服务在一次调度里累计 CPU 超过预算，就把它剩余的消息排到 ready 队尾，让别人先跑。
   - 与 watchdog 共用同一对 `hrtime`，两个都关时只多一次布尔比较。
   - `slice_hit` / `tick_over` 进 `stats()` 并随 `tsf_scheduler_*` 导出。

**实测**（`tests/slice-test`，17 项全过）：

| 断言 | 结果 |
|:--|:--|
| 关闭 slice：快服务排在 10 条慢消息之后 | `fast.first=10` |
| 开启 slice(1ms)：快服务插进慢服务中间 | `fast.first=1` |
| 打断后消息不丢 | `slow=10 fast=10` |
| 单条 5 ms 的消息不被 slice 打断 | `elapsed=5ms`，这条仍完整跑完 |
| tick 预算 2 ms 下 500 条消息 | 首轮 `handled=64`，多轮后 `count=500` |
| 关掉两个开关后行为回到原状 | `fast.first=10` |

**边界（必须知道）**：slice 只在**消息边界**生效，一条消息自己跑 100 ms 拦不住——PHP 无法中断正在执行的代码。它防的是"一个服务长期霸占"，不是"一件事做太久"。协程模式下不生效（墙钟含 I/O 等待，会误判），那里该用 `setBudget` 限条数。

### P0-2 脚本视图层 + 灰度 + 重载广播（进行中）

**问题**：脚本现在只能按白名单读写标量字段。

```php
$ctx = new Context($player, ["uid", "level", "gold"], ["gold"]);
```

写不了"三段式副本状态机""连击判定""条件组合"。于是这类逻辑被迫回 AOT，热更覆盖面缩到开关级。**这是与 Lua 系唯一实质差距。**

**已完成（2026-11-26）：灰度 + 广播 + 视图示例**

| 能力 | 实现 | 回归 |
|:--|:--|:--|
| 灰度 | `Manager::registerAlt()` / `setGray()` / `pick()` / `callGray()`，按 uid 乘法散列分流 | 9 项 |
| 集群广播 | `Script\Broadcast`：接 `\Closure(int $node, int $msgId, string $payload)`，**不依赖 Cluster** | 14 项 |
| 类型化视图 | `tests/script-test` 的 `PlayerView` + `view.php`，可跑的例子 | 4 项 |

`script-test` 60 → **90 项**。两次变异检查都做了：
把散列常数改成 `1000000` → 命中率与"不按段划分"两条变红；
把 `report()` 的 `settled` 改成只数 acked → "失败也计入 settled"与"done=true"变红。

**实测挖出的坑**：`PlayerView` 没有 `__set` 时，脚本写 `$v->level = 99` 只是 Deprecated，
**静默创建动态属性**——脚本返回 `wrote`，宿主状态没变。这比报错难查得多，已加 `__set` 拦截并钉成断言。

**剩余**：

1. **`callWithContext` 的 timeout 优化**。实测 `zend_set_timeout` 占 527 ns（白名单用例的 20%）。
   只有传了非零 timeout 时才需要设；需要一个"信任源码"的快速路径。
   **注意**：这要改 `ext/interp` 的 C 代码，比前两项重，优先级低于 lint 规则。

2. **lint 规则 6/7/8**（见第四节）。规则 7（`scripts/` 只能 `use TSF\Script\*`）
   是唯一能把"脚本不许直接抓 Service"从约定变成门禁的手段。

3. **`Broadcast` 接 `Cluster` 的装配示例**。协议层已实现并测试，但"收到的包怎么从
   `Cluster::poll()` 喂给 `Broadcast::onMessage()`、ack 怎么发回去"只有文档描述，
   没有可跑的 demo。这条要在 `demo/duel` 或新 demo 里落一次，否则接线方式仍靠读源码。

**验收标准**：

| 断言 | 期望 |
|:--|:--|
| 脚本对 View 的写操作 | 编译/运行期报错，不静默 |
| 同一 `Context` 下 View 读到的值与 AOT 读到的值 | 逐字段相等（含 float 精度） |
| `gray=10` 时 uid 取模 10% 走 v2，其余走 v1 | 分流精确 ✅ 已完成 |
| v2 抛异常，v1 不受影响 | 各自隔离 |
| 3 节点集群 `reloadAllNodes()` | 3/3 ack；1 个节点掉线时返回 2/3 且列出缺失节点 |

**回归**：`script-test` 69 项（已含灰度）；集群广播加 4 项到 `cluster-guard`。

### P0-3 脚本性能标定 ✅ 已完成（2026-11-26）

**问题**：文档写"慢 10–50 倍"，是估算，没有实测。没有这个数字，就无法判断"这条规则能不能放脚本"。

**产出**：`bench/script-cost`（不进 verify，基准不是回归），结果写进 `12-hot-reload.md` §5.1/§5.2。

| 用例 | 脚本 | AOT | 倍数 |
|:--|--:|--:|--:|
| 空调用 | 565 ns | 105 ns | 5.4× |
| 空调用 + Context 包装 | 1092 ns | — | 包装多 527 ns（`zend_set_timeout`） |
| 3 读 1 写（白名单） | 2733 ns | 216 ns | 12.7× |
| 10×4 次方法调用 | 1808 ns | 3134 ns | **0.58×** |
| 100 次 `addStateInt` | 29758 ns | 4875 ns | 6.1× |

**三个非直觉结论**：

1. "慢 10–50 倍"是错的，真实 5–12 倍，绝对值 0.5–3 µs。
2. **脚本调 AOT 方法比 AOT 自己调还快**（解释器走 zend 调用缓存，AOT 每次走完整调用协议）。
   所以 AOT 的优势在计算，不在调用——这修正了"编译后一切都快"的直觉。
3. **白名单字段访问 410 ns/次，比方法调用（45 ns）贵 9 倍**——
   这是 P0-2 用类型化视图替换白名单的**性能依据**，不只是表达力理由。

**判定线**（写进 `12-hot-reload.md` §5.2）：脚本按"次"收费。每人每分钟 1 次的活动判定
可以放；每人每秒 10 次的玩家操作路径放不下（1.7 万在线 ≈ 0.5 s/s）。

**顺带发现的优化点**：`callWithContext` 每次设 `zend_set_timeout` 占 527 ns（白名单用例的 20%）。
只有传了非零 timeout 时才需要设，改掉能省这部分——留给 P0-2 一起做。

## 三、P1：上线后会被要（2 项）

### P1-1 单服务内存归因 ✅ 已完成（2026-11-26）

**问题**：所有 Service 共享 PHP 堆。一个服务持有 500 MB，整个 node 陪葬。Erlang 的 per-process heap 补不了，但可以做到"抓出是谁"。

**做法**：`Scheduler::setMemGuard(int $perMsgMb, int $perServiceMb, string $action = "log")`。

- 在 tick 边界取 `memory_get_usage()` 差值，归到刚处理完的那个服务上（同一 tick 内服务是串行的，差值不会混进别的服务）
- 单批净增长超 `$perMsgMb` → `mem_spike++` 并记 error（通常是"一次查询捞了整张表"）
- 累计超 `$perServiceMb` → **每个服务只告警一次**（逐批报会把磁盘写满，还把"第一次"埋在重复里）
- `action=kill` 时走 `onCrashed()`，受监督树约束（不是绕过去直接 kill）
- `memByService()` 返回地址可读形式到累计净增长的映射
- `kill()` 里同步清归因表：id 会回绕，留着会让新服务一出生就顶前一个的内存债

**实测**（`tests/mem-attr-test`，18 项全过）：

| 断言 | 结果 |
|:--|:--|
| 关闭时不记录任何归因 | `memByService() === []` |
| 8 MB 单批触发尖峰 | `spike=1`，只有它进表（不分配的不进） |
| 6 次 × 1 MB、配额 3 MB，告警只 1 次 | `warn=1`、`mem_kill=0`、服务还活着 |
| `action=kill` 超配额 | 服务被销毁、`mem_kill=1`、归因表清空 |
| 不分配内存的服务 | 不触发尖峰、不被杀 |

**变异检查**：把"只报一次"的判断改成恒真，`warn` 从 1 变 4，"配额告警只报一次"变红。

**明确做不到的**：每次 1 KB 的缓慢增长。那需要逐分配追踪，PHP 做不到。`memByService()` 是**累计净增长**，不是当前占用——PHP 释放内存时不会回退这个数。

**回归**：`tests/mem-attr-test`（18 项，无端口——纯进程内调度）。

### P1-2 分区后的边界带同步（只在做大世界时才需要）

**问题**：`SCENE-CAPACITY.md` §四 已证明"按位置分区"能线性扩展（4 块：10.2 → 2.6 ms），但**分界线两侧互相看不见**。不做这层，玩家走到线上会看到人凭空消失/出现。这是唯一"框架已给方案但缺最后一块"的地方。

**做法**：分界线两侧各留 2 格宽的**边界带**，带内实体的位置每帧以增量方式同步给邻区（只同步位置和必要属性，不同步完整实体）。带内实体数 ≈ 边界长度 × 2 格 × 密度，远小于全量。

**验收**：两个 zone 各 5000 人，玩家沿分界线往返 1000 次，视野内实体集合与单区基准的差异为 0（允许 1 帧延迟）。

**回归**：`tests/zone-edge-test`，端口 **9430**。

**前置依赖**：跨区迁移已在 `pkg/handoff`，但"双写窗口"是已知代价（review §50）。边界带同步不能复用迁移路径，要单独做。

## 四、三层固化规范（这是防腐化的部分，比补功能更关键）

现在的问题不是能力缺失，是**没有强制分层**：该热更的写进了 AOT，该 AOT 的图省事塞进脚本。三层一旦互相污染，热更能力会逐月退化。

| 层 | 放什么 | 改一次要多久 | 性能量级 |
|:--|:--|:--|:--|
| **L0 内核** | 传输、网关、调度、集群、存储 | 重启（不可热更） | 870 ns/msg（进程内） |
| **L1 玩法** | AOI、帧循环、房间、战斗、状态机 | 快照 + 滚动重启 | 原生 |
| **L2 规则** | 活动、掉落、任务、数值、条件 | 改文件 + GM 重载，秒级 | 解释执行（见 P0-3） |

**靠 lint 强制，不靠自觉**。`lintTree()` 现在有 5 条（1 `mixed`、2 命名空间、3 `ext/` 无 `TSF\`、4 核心不引用 pkg、5 属性喂内置函数的提示）。

**已加规则 6/7（2026-11-26）**，`tsf lint <工程目录>` 生效；不带参数时行为完全不变（只查框架）：

6. **`scripts/` 下不能有 `class` / `function` 定义**。理由是硬的：PHP 不允许重复定义，
   `reload()` 第二次必然 `Cannot redeclare`。而且这个错误**开发期不暴露**（首次加载是好的），
   要等运营点第一次重载才炸。
7. **`scripts/` 下只能 `use TSF\Script\*`**，能力一律从 `Context` 取。这是 §6.5 那条安全边界
   唯一能落成门禁的形式，否则第一个图省事的人 `use TSF\Room\Room` 就破了。

**规则 8（`onMessage` 的类必须在 `Service/` 目录）没有做**，两个理由：
误报率高（`tests/*/main.php` 全都定义 Service 子类但没有 `Service/` 目录）；
收益低——`Scheduler::register` 找不到工厂时会立刻报错，不像规则 6/7 那样静默到上线才炸。
不做比做一个经常要人跳过的规则好。

**判定口径**（写进 CONTRIBUTING）：一段逻辑该放哪一层，问三个问题——
- 它会在线上被改吗？→ 会，进 L2
- 它每帧都跑吗？→ 跑，进 L1（脚本慢 10–50×）
- 它要改玩家状态吗？→ 要改，状态留在 L1，L2 只调能力方法

## 六、运行时评估：功能面补完之后看什么（2026-11-26）

P0/P1 补完，能力面齐了。但那是"能不能做"，还有一个维度没看过：**能不能长期跑**。

三项，都直接决定能不能上生产：

| 测什么 | 为什么 | 结果 |
|:--|:--|:--|
| spawn / kill 内存收敛 | "一房一 Service"就是频繁建销毁，每轮漏一点就是 OOM | ✅ 平坦（第 2 轮起增量 0） |
| 带定时器的 spawn / kill | 同一场景 + 每房一个倒计时 | ❌ **发现内存泄漏**，已修（v0.14.1） |
| 循环引用 GC 停顿 | 业务对象互指（玩家↔公会）时，一次停顿落在触发 GC 的那条消息上 | 2 万对象约 2.5–7.5 ms |
| **协程规模** | 一局之内每个房间都可能挂着一个等 redis 的协程 | ⚠️ 并发成立，但**创建协程 11 µs/个**是新的容量上限 |
| 冷启动 | 决定滚动重启能多激进 | ✅ 36 ms（中位），不构成约束 |
| 长跑延迟漂移 | 内存碎片、哈希表历史峰值只在长时间运行后显形 | ✅ 30 秒内 p99 持平（10.4–10.8 ms） |

### 冷启动与延迟漂移（2026-11-26 实测）

**冷启动 36 ms**（`bench/cold-start`，空 main 跑 20 次取中位，区间 34.5–39 ms）。
里面是动态链接 libphp.so、模块初始化、opcache 载入、运行时建立、退出清理。
不含业务初始化（配置、连库、注册集群、预热）。

结论：滚动重启不是问题。1 万个进程顺序重启也在 6 分钟量级，
可以做"连批重启"而不用精细错峰。

**30 秒长跑无漂移**（`bench/latency-drift`，每 10 ms 一条自投消息、1 ms tick 一次）：

| 窗口 | p50 | p99 | 最大 |
|:--|--:|--:|--:|
| #1 | 10.15 ms | 10.69 ms | 11.0 ms |
| #3 | 10.16 ms | 10.67 ms | 15.3 ms |
| #6 | 10.09 ms | 10.38 ms | 15.3 ms |

p50/p99 六个窗口完全持平，没有上升趋势。

**但这个时长不够**：30 秒排不掉"跑一天才卡"那类问题。真要排除，
得上小时级运行或者人为制造内存压力（比如持续建销毁服务后再测）。
现在只能说"没有快速退化"，不能说"长跑稳定"。

### 协程的容量上限（2026-11-26 实测）

`bench/coroutine-scale`，每次等待 50 ms（模拟一次 redis/pdo 往返）：

| 并发数 | 总耗时 | tick 分发 | RSS 增量 | 每协程 |
|--:|--:|--:|--:|--:|
| 100 | 54 ms | 1.2 ms | 1.8 MB | 18 KB |
| 500 | 59 ms | 6.1 ms | 6.7 MB | 14 KB |
| 1000 | 65 ms | 9.7 ms | 8.8 MB | 9 KB |
| 2000 | 76 ms | 19.5 ms | 17.4 MB | 9 KB |
| 5000 | 110 ms | **56.5 ms** | 59.7 MB | 12 KB |

对照：同步模式 50 个串行 2509 ms（正好 50×50）。协程模式 5000 个并发 110 ms——**并发是成立的**。

但有两件事必须记住：

1. **每协程约 10 KB RSS**。协程栈是 C 层 mmap，**不在 PHP 堆里**——
   `memory_get_usage` 看不到它，只看堆会得出"协程不要钱"的错误结论。
   1 万个并发协程 ≈ 100 MB。
2. **创建协程要约 11 µs/个**（`tick()` 分发 5000 个要 56 ms，线性）。
   这是新出现的容量上限，之前没人算过：

   | 帧率 | 帧预算 | 单帧最多分发 |
   |:--|--:|--:|
   | 30 Hz | 33 ms | ~3000 个服务 |
   | 60 Hz | 16 ms | ~1500 个服务 |

   换算成速率：**约 9 万个协程/秒**封顶。1 万个房间 × 20 Hz = 20 万/秒 → 超一倍。

   **所以协程模式适合"低频 + 大 I/O"，不适合"高频 + 小消息"**。
   房间帧循环这类高频路径，要么用同步模式配定时器，要么让一个协程处理一批消息
   （`setBudget` 调大，减少每批的协程数）。

这个 11 µs 比 Swoole 原生协程创建（1–2 µs）高一个量级，值得后续单独查：
每批一个闭包（捕获 5 个变量）+ AOT 下的调用开销，可能都有份。

### 发现的 bug

`Scheduler::tick()` 用 `if ($this->timers->size() > 0)` 决定要不要调 `due()`。
`size()` 只数**有效**定时器；服务批量销毁后 live 归零、对象被标记 cancelled 留在时间轮槽里
等翻到——于是 `due()` 再也不被调用，游标不前进，死对象永远留着。

现象：**不报错、不崩溃、`stats()["timers"]` 一直显示 0，只有内存在涨。**
每 2000 个定时器约 47 万 B/轮，十轮 6 MB 不收敛。压测看不出来，跑几小时才显形。

修法：`hasPending()`（live / wheel / immediate / far 任一非空就调 `due()`）。
回归 `tests/lifecycle-test` 8 项，变异检查三条断言同时变红。

### 排查方法（比结论更值得记）

这个 bug 我从"猜测"到"定位"走了四次弯路，方法比结果有用：

1. **先二分**：加一个 `TickerNoTimer` 对照组（同样有 `onStart` 但不建定时器）。
   对照组完全平坦、实验组每轮涨 47 万 → 确定问题在定时器路径，不在 Service 生命周期。
2. **分段归因**：在 spawn 后 / kill 后 / tick 后各测一次内存。
   tick 阶段**恰好是 0** 是决定性线索——如果死对象真在轮里，到期清理该掉下来。
3. **加自省而不是继续猜**：给 `Timers` 加 `debugSizes()`，一眼看到
   `wheelItems 每轮 +2000`。在此之前我改过 `TimerHeap` 的 key 重排（那个也确实是问题，
   但不是主因），白改一轮。
4. **区分垃圾与保留**：中途用 `gc_collect_cycles()` 排除"成环垃圾"（回收 0 个 → 不是）。

教训：**"看起来该释放却没释放"的时候，不要靠读代码推断，先让程序自己把内部计数说出来。**

## 七、这份路线图不承诺什么
- **不承诺抢占**。PHP 单线程无法中断执行中的代码，`slice` 只能在 tick 边界让出。写死循环的服务仍然会卡住整个 node，直到 watchdog 或 slice 生效。要真抢占，得换运行时。
- **不承诺堆隔离**。内存归因是"事后定位 + 杀"，不是"防止传染"。
- **不承诺跨 key 一致性**。一个玩家的房间和背包分属不同 key 时，迁移会出现双写窗口（review §50）。解决方式在业务侧：按 uid 把同一玩家的所有状态聚到一个 key。
- **不承诺 30 Hz 以上全量广播**。百人同屏 1.1% 占用是"每人只收视野内增量"；全量广播（每帧给所有人发所有人）不在这个数字里。
