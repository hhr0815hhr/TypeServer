# 09 · 编译成 native 还是 wasm

> 这一篇讲判断：**同一份 PHP 代码，该编译成原生可执行文件，还是 wasm 组件。**
>
> 先纠正一个常见误解（也是本文初稿的错误）：**wasm 模块也是 PHP 写的**，
> 用同一个 `tpc` 编译。区别只在**输出目标**——一个是直接跑的原生程序，
> 一个是宿主内加载的 WASI 组件。
>
> 不是"PHP vs Rust"，是"同一个编译器，两种产物"。

## 两种编译目标

| | **native** | **wasm** |
|:--|:--|:--|
| 命令 | `tsf build` | `tsf module build` |
| 产物 | 单个可执行文件 | `.wasm` → 预编译成 `.cwasm` |
| 启动 | 独立进程 | 宿主进程内加载 |
| 更新 | **重启进程** | **`canary` / `swap` 热更**（实测 5ms） |
| 性能 | 直接机器码 | 有沙箱和跨边界开销 |
| 接口 | 自由改 | **导出签名不能变** |
| 状态 | 进程内随便存 | 换实现不迁移内存 |

代码几乎一样，差别只在 `project.yml`：

```yaml
# native
name: myworld

# wasm 组件
name: activity
wasm: component
```

## 判断只有一条

```
这段逻辑需要不停服更新吗？
├─ 是 → wasm
└─ 否 → native
```

**性能不是首要判据**——因为代码同源，写法优化（避免动态调用、减少数组拷贝）两边通用。

## wasm 的完整流水线

`tsf module build` 一条命令做三件事（实现在 `tsf/bin/tsf` 的 `moduleBuild()`）：

```
1/3  tpc project.yml            → name.wasm（WASI 组件）
2/3  tp-precompile in out        → dist/name.cwasm（预编译 + fuel/epoch 插桩）
3/3  写 manifest                 → 宿主按 manifest 加载
```

**三个必须满足的前置**：

| 依赖 | 说明 |
|:--|:--|
| `wasm32-wasip2-clang` | wasi-sdk，**clang 必须 >= 22**（SDK 太旧 tpc 直接拒绝） |
| `wasmtime` CLI | 运行 / 验证 |
| `wit-bindgen` | 0.60，生成接口绑定 |

**一个隐蔽的坑**：

> **必须用 `tp-precompile`，不能用 `wasmtime compile`。**
>
> fuel/epoch 是**编译期插桩**，产物带 fingerprint。用 wasmtime CLI 编出来的配置不一致，
> 宿主会拒绝启动——现象是**所有模块句柄变成 `-1000`**，很难联想到是预编译参数的问题。

## 热更的约束（做不到就别用 wasm）

```php
$m = Module::load("activity", ".../v1/dist/activity.cwasm");
$m->canary(".../v2/dist/activity.cwasm", 100);   // 千分比，100 = 10%
$m->swap(".../v2/dist/activity.cwasm");          // 全量
$m->rollback();                                   // 回滚
```

| 能改 | 不能改 |
|:--|:--|
| 导出函数的实现 | 导出函数的**签名** |
| 内部逻辑、数值、算法 | `package` / `world` 名（宿主按名匹配） |
| — | 宿主里的**状态结构**（换实现不迁移内存） |

**灰度用千分比**（`permille`，100 = 10%），不是百分比——这样 0.1% 这种细粒度也能表达。

**分流是确定性的**：同一个 `$key`（通常玩家 id）永远落同一侧。用随机数分流会让同一局的一半请求走旧逻辑、一半走新逻辑，**状态会分裂**。

## 什么时候 native 一定更好

| 场景 | 为什么 |
|:--|:--|
| 战斗帧同步、物理、寻路 | 每次调用都要跨 wasm 边界，累积开销大 |
| 调用频率极高的小函数 | 跨边界成本可能超过计算本身 |
| 需要读宿主内存结构 | wasm 只能通过显式导入访问 |
| 接口还在设计中的新功能 | 每次改签名都要重编宿主 + 重启 |

## 一个容易被忽略的点

**wasm 适合"一次调用做很多事"，不适合"频繁小调用"。**

```
✗ 每帧调用 100 万次 wasm 的 add(a, b)
✓ 每帧调用 1 次 wasm 的 step(worldSnapshot)
```

因为跨边界要传参、切换执行上下文。**如果设计成细粒度调用，wasm 会比 native 慢一个量级**——这比沙箱本身的开销严重得多。

## 三个真实例子的判断

| 例子 | 判断 | 理由 |
|:--|:--|:--|
| **斗地主出牌判断** | **native** | 每局几十次，没有热更需求 |
| **AOI 九宫格** | **native** | 纯整数运算，6 万次/秒，跨边界不划算 |
| **运营活动逻辑** | **wasm** | 频率低，但**改一次要停服**——这是唯一无可替代的价值 |

**第四个例子：数值平衡公式**

策划天天调伤害公式，每次改都要重启 → **wasm**。而且接口稳定（`calcDamage(atk, def, crit): int`），符合"不改签名"的约束。这是 wasm 最典型的用法：**逻辑会变，接口不变。**

## 性能差异有多大

**没有实测数据**，只能说理论上：

| 因素 | 影响 |
|:--|:--|
| 沙箱 | wasm 的内存访问要过边界检查 |
| 跨边界调用 | 每次调用有固定成本（微秒级） |
| 编译优化 | 两者都过 LLVM，优化级别相当 |
| 启动 | native 是进程启动（毫秒），wasm 是宿主内加载（微秒） |

**判断方法**：如果这段逻辑不是"每帧百万次"，wasm 的性能损失通常感知不到。先用 wasm 让运营能改，真发现慢了再降回 native——**降级只需改 `project.yml` 里一行**。

## 最后一句

**typephp 让 PHP 不再是"慢语言"（编译成机器码），`pkg/wasm` 让它"能不停服换"（编译成可热替换的组件）。**

两者是**同一个编译器的两个输出目标**，不是两种技术路线。这也意味着：**切换成本极低**——同一份代码，改一行 yaml 就能换目标。

所以正常的工程里，**wasm 占比应该很小**——只有运营要频繁改、且接口已稳定的那几块。如果你的 wasm 模块比 native 还多，大概率是把"能热更"当成了默认选项。
