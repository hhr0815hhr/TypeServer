# 09 · wasm 还是 typephp：什么时候该用哪个

> 这一篇不是讲 API（那是 06 篇的事），是讲**判断**。
>
> 常见的误解是"wasm 是性能方案，performance 敏感就上 wasm"。**在这个框架里不成立**——
> `pkg/wasm` 的 API 是 `canary()` / `swap()` / `rollback()`，全是**发布**动作，不是性能动作。
>
> 理清这三个东西的区别，选择就自然清楚了。

## 先分清三个东西

| 名字 | 是什么 | 解决什么 | 粒度 |
|:--|:--|:--|:--|
| **typephp** | 把 PHP 编译成 C++（AOT） | **性能** + 单文件部署 | 全局（整个工程） |
| **`pkg/wasm`** | 运行时加载 `.cwasm` 模块 | **热更 / 灰度 / 回滚** | 按模块 |
| **wasm 模块本身** | Rust/C++ 编出来的字节码 | 可以是性能手段，也可以是"能热替换的容器" | 按导出函数 |

关键结论：**typephp 是编译方式，wasm 是发布手段。两者不冲突。**

## 一句话判断

> **typephp 解决"PHP 跑得快不快"，wasm 解决"逻辑能不能不停服更新"。**

```php
// 这段逻辑需要不停服更新吗？
//   是 → wasm（能热替换，但接口不能变）
//   否 → PHP（被 typephp 编译，性能已经接近 Go/Java）
```

## 为什么"PHP 慢"这个前提在 typephp 下不成立

普通的 PHP 是解释执行，慢。但这里不是：

```
PHP 源码 → typephp 编译成 C++ → clang 编译成机器码
```

所以下面这些"PHP 慢"的典型原因，大部分**不是语言问题，是写法问题**：

| 真慢的原因 | 怎么改 |
|:--|:--|
| 动态调用（`call_user_func`、`$obj->$method`） | 改成直接调用 |
| 大量数组拷贝（PHP 数组是值语义） | 传引用、或用固定结构的对象 |
| 每帧拼字符串 | 预先分配缓冲、或改用二进制 |
| 反射（`ReflectionProperty`） | 缓存到数组里（`Meta` 就是这么做的） |
| 算法复杂度高（O(n²)） | **换语言也没用，先换算法** |

**先把这些改掉，再考虑 wasm。** 大多数"性能问题"在第 2-4 条就解决了。

## 真的该上 wasm 的四种情况

### ① 需要不停服更新（这是 `pkg/wasm` 唯一的原生用途）

```php
$m = Module::load("activity", "/path/v1/dist/activity.cwasm");

// 活动逻辑改了，不想停服
$m->canary("/path/v2/dist/activity.cwasm", 100);   // 10% 玩家走新版（千分比）
// 观察 10 分钟，没问题：
$m->swap("/path/v2/dist/activity.cwasm");          // 全量
// 有问题：
$m->rollback();                                     // 回到 v1
```

实测切换耗时（`tsf verify wasm`）：

```
swap v2      5669 us
rollback v1  4316 us
```

**5 毫秒换一次实现，不需要重启进程。** 这是 wasm 在这里最实在的价值。

**必须满足的约束**（做不到就别用）：

| 能改 | 不能改 |
|:--|:--|
| 导出函数的实现 | 导出函数的签名 |
| 内部逻辑、数值、算法 | `package` / `world` 名（宿主按名匹配） |
| — | 宿主里的状态结构（换实现不迁移内存） |

所以：**接口稳定的模块才适合 wasm**。运营活动（"开始/结束/发奖"三个导出）符合；还在设计中的新功能不符合。

### ② 要复用成熟的 C/C++ 库

zlib、protobuf、物理引擎、加密库——重写成本远高于接入。

**注意**：这种场景**不一定用 `pkg/wasm`**。typephp 有 `.stub.php` 机制可以把 C++ 直接暴露成 PHP 类（`tsf` 工具链里的 `get_stub_api`），**比 wasm 快**（没有沙箱开销），但**编进二进制、不能热更**。

选哪个：

```
这段 C++ 代码会频繁改吗？
├─ 会（算法还在调）       → wasm（能热更）
└─ 不会（成熟的库，只调用）→ stub（性能更好）
```

### ③ 单帧内调用百万次的热点

比如 AOI 的视野计算、碰撞检测、大量二进制协议解析。

但先看 `pkg/aoi` 是怎么做的——**它没上 wasm，仍然是纯 PHP**：

```php
// 九宫格：纯数学，格子坐标的加减
$cx = intdiv($x, $cellSize);
$cy = intdiv($y, $cellSize);
```

1000 个实体 × 60 帧 = 6 万次/秒，PHP 编译后够用。**因为它是纯整数运算，没有动态调用。**

真正需要 wasm 的是"带复杂状态机 + 每帧百万次"的场景，比如物理引擎的连续碰撞检测。

### ④ 需要严格的内存布局

比如大批量二进制协议解析（固定偏移、大小端、对齐）。PHP 的字符串虽然也是字节数组，但每次 `substr` 都分配新内存。wasm 可以直接在内存上做 view。

## 什么时候**不要**用 wasm

| 场景 | 为什么 |
|:--|:--|
| 业务逻辑（状态机、规则判断） | 可读性 >> 性能。斗地主出牌判断每局几十次，PHP 完全够 |
| 调用频率低的（登录、支付、邮件） | 优化收益是 0，还多了工具链负担 |
| 接口还在变的新功能 | 每次改接口都要重编宿主 + 重启 |
| 需要读宿主状态的 | wasm 只能通过显式导入访问宿主，每次跨边界都有开销 |

**最后一条容易被忽略**：如果把"每帧百万次"的循环切碎成"百万次跨边界调用 wasm"，会**比纯 PHP 还慢**。wasm 适合"一次调用做很多事"，不适合"频繁小调用"。

## 一个完整的判断流程

```
这段代码慢吗？
├─ 没度量过 → 先埋点（Metrics / hrtime），别凭感觉
└─ 慢
   ├─ 是算法问题（O(n²)、重复计算）→ 改算法，换语言无用
   ├─ 是写法问题（动态调用、数组拷贝、反射）→ 改写法
   └─ 都不是
      ├─ 这段逻辑需要热更吗？
      │  ├─ 需要 → wasm（顺便解决性能）
      │  └─ 不需要
      │     ├─ 会频繁改算法吗？ → wasm
      │     └─ 稳定了 → stub（C++ 直连，最快）
      └─ 涉及大量跨边界的小调用 → 重新设计接口（批量而不是逐条）
```

## 三个真实例子的判断

### 斗地主的出牌合法性（07 篇）

- 频率：每局几十次
- **判断：PHP。** 频率太低，优化收益为零
- 除非：策划要经常调牌型规则**且**不能停服 → 那时用 wasm

### AOI 的九宫格（`pkg/aoi`）

- 频率：每帧每实体一次，6 万次/秒
- **判断：PHP。** 纯整数运算，无动态调用
- 如果真不够：优先 **stub**（不需要热更）

### 运营活动逻辑

- 频率：低（活动开关、发奖）
- 但**改一次要停服**
- **判断：wasm。** 频率不是问题，**可用性**才是——这是 wasm 唯一无可替代的场景

## 一张对照表

| 需求 | 选择 |
|:--|:--|
| 常规业务逻辑 | **PHP** |
| 需要不停服更新 | **`pkg/wasm`** |
| 需要 C++ 性能且稳定 | **stub**（`.stub.php`） |
| 需要 C++ 性能且会改 | **wasm** |
| 算法本身有问题 | **先改算法**，别换语言 |
| 没度量过就喊慢 | **先埋点** |

## 最后一句

**typephp 让 PHP 不再是"慢语言"，`pkg/wasm` 让逻辑可以"不停服换"。** 前者是默认（你什么都不用做，编译时自动发生），后者是按需（只有那几块需要热更的代码）。

所以正常的工程里，**wasm 占比应该很小**——如果你的 wasm 模块比 PHP 还多，大概率是判断错了。
