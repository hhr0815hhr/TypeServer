# S5 前置分析 —— 快照粒度怎么选

> 执行时间：2026-11-12
> 环境：tpc v0.9.6 原生 AOT / PHP 8.5.12 / WSL2 ext4
> **结论：粒度不是一道单选题。「恢复单元」由一致性边界决定（必须是房间），「存储单元」由 IO 效率决定（应该批量），两者本来就该分开——所以最优解是两级：房间级周期全量 + 玩家级高频增量，再叠一层高价值事件日志。按粒度直接切分（玩家/房间/分片三选一）都会在某一边明显吃亏。**

---

## 一、先验证前提：AOT 到底能不能做序列化

快照方案的可行性首先取决于 `serialize` / `unserialize` 在 AOT 下是否可用。实测：

```
serialize 可用: yes | unserialize 可用: yes | json: yes
```

三种都可用。真实成本（玩家对象含背包，`bag=50` 约 4.7 KB）：

| 状态规模 | 体积 | serialize | unserialize | json_encode |
|:--|:--:|:--:|:--:|:--:|
| bag=10 | 1.85 KB | 3.44 µs | 7.94 µs | 2.65 µs |
| bag=50 | 4.73 KB | **7.45 µs** | **22.78 µs** | 5.50 µs |
| bag=200 | 15.6 KB | 22.63 µs | 85.54 µs | 16.50 µs |
| bag=500 | 37.5 KB | 55.87 µs | 218.78 µs | 38.17 µs |

三点关键读数：

1. **反序列化比序列化贵 2–4 倍**（对象图重建比遍历贵）——所以"恢复时延"的瓶颈在反序列化，不在读盘；
2. **成本随体积近似线性**：serialize ≈ 1.5 µs/KB，unserialize ≈ 5.8 µs/KB；
3. **json 比 serialize 快 30%**，但会丢失类型信息（浮点精度、对象类型），只适合纯数值状态。

IO 侧（单进程、page cache 命中）：

| 写入方式 | 总数据量 | 耗时 | 折算 |
|:--|:--:|:--:|:--:|
| 1000 个小文件 × 4.7 KB | 4.7 MB | 22.6 ms | **22.6 µs/文件** |
| 每 10 个合并成 1 个文件（100 个） | 4.7 MB | 6.7 ms | 3.4 倍快 |
| 1 个 4.7 MB 大文件 | 4.7 MB | 3.2 ms | **7 倍快** |

**小文件写入的成本主要是元数据与 syscall，不是带宽。** 这条直接决定"存储单元不能等于恢复单元"。

## 二、四种粒度的定量对比

基准场景取自 S6/S4 的实测：一个 worker **3,000 在线**，玩家状态 4.7 KB/人（合计 14.1 MB），60 个房间 × 50 人（每房 235 KB）。

### 2.1 成本模型

| 粒度 | 一次全量快照的成本（3000 人） | 单房间恢复耗时 | 恢复半径 | 一致性 | 实现复杂度 |
|:--|:--|:--:|:--:|:--:|:--:|
| **A 玩家级**（每人一文件） | serialize 22.4 ms + 写 67.8 ms = **90 ms** | 1.2 ms | 单玩家 | ❌ 房间共享态丢失 | 低 |
| **B 房间级**（每房一文件） | serialize 0.37 ms×60 + 写 0.16 ms×60 = **32 ms** | **1.3 ms** | 单房间（50 人） | ✅ | 中 |
| **C worker 级**（一文件 14 MB） | serialize 22.4 ms + 写 9.6 ms = **32 ms** | 78 ms（但牵连 3000 人） | **整个 worker** | ✅✅ | 低 |
| **D 两级**（房间全量 + 玩家增量） | 32 ms + 增量 ~3 ms/2s = **约 80 ms/30s** | **1.3 ms + 重放 ≤2s** | 单房间 | ✅✅ | 高 |

### 2.2 三个必须看清的差异

**差异一：写成本差不多，恢复半径差 60 倍。**

A/B/C 三种粒度的**写成本几乎一样**（80–90 ms / 30 秒周期，折算 CPU 占用 0.3%），因为总数据量相同。真正的差别在恢复：

- 房间级：崩一个房间 → 只恢复 50 人（**1.3 ms**）；
- worker 级：崩一个房间 → 必须恢复全部 3000 人（**78 ms**），而且这 3000 人要么被踢下线、要么集体卡顿；
- 玩家级：恢复快，但房间的公共状态（怪物血量、掉落归属、计时器、随机种子）**根本不在任何人的快照里**，恢复出来是个状态自相矛盾的房间。

**差异二：玩家级快照有一致性硬伤，不是性能问题。**

MMO 的房间状态是"共享可变状态"：BOSS 血量、地面掉落、技能冷却、房间计时器。这些既不属于任何单个玩家，又决定了每个玩家的合法性（比如"这个掉落归谁"）。按玩家存快照，崩溃后无法复原这些，只能重建一个"新房间"——那本质上就是回档，只是回档得更细。

**差异三：一旦改成事件驱动，任何粒度都会爆。**

如果"有变化就写快照"：

- 3000 人 @10 Hz = 30,000 次/秒 × 4.7 KB = **141 MB/s**；
- 即便按房间合并（500 包/秒/房 × 235 KB）= **117 MB/s/worker**。

两者都不可行。**所以"周期 + 脏页合并"不是优化选项，而是唯一可行解。** 粒度只在"周期快照存什么"这个问题上有意义。

## 三、最优解：两级快照 + 冷热分层

### 3.1 结构

```
第 0 层（实时）   高价值写操作 → 事件日志（充值/交易/装备/掉落归属）
                  写放大最高但量最少，用于审计与精确恢复

第 1 层（2–3 秒） 玩家级「热状态」增量
                  只含坐标/HP/MP/临时 buff 等每秒都变的字段（约 1 KB）
                  每玩家一个 delta 记录，按房间批量落盘

第 2 层（10–30 秒）房间级全量快照
                  含房间共享态 + 全部玩家冷状态（背包/任务/技能）
                  一个房间一个文件，235 KB
```

### 3.2 为什么这样切

| 设计选择 | 依据（实测） |
|:--|:--|
| 恢复单元 = 房间 | 一致性边界在房间；且 S4 已证明房间是独立进程，崩了 4 ms 重启，恢复天然就是"重建这个房间" |
| 存储单元 = 房间文件（235 KB） | 单文件写 0.16 ms，比 50 个小文件（1.1 ms）快 7 倍 |
| 玩家增量 2–3 秒 | 把最坏回档从 30 秒压到 3 秒；单次成本仅 3.44 µs/人 |
| 冷热分离 | 背包占体积 80% 但极少变；bag=50 全量 7.45 µs，只存热状态（1 KB）约 1.5 µs，**省 80%** |
| 高价值操作走日志 | 回档 3 秒仍会丢交易，这类必须精确恢复 |

### 3.3 成本核算（3000 人 / worker）

| 项 | 频率 | 单次成本 | 折算占用 |
|:--|:--|:--:|:--:|
| 房间全量（60 房 × 235 KB） | 30 s | 32 ms | 0.1% |
| 玩家热增量（900 活跃 × 1 KB） | 2 s | 3.2 ms | 0.16% |
| 事件日志（按 5% 玩家有交易） | 实时 | 可忽略 | — |
| **合计** | — | — | **< 0.3% CPU** |

恢复：单房间 = 读 235 KB（0.16 ms）+ 反序列化 50 人（1.14 ms）+ 重放 ≤2 s 增量 + 进程重启 4 ms ≈ **6 ms**。远低于"< 3 秒"的目标。

## 四、被否掉的三个方案

| 方案 | 否决理由 |
|:--|:--|
| **纯玩家级**（每人一文件，Redis 存） | 房间共享态无处可放；且 3000 个小文件写比一个房间文件慢 7 倍 |
| **纯 worker 级**（RDB 式整体 dump） | 恢复半径 = 整个 worker，一个房间崩溃连累 3000 人；与 S4 的"房间进程"边界不匹配 |
| **事件驱动全量** | 117–141 MB/s 写放大，任何存储都扛不住；且没有合并窗口，IOPS 直接打满 |

还有一个常被忽略的坑：**跨进程恢复顺序**。房间进程重启时，如果先读玩家增量、后读房间全量，会出现"增量基于旧基线"的错误。正确顺序固定为：**先房间全量 → 再重放增量 → 最后补事件日志**，且每份数据带版本号，重放时校验基线版本。

## 五、S5 接下来要测什么

以上成本是模型推算 + 分项实测的组合。S5 本身要验证的是**端到端恢复时延**：

| 测试项 | 方法 | 通过标准 |
|:--|:--|:--|
| 房间级恢复时延 | 起 60 个房间进程，各存 235 KB 快照；kill 一个，测"重启 → 加载 → 服务恢复"总耗时 | < 50 ms |
| 增量重放正确性 | 快照后写入 N 条增量，恢复后比对状态哈希 | 完全一致 |
| 3000 人规模 IO 压力 | 60 房间同时快照（模拟全局定时器同时触发） | 不出现写风暴（错峰 > 分片抖动） |
| 回档窗口验证 | 记录最后一条成功增量时间，kill 后统计丢失操作数 | ≤ 3 秒内操作 |

其中"60 房间同时快照"这一项要特别测——**定时器同时触发会造成周期性写尖峰**，解法是给每个房间的周期加随机抖动（±20%），这一条务必落在实现里。

---

## 六、结论

1. **快照粒度不是"玩家/房间/分片"三选一**，而是三个正交决策：恢复单元（房间）、存储单元（房间文件）、触发策略（周期 + 脏页合并）；
2. **恢复单元必须是房间**，因为共享态的一致性边界在房间，且与 S4 的进程边界天然对齐；
3. **存储单元要批量**，1000 个小文件比 1 个大文件慢 7 倍；
4. **冷热分层比换粒度更值钱**：只存热状态能省 80% 的序列化成本，而状态瘦身对恢复时延是线性收益；
5. 事件驱动全量写在任何粒度下都不可行（117–141 MB/s），"周期 + 抖动"是必选项而非优化项。
