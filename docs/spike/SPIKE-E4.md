# E4 落地 —— 房间分级 + 重启强度监督

> 执行时间：2026-11-12
> 环境：tpc v0.9.6 原生 AOT / Swoole 6.2 / PHP 8.5.12
> **结论一句话：房间分级与监督都跑通了。退避阶梯实测 0 / 0 / 100 / 200 / 400 ms 逐级递增，第 6 次重启触发隔离、不再占资源；其余房间全程零影响。同时确认了协程模式的连带代价——宿主一崩，50 个协程房间一起重建。**

---

## 一、背景：为什么不用 `Process\Pool`

S4 用 `Swoole\Process\Pool` 验证过"房间独立进程"可行，但落地时发现它撑不起监督：

| 需求 | `Process\Pool` | 自建 `Swoole\Process` + `wait()` |
|:--|:--|:--|
| 感知子进程退出 | ❌ 只有 `WorkerStart`，拿不到退出事件 | ✅ `Swoole\Process::wait(true)` 返回 `pid/code/signal` |
| 重启退避 | ❌ 无任何节流（S4 实测 10 次连杀每次 4ms 复活） | ✅ 完全可控 |
| 重启强度限制/隔离 | ❌ 不支持 | ✅ 支持 |
| 分级（进程/协程）混合 | ❌ 池内 worker 同构 | ✅ 可按房间类型分派 |

所以监督层必须自己写。**`Process\Pool` 只适合"全部同构、且不怕重启风暴"的场景**，而房间恰恰不是。

---

## 二、拓扑与实现

```
父进程（监督器）
├── big0 … big5   各一个独立进程（对局/战场：状态价值高、数量可控）
└── small0        一个宿主进程，内含 50 个协程房间（挂机/个人房：数量多、单房价值低）

监督循环：
  Swoole\Process::wait(true) 阻塞回收
    → 60s 滑动窗口内计数
    → 超过 MAX_RESTARTS(5) 次 ⇒ 隔离（写 state=quarantined，不再重建）
    → 第 1~2 次立即重启；第 3 次起指数退避 100/200/400/800ms
```

代码只有 200 行左右（`spike/e4/main.php`），关键在三个判断：窗口计数、退避计算、隔离标记。状态与事件都落文件（`rooms/*.state`、`supervisor.log`），便于外部观测和排障。

## 三、实测

### 3.1 初始拓扑

```
进程数: 8 (1 父 + 6 大房 + 1 小宿主)
big0 pid=97833 … big5 pid=97838
small0 pid=97839  协程房间状态文件=50 个
```

### 3.2 kill 单个大房间：11.9 ms 重生，其余零影响

```
big3: 97836 -> 97888  耗时 11.9 ms  restarts=1
其他：big0/1/2/4/5 pid 全部不变，tick 连续（32）
```

11.9 ms 比 S4 的 4 ms 慢一些，因为这里是"父进程 wait 到退出 → fork → 子进程启动写状态"，多了一次状态文件写入与轮询间隔（2 ms）。

### 3.3 连续 kill：退避阶梯与隔离

```
第 1 轮: 97888 -> 97922  耗时  11.9 ms  state=running     restarts=2
第 2 轮: 97922 -> 98018  耗时 109.3 ms  state=running     restarts=3
第 3 轮: 98018 -> 98183  耗时 204.9 ms  state=running     restarts=4
第 4 轮: 98183 -> 98492  耗时 404.7 ms  state=running     restarts=5
第 5 轮: 98492 ->     0  耗时   4.2 ms  state=quarantined restarts=6
```

监督器日志（原始证据）：

```
exit big3 pid=97836 restarts=1 backoff=0ms
exit big3 pid=97888 restarts=2 backoff=0ms
exit big3 pid=97922 restarts=3 backoff=100ms
exit big3 pid=98018 restarts=4 backoff=200ms
exit big3 pid=98183 restarts=5 backoff=400ms
QUARANTINE big3 restarts=6 (窗口 60s)
```

**测到的延迟几乎等于配置的退避值 + 约 5~10 ms 的进程启动开销**，说明退避是真实生效的，不是"配了但没用"。

隔离后 `big3` 的 pid 记为 0、状态 `quarantined`，**不再占用进程与内存**。最终进程数 7（父 + 5 大房 + 1 宿主）。

### 3.4 协程模式的连带代价（实测）

kill 小宿主：

```
small0: 97839 -> 98534
协程房间 sroom0_0: pid 97839 -> 98534   ← 50 个协程房间一起重建
```

这就是 S4 测到的"崩溃半径 = 整个进程"在运维层面的体现：**一个小房间的致命错误会让同宿主内 49 个无辜房间一起重建**（重建后要重新激活玩家，成本远大于进程重启本身）。

所以分级不是优化，是必需：

| 房间类型 | 承载方式 | 依据 |
|:--|:--|:--|
| 对局 / 战场 / 活动副本 | 独立进程（19.6 MB，4~12 ms 重启） | S4+S6：状态价值高、数量可控 |
| 大地图分线 | 独立进程 + 分片 | 分线即天然隔离边界 |
| 挂机 / 个人房 / 离线托管 | 协程（约 0.24 MB/房） | 数量上千，卡一下可接受，但要接受"连带重建" |

## 四、三个关键设计判断

**1. 隔离不是"放弃"，而是"止损 + 转人工"。**

如果不对崩溃房间做隔离，一个"启动即崩"的房间会无限重启：S4 实测每次 4 ms，即 **250 次/秒**，CPU 与日志都会被刷爆。隔离之后它退化成一条待处理记录，让人来看，而不是让机器空转。

**2. 阈值取 5 次 / 60 秒，退避从第 3 次开始。**

- 第 1~2 次立即重启：覆盖偶发崩溃（OOM、瞬时依赖失败），玩家几乎无感；
- 第 3 次起退避：说明是持续性故障，拖慢重启频率、给依赖恢复留时间；
- 第 6 次隔离：基本可判定为"代码或数据坏了"，重启无用。

这三个数是策略而非定律，应按实际故障分布调；关键是**机制已经在了**。

**3. 分级依据用数据而不是感觉。**

19.6 MB/进程（S4）与 3.5 KB/连接、20.9 µs/包（S6）这几个数决定了"什么房间值得独立进程"。真机复测后应重新算一遍阈值。

## 五、已知限制与修正方向

| 限制 | 影响 | 修正 |
|:--|:--|:--|
| 退避用 `usleep` 阻塞父进程 | 退避期间父进程无法处理其他房间的退出，极端情况下多个房间同时崩会排队 | 改成 `Swoole\Timer::after` + 待重启队列，父进程始终非阻塞 |
| 隔离只写标记，无告警与恢复入口 | 需要人工发现 | 接告警（企微/邮件）+ 提供"解除隔离"的管理命令 |
| 窗口计数在内存里 | 监督器本身重启后计数清零 | 落盘或放 `Swoole\Table`；监督器重启应视为一次全量重启并限流 |
| 小房间宿主内没有单房间隔离 | 一个协程崩带走 50 房 | 协程内必须包 `try/catch`；危险逻辑（玩家自定义脚本、AI 寻路）一律不放协程池 |
| 没有资源配额（CPU/内存） | 单个房间吃满 CPU 会拖慢同机其他房间 | 后续接 cgroup 或 wasm 的 fuel/epoch（S3 已验证） |

前两条建议在接入实际服务前补掉，其余可以随迭代做。

## 七、E4 判定

**落地通过。** 三个可用的数字：

1. **11.9 ms**：单房间崩溃后的重生耗时；
2. **0 / 0 / 100 / 200 / 400 ms**：退避阶梯，第 6 次隔离——重启风暴被彻底堵住；
3. **50**：一个协程宿主崩掉时被连带重建的房间数——这就是为什么大房间必须独立进程。

至此 E1（wasm 热更链路）与 E4（崩溃半径 + 监督）两条都从"验证可行"推进到了"有可运行骨架"。剩余工作属于工程细化而非技术验证：非阻塞退避、隔离告警、监督器自身的状态持久化，以及把房间状态接到 S5 的两级快照上。

## 八、第二版：非阻塞退避 + 告警 + 解除隔离

第一版的退避用 `usleep` 阻塞父进程——房间数一多就会出问题：**A 房在退避 400 ms 期间，B 房崩了没人收**。第二版把这条修掉，并补上告警与人工恢复入口。

### 8.1 改了什么

| 项 | 旧实现 | 新实现 |
|:--|:--|:--|
| 回收退出 | `Process::wait(true)` 阻塞 | `Process::wait(false)` 非阻塞轮询 |
| 退避 | `usleep(backoff)` 卡住整个循环 | 排进「待启动队列」，到期才 fork |
| 告警 | 只写 `state=quarantined` | 追加写 `alarms.log` + stdout（供采集器） |
| 解除隔离 | 无 | 写 `rooms/<key>.cmd` 内容 `reset`，1 s 内生效 |
| 轮询开销 | — | 自适应：有退避任务 1 ms，空闲 4 ms |

### 8.2 A/B 对照：退避会不会拖累其他房间

实验设计：把 `big0` 打到 `restarts=4`（下一次退出触发 400 ms 退避）→ kill big0 → **等 50 ms**（让它进入退避窗口）→ 再 kill `big1`，测 big1 的重生耗时。

```
--- A 组：阻塞退避（旧实现） ---
  big1（旁观者）重生:  358.0 ms   ← 被 big0 的 400ms 退避拖住
  big0（退避者）重生:  364.0 ms

--- B 组：非阻塞退避（新实现） ---
  big1（旁观者）重生:    5.6 ms   ← 立刻被处理
  big0（退避者）重生:  354.1 ms   ← 自己仍按退避走

旁观房间重生：阻塞 358.0 ms  →  非阻塞 5.6 ms（**63 倍**）
```

退避者自己的耗时在两组里一致（约 354–364 ms），说明**退避本身没被削弱，只是不再阻塞别人**。这才是正确的语义。

> 实验踩坑：第一次做这个对照时两组都是 6 ms，看起来"修了也没用"。原因是两次 kill 几乎同时发出，`wait` 返回顺序不确定，big1 可能先被回收。**必须先把 big0 的退出消化掉、进入退避窗口，再 kill 旁观者**，实验才成立。

### 8.3 隔离告警与解除

```
连续 kill big2：
  第 6 轮: 166610 -> 无  state=quarantined restarts=6

alarms.log：
2026-11-12T11:55:33+08:00 QUARANTINE key=big2 restarts=6 window=60s \
  reason=窗口内重启超过 5 次，疑似启动即崩；修复后写 rooms/big2.cmd 为 reset

写 reset 命令后：
  cmd big2 reset
  respawn(reset) big2 pid=175734
  big2: pid=175734 state=running restarts=0
```

告警文本里带了**处置指引**（"修复后写 rooms/big2.cmd 为 reset"），值班的人不需要查文档就知道下一步。解除后计数清零、房间重新纳入监督。

> 这里踩了第二个坑：隔离时没有把内部 `pids` 清零，导致 reset 只改了状态文件、没有真正 fork——房间显示 `running` 但其实**没有进程**。这类"状态文件说活着、实际是空的"最难查，现在隔离路径会显式 `pids[key] = 0`。

### 8.4 轮询开销

```
自适应轮询（空闲 4ms）：3 秒内 CPU 20 ms => 0.66% 单核
```

纯 1 ms 轮询实测约 2%，放宽到 4 ms 后降到 0.66%——对一个节点级的监督进程完全可以接受。有退避任务在等时仍用 1 ms，保证重生延迟不受影响。

### 8.5 仍然缺的

| 缺口 | 影响 | 建议 |
|:--|:--|:--|
| 告警只写文件 | 需要采集器接走才会真的通知到人 | 接 filebeat/vector → 企微/邮件；或在 `alarm()` 里加 webhook |
| 监督器自身无持久化 | 监督器重启后计数清零、已隔离房间会被重新拉起 | 落盘到 `supervisor.state`，启动时恢复 |
| 无"暂停重启"开关 | 发布期间想让某些房间不受监督 | 增加 `rooms/<key>.cmd` 的 `pause` / `resume` 指令 |
| 小宿主机内无单房隔离 | 一个协程崩带走 50 房 | 协程内 `try/catch`；危险逻辑不进协程池 |

前两条建议在接入实际服务前补掉。

## 九、第三版：监督器状态持久化

### 9.1 为什么必须做

监督器如果重启（发布、OOM、手工重启），内存里的计数与隔离标记全丢，会导致两个后果：

1. **已隔离的房间被重新拉起**——隔离机制形同虚设，那个"启动即崩"的房间又回到重启循环；
2. **重启次数从 0 重新计**——退避阶梯与阈值全部失效，等于给了它 5 次免费的快速重启。

这两个都不是理论风险：监督器本身也是进程，发布时必然重启。

### 9.2 实现

状态落 `supervisor.state`，制表符分隔，一行一个房间：

```
# key	restarts	window_start	quarantined	updated=2026-11-12T12:01:19+08:00
big0	0	1794456065	0
big2	6	1794456065	1        ← 已隔离
big4	2	1794456065	0
small0	0	1794456065	0
```

三个要点：

- **只在状态变更时落盘**（退出、隔离、重生、reset 各一次），不是每轮询都写；
- **写临时文件再 `rename`**，保证不会读到半截文件（`rename` 在 AOT 下可用）；
- **启动时恢复**：`quarantined=1` 的房间只写状态标记、**不 fork**，并在日志里明确记录。

### 9.3 实测

```
=== 隔离前的状态文件 ===
big2	6	1794456065	1
big4	2	1794456065	0

=== kill -9 监督器后重启 ===
重启后进程数: 7（期望 7：big2 被隔离，少一个房间进程）
big2: pid=0 state=quarantined restarts=6
big4: pid=191215 restarts=2

启动日志:
restore quarantined big2 restarts=6（不自动拉起）
supervisor ready, children=6/7 blocking=0 restored_quarantined=1 restored_counts=1

=== 计数是否真的累计：kill big4 一次 ===
big4 restarts=3        ← 若是 1 就说明清零了
exit big4 pid=191215 restarts=3 backoff=100ms

=== reset 解除隔离 ===
big2: pid=191320 state=running restarts=0
respawn(reset) big2 pid=191320
进程数: 8
```

三条全部达成：隔离跨重启保留、计数跨重启累计、reset 仍有效。

### 9.4 一个需要注意的边界

`window_start` 也一起持久化了。如果监督器停机时间超过 60 秒窗口，恢复后第一次崩溃会**先触发窗口滚动、计数归零**——这是正确行为（旧窗口已过期），不是 bug。反过来说：**监督器长时间停机后恢复，等价于给所有房间重置了一次计数**，这符合"窗口是一段时间内的重启强度"这个语义。

### 9.5 剩余缺口

| 缺口 | 影响 | 建议 |
|:--|:--|:--|
| 告警只写文件 | 需要采集器接走才会通知到人 | 接 filebeat/vector → 企微/邮件，或在 `alarm()` 加 webhook |
| 缺"暂停重启"开关 | 发布期间无法让某些房间暂时不受监督 | 增加 `rooms/<key>.cmd` 的 `pause` / `resume` |
| 小宿主机内无单房隔离 | 一个协程崩带走 50 房 | 协程内 `try/catch`；危险逻辑不进协程池 |
| 没有资源配额 | 单房吃满 CPU 会拖慢同机其他房间 | 接 cgroup 或 wasm 的 fuel/epoch（S3 已验证） |

至此 E4 的监督层在"能防住重启风暴"这个目标上是闭环的：**退避生效、隔离生效、告警可见、可人工恢复、重启不丢状态**。
