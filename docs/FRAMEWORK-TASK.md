# TSF（TypePHP Server Framework）架构设计与任务分解

> **注意（2026-11-18）**：本文里的 wasm 相关内容已移除 —— wasm 是沙箱，
> 访问不到宿主数据，无法替代 Lua。当前方案见 [research/hot-reload.md](research/hot-reload.md)。

> 版本：v0.1 草案 · 编制时间：2026-11-12 · 状态更新：M0–M6 已交付（对应 TSF v0.6.0）
> 依据：S1 / S2 / S3 / S4 / S5 / S6 六项技术验证 + E1 / E2 / E4 三项落地骨架（`spike/` 下有可复现代码）
> 定位：**通用高性能游戏服务器框架**，用 TypePHP（AOT）+ PHP 取代「C++ + Lua」
> **本文是给排期用的：每个任务都有验收标准与实测依据，决策处标注了"为什么不是另一个方案"。**

---

## 零、先看结论

1. **技术前提已经验证完毕**，不存在"能不能做"的风险；剩下的全是工程量与产品取舍。
2. **架构主线定了四条**：Swoole 网络 + Service 消息模型 + 房间级进程隔离 + 三级热更（数据/模块/进程）。
3. **和 C++/Lua 最大的差异不是性能，是热更**：AOT 之后 PHP 代码改不了，必须用"配置热更 + wasm 模块热更 + 滚动重启"三条轨道替代 Lua 的脚本热更。这一条如果不提前设计进框架，后期改不动。
4. **Composer 插件化在 AOT 下必须改成"编译期装配"**：Hyperf 那套"装包即生效"依赖运行时加载，AOT 需要重新编译。框架要把这件事做到"一条命令、增量编译、秒级重启"。
5. 工作量估算：**94 人日**；单人约 **19 周**，3 人并行约 **8–10 周**。

## 一、项目定位

### 1.1 目标

| 维度 | 目标 |
|:--|:--|
| 性能 | 单 worker 3,300 在线 @10Hz（S6 实测），单机 2.6 万在线（8 worker） |
| 隔离 | 房间崩溃半径 = 1 个房间，恢复 ≤15 ms（S4/E4/D 实测 5.6–11.9 ms） |
| 热更 | 配置热更即时生效；玩法逻辑热更 4–6 ms；代码版本滚动重启，玩家无感（靠快照 9.6 ms） |
| 开发体验 | 全栈 PHP + Composer 生态 + IDE 静态分析；`tsf watch` 改一行代码 3 秒内看到效果 |
| 运维 | 崩溃自动恢复、隔离告警、指标可观测、灰度可回滚 |
| 生态 | 插件按需安装（`composer require typephp/xxx`），不用的不编译进产物 |

### 1.2 非目标（明确不做，防止范围膨胀）

| 不做 | 原因 |
|:--|:--|
| 自研网络库 / 自研事件循环 | Swoole 已在 AOT 下验证可用（S4/S6 全跑在上面），自研只增加永久维护负担 |
| 通用 Durable Execution 平台（Temporal 类） | 对 tick 模型是错配；只借"事件溯源"概念（E2） |
| 全量事件溯源 | 成本高，只有审计/回滚需要；一级（高价值写）足够 |
| 完整分布式事务 | 用"事件日志 + 幂等 + 补偿"解决 99% 场景，不引入 2PC |
| 一房一进程地塞 wasm 宿主 | 19.6 + 55 ≈ 75 MB/房，成本失控；wasm 宿主应共享在跑玩法的进程里 |
| 对标 Unity/Unreal 那种引擎能力（渲染、物理） | 服务端框架，不做客户端引擎 |

### 1.3 对标分析与取舍

成熟框架的能力清单，逐项决定"抄什么、不抄什么"：

| 能力 | Skynet (C+Lua) | Orleans (.NET) | Pomelo (Node) | Akka | Hyperf | **TSF 决策** |
|:--|:--|:--|:--|:--|:--|:--|
| 并发模型 | service + 消息队列 | virtual actor | 进程 + session | actor | 协程 | ✅ **Service + 单线程消息循环**（进程内协程执行，隔离由消息保证） |
| 服务隔离 | 服务级 | 无（单进程） | 进程级 | actor 级 | 无 | ✅ **房间级进程**（S4 实测 19.6 MB / 4 ms 重启） |
| 热更 | Lua 脚本热加载 | 无 | 无 | 无 | 无 | ⚠️ **三级轨道**（见 §1.4） |
| 持久化 | 自建 | Provider | 自建 | Persistence | ORM | ✅ **房间快照 + 高价值事件日志**（S5/E2 实测） |
| 集群 | master/slave | silo + cluster | 多 frontend | cluster sharding | 无 | ✅ 服务发现 + 一致性哈希分片 + 跨服 RPC |
| 插件化 | 无 | NuGet 包 | 无 | 模块 | **Composer + ConfigProvider** | ✅ **Composer，但编译期装配**（§3.2） |
| 网关/会话 | 有 | 无（自建） | **frontend/backend 分离** | 无 | 无 | ✅ 抄 Pomelo 的 gateway 分离 |
| 匹配 | 无 | 无 | 有 | 无 | 无 | ✅ 自研匹配器（区间 + 队列 + 超时放宽） |
| AOI/场景 | 无 | 无 | 有 | 无 | 无 | ✅ 九宫格 AOI（大地图分线） |
| 定时器 | 时间轮 | 有 | 有 | scheduler | 有 | ✅ 最小堆 + Swoole\Timer，精度 10 ms |
| 分布式事务 | 无 | 有（弱） | 无 | 无 | 无 | ❌ 用事件溯源 + 幂等替代 |
| 观测 | 有 | Metrics | 有 | Telemetry | 有 | ✅ 指标 + 慢调用 + 陷阱统计（E1 已实现 per-module 观测） |
| GM/后台 | 无 | 无 | 无 | 无 | 无 | ✅ 内置指令通道 + Web 后台（可选包） |

**结论**：并发模型抄 Skynet（服务隔离 + 消息），集群与网关抄 Pomelo，生命周期管理抄 Orleans（grain activation ≈ 房间按需激活/回收），插件化抄 Hyperf 但改装配方式。

### 1.4 与 C++/Lua 的根本差异：热更

这是全篇最重要的一节。**AOT 的代价就是代码在编译期固定**，必须承认并设计替代方案。

先纠正一个常见误解：TypePHP 的 `embedded-files` 会把不支持 AOT 的依赖**在构建期**转成 opcode 嵌入二进制，运行时 `require` 是从**内存 opcode 表**加载——**不是从磁盘读文件**。所以"改磁盘上的 .php 就能热更"这条路走不通。

三级热更轨道：

| 轨道 | 机制 | 生效时间 | 适用 |
|:--|:--|:--:|:--|
| **L1 数据热更** | 配置表（Excel → 二进制）文件监听 + 原子替换 | **<100 ms** | 数值、掉落、活动参数（占日常变更的 80%） |
| **L2 模块热更** | wasm 模块：新实例就绪 → 换句柄 → 释放旧实例 | **4–6 ms**（E1 实测 3.7–5.5 ms） | 需要频繁改的玩法逻辑、有风险的第三方脚本 |
| **L3 代码热更** | 滚动重启：快照恢复（房间 9.6 ms）+ 玩家重连 | **秒级，玩家无感** | 框架层/数据结构变更（低频但必须） |

**关键设计含义**：
- 业务代码从第一天就要按"能不能热更"分类落位：稳定性高的走 AOT，变化快的走 wasm；
- L3 必须做到"玩家无感"，否则框架在日常维护上会很难受——这依赖 S5 的快照恢复与 D 的快速重启；
- **不要承诺"改任何 PHP 都立即生效"**，那是 Lua 方案的能力，AOT 给不了。给不了就要提前说清楚。

## 二、架构总览

### 2.1 分层

```
┌──────────────────────────────────────────────────────────┐
│ 业务层  game/  玩家、战斗、任务、活动（AOT 编译 + 可选 wasm 模块）│
├──────────────────────────────────────────────────────────┤
│ 框架层  src/   actor · room · network · match · db · rpc … │  ← Composer 组件
├──────────────────────────────────────────────────────────┤
│ 引擎层  ext/   swoole · wasm-host(Rust .so) · codec · timer│  ← C/C++/Rust
├──────────────────────────────────────────────────────────┤
│ 运行时  TypePHP AOT 二进制 + Swoole 事件循环 + Zend（内嵌）│
└──────────────────────────────────────────────────────────┘
```

**为什么引擎层要 Rust/C++**：wasm 宿主、序列化、编解码这类"每包都要跑"的东西，用 PHP 写会吃掉一半帧预算（S6 实测：PHP 业务层每包 20.9 µs，其中约 12 µs 是 syscall，纯 PHP 逻辑约 9 µs）。下沉到原生能把这部分压到微秒以下。

### 2.2 进程模型

```
                    ┌──────────────┐
   客户端 TCP ─────▶│  gateway ×N  │  连接/编解码/鉴权/心跳/限流，无业务状态
                    └──────┬───────┘
                           │ UDS（批量投递 + 背压）
              ┌────────────┼─────────────┐
              ▼            ▼             ▼
        ┌──────────┐ ┌──────────┐  ┌──────────┐
        │ world ×1 │ │ room ×N  │  │ lobby ×N │
        │ 全局单点 │ │ 大房独占 │  │ 小房协程 │
        └──────────┘ └──────────┘  └──────────┘
              │            │             │
              └────────────┼─────────────┘
                           ▼
                 ┌───────────────────┐
                 │ supervisor ×1     │  重启监督/退避/隔离（E4）
                 └───────────────────┘
```

| 进程类型 | 数量 | 职责 | 崩溃影响 |
|:--|:--:|:--|:--|
| **gateway** | 2–4 | 连接管理、协议编解码、鉴权、心跳、限流、路由 | 该进程上的连接断开，客户端重连 |
| **world** | 1（可主备） | 全局单点服务：排行榜、跨服、世界 Boss、全局定时 | 全服短暂阻塞，需快速重启 |
| **room** | 按房间数 | 对局/战场/副本，一房一进程 | **仅该房间**（S4 实测） |
| **lobby** | 1–2 | 挂机/个人房，宿主机内多协程 | **整个宿主内的所有小房**（S4 实测连带） |
| **supervisor** | 1 | 进程监督、退避、隔离、状态持久化 | 监督失效，需 init 拉起 |

**gateway 为什么必须无业务状态**：这样 gateway 可以随意重启/扩容，断线重连不丢数据。代价是多一跳转发（UDS 往返约 40 µs，S2 实测 sidecar 41 µs），**所以 gateway 只做协议处理，不碰业务**；同一玩家的业务消息按 `uid` 哈希固定投到同一个 room 进程，避免状态分裂。

### 2.3 一次玩家操作的完整路径

```
客户端发包
  → gateway 收包：拆包 → 解密 → 解压 → 反序列化 → 鉴权校验（session 表）
  → 查路由表：uid → room 进程（一致性哈希）
  → 投递到目标 room 的 mailbox（UDS 批量写，攒批 200 µs）
  → room 进程：Service 消息循环取出 → 派发给 Player Actor 的 handler
  → 业务逻辑（AOT 编译代码 / 必要时调 wasm 模块 0.8 µs）
  → 状态变更：写内存 + 追加事件日志（高价值操作）
  → 回包：序列化 → 路由回 gateway → 写回客户端
```

关键延迟预算（基于实测）：

| 环节 | 预算 | 依据 |
|:--|:--:|:--|
| gateway 编解码 | ≤20 µs/包 | 原生实现，未实测，待标定 |
| UDS 跨进程 | ~40 µs | S2 实测 sidecar 往返 41 µs |
| Service 调度 | ≤5 µs | 队列 + 协程切换 |
| 业务逻辑 | ≤100 µs | 帧预算的 0.2%（50 ms 帧） |
| wasm 调用 | 0.8 µs | E1 实测 |
| 事件日志追加 | ≤7 µs | E2 实测批量 1.55 M/s |

一次典型操作 **~200 µs**，在 50 ms 帧里占比 0.4%。

### 2.4 关键设计决策

| # | 决策 | 依据 | 代价 |
|:--:|:--|:--|:--|
| D1 | 网络用 Swoole，不自研不引 libhv | S4/S6 已在 AOT 下跑通；libhv 需额外写 stub（未验证） | 受 Swoole 版本约束 |
| D2 | Service 单线程消息循环（进程内也用消息，不共享内存） | 消除竞态；Skynet 验证过的模型 | 消息拷贝开销，需零拷贝优化 |
| D3 | 大房进程 / 小房协程 | S4：进程 19.6 MB/4 ms 重启；协程 0.24 MB 但连带 | 需分级策略与配置 |
| D4 | 三级热更（数据/模块/进程） | AOT 不可运行时改代码 | 业务需按热更需求分类落位 |
| D5 | 房间级快照 + 高价值事件日志 | S5 恢复 9.6 ms；E2 零丢失 | 写放大与存储 |
| D6 | Composer 编译期装配 + embedded-files 双轨 | AOT 编译需要源码；非 AOT 依赖靠 opcode 嵌入 | 安装包后要重新编译 |
| D7 | 监督器自建（不用 Process\Pool） | E4：Pool 拿不到退出事件、无退避无隔离 | 多写 200 行 |
| D8 | 帧预算按"每包 20.9 µs"倒推 | S6 实测 | 高负载下必须降级策略 |

## 三、组件划分

### 3.1 包清单

每个包是一个 Composer 包，独立可测、可裁剪。

| 包 | 职责 | 关键内容 | 必需 |
|:--|:--|:--|:--:|

### 3.2 Composer 装配机制（AOT 下的"随用随装"）

Hyperf 的做法：安装包 → `ConfigProvider` 注册 → 运行时容器自动发现。**AOT 需要在编译期完成同等的事**：

```php
// 每个包提供 ConfigProvider
final class ConfigProvider
{
    public function __invoke(): array
    {
        return [
            'dependencies' => [PlayerRepository::class => DbPlayerRepository::class],
            'listeners'    => [PlayerLoginEvent::class => [SendWelcomeMail::class]],
            'commands'     => [RoomDebugCommand::class],
            'annotations'  => ['scan' => ['path' => __DIR__ . '/Controller']],
            'publish'      => [/* 默认配置 */],
        ];
    }
}
```

构建流程：

```
composer require typephp/match
   ↓
tsf build
   ├─ 扫描 vendor/composer/installed.json，收集所有 ConfigProvider
   ├─ 合并配置（依赖/监听/命令/路由）→ 生成 build/container.php（编译期固化）
   ├─ 收集 AOT 编译源：所有包 src/ + 业务 src/
   ├─ 非 AOT 兼容依赖 → 走 embedded-files 转 opcode 嵌入
   └─ 产出 build/tsf-server（单二进制 + 嵌入式配置）
```

**四条必须遵守的规则**：
1. **不能用运行时反射做容器装配**——AOT 需要编译期确定的类型图；注解扫描必须在构建期完成；
2. **不能依赖"改 PHP 文件即生效"**——开发期用 `tsf watch`（增量编译 + 重启），生产期走三级热更；
3. **玩法功能一律做成可选包，不进核心**——判据是"是否所有游戏都要"：棋牌不需要帧循环和视野，
   SLG 不需要 50 ms 帧同步。包在 `tsf/pkg/<name>/`，用 `pkg.json` 声明命名空间与依赖，
   工程用 `project.json` 的 `packages` 选装，**没声明的包根本不参与编译**。
   AOT 兼容性随包声明（不兼容的走 embedded-files，M6 实现）。
4. **源码里不出现 `mixed` 类型声明**——消息体用 `string|array|object`，容器只装 `object`，
   配置值用 `string|int|float|bool|array`。这不是性能要求（实测 `mixed` 与具体类型同速，
   见 `bench/REPORT.md` §9.1），而是"让签名把约定说清楚"。门禁：`tsf lint`。

### 3.3 目录结构

目录按**层**划分，命名空间与物理路径一一对应；依赖只能单向向下
（`Gateway → Transport → Protocol → Kernel`）。这套结构在 M1 收口后重排过一次，
原因与取舍见 `docs/archive/tsf-readme-full.md` §8。

```
tsf/                          ← 框架源码仓库
├── src/
│   ├── Kernel/               Bootstrap / Config / Container / Logger
│   ├── Protocol/             分帧 + 消息体
│   │   ├── Contract/         FrameCodec / PayloadCodec（接口）
│   │   ├── Frame/            HeaderFrame / NativeHeaderFrame
│   │   └── Payload/          Raw / Json / Msgpack / Registry / Protobuf
│   ├── Transport/            Server（抽象）+ Tcp/ + Ws/ + ServerFactory
│   ├── Gateway/              Gateway / Session / SessionManager / TokenAuth / RateLimiter
│   ├── Service/              （M2）mailbox、调度
│   ├── Actor/                （M2）
│   └── Room/                 （M3）
├── ext/
│   ├── wasm-host/            Rust：wasm 宿主 C ABI（已有，spike/s2）
│   └── codec/                C++：帧原语 c_encode / c_frame_len / c_decode_body
├── bin/tsf                   命令行入口
└── composer.json

my-game/                      ← 业务项目
├── composer.json             依赖 tsf 各包
├── config/
├── src/
│   ├── Player/
│   ├── Battle/
│   └── wasm/                 可热更模块（PHP → wasm）
├── project.yml               TypePHP AOT 配置
└── build/                    编译产物
```

**`ext/` 的边界**：只放原生原语，不放带协议语义的 PHP 类。
适配类（如 `NativeHeaderFrame`）一律在 `src/` 下，这样扩展缺失时只影响被选中的实现。

## 四、核心子系统设计

### 4.1 引导与生命周期

```php
// 业务入口
require __DIR__ . '/vendor/autoload.php';
TSF\Bootstrap::run(__DIR__);
```

启动序列（顺序不能错）：

```
1. 加载编译期容器（build/container.php）
2. 初始化配置（含 ConfigProvider 默认值 + 环境覆盖）
3. 初始化日志/指标（最先可用，后续步骤出错要能记录）
4. 初始化存储（DB/Redis 连接池，失败则快速失败退出）
5. 初始化 wasm 宿主（每个模块校验 manifest，不匹配拒绝启动）
6. 按进程角色启动：gateway → room → world（先起下游再起上游）
7. 注册信号处理（SIGTERM 优雅退出：摘流量 → 落快照 → 退出）
8. 就绪探针置位
```

**验收**：任一初始化步骤失败时，进程以非 0 退出且日志含明确原因；`SIGTERM` 后 5 秒内完成优雅退出。

### 4.2 网络与协议

```php
interface Server
{
    public function listen(string $host, int $port, array $options = []): void;
    public function onConnect(callable $cb): void;      // fn(int $fd, string $remote)
    public function onMessage(callable $cb): void;      // fn(int $fd, string $payload)
    public function onClose(callable $cb): void;
    public function send(int $fd, string $frame): bool;
    public function broadcast(array $fds, string $frame): void;
}
```

帧格式（8 字节头，全原生处理）：

```
| len(4B, 含头) | msgId(2B) | flags(1B: 压缩/加密/序号) | reserved(1B) | body |
```

- 拆包/粘包在 C++ 扩展里做，**回调只收完整帧**（避免 PHP 层切字符串）；
- 心跳：服务端 30 s 未收包断开，客户端 15 s 发一次；
- 顶号：同 uid 新连接踢旧连接，旧连接收到 `KICKED` 帧；
- 限流：每连接令牌桶（默认 50 包/s，可配置）。

**验收**：单 gateway 进程 1 万连接、每连接 10 Hz 心跳，CPU ≤60% 单核；**待标定**（S6 只测了回环 echo，未测真实编解码）。

### 4.3 Actor 与调度

```php
abstract class Service
{
    protected int $id;
    public function getId(): int;
    public function send(int $targetId, string $cmd, mixed $payload): void;  // 异进程也行
    abstract public function handle(string $cmd, mixed $payload): void;
}

// Actor：挂在 Service 内的实体（玩家、怪物、NPC）
abstract class Actor
{
    public function onMessage(string $cmd, mixed $payload): void;
    protected function tick(int $deltaMs): void;   // 可选，按帧
}
```

调度模型：

```
每个 Service 一个 mailbox（进程内 = 无锁队列，跨进程 = UDS 收包）
主循环：
  while (true) {
    批量取出 ≤N 条消息（N=100，避免饿死定时器）
    逐条 handle()（协程内执行，可 await IO）
    处理到期的定时器
    处理帧回调（房间类的 Service 每 50 ms 一次 tick）
    yield（Swoole\Coroutine::sleep(0)）
  }
```

**为什么进程内也用消息而不是直接调用**：直接调用会产生跨 Service 的隐性依赖与竞态（A 调 B 时 B 的状态可能正在被改）。消息模型强制解耦，也让"本地调用"和"远程调用"在业务代码里长得一样——将来把 Service 拆到别的进程不用改业务代码。

**验收**：单 Service 消息吞吐 ≥50 万条/s；消息延迟 p99 ≤100 µs（进程内）；跨进程 p99 ≤500 µs。

### 4.4 定时器

```php
TSF\Timer::after(int $ms, callable $cb): int;
TSF\Timer::tick(int $ms, callable $cb): int;
TSF\Timer::clear(int $id): void;
TSF\Timer::at(string $cron, callable $cb): int;     // "0 5 * * *"
```

实现：最小堆 + 单次 `Swoole\Timer::after` 驱动（避免大量 Timer 句柄）。精度 10 ms，同一毫秒内的定时器合并执行。

**验收**：10 万个定时器时，单次 tick 处理 ≤1 ms；误差 ≤20 ms。

### 4.5 房间、场景与匹配

```php
final class Room
{
    public static function create(RoomConfig $cfg): RoomHandle;   // 分配进程 + 初始化
    public function join(int $uid): void;
    public function leave(int $uid, string $reason): void;
    public function tick(int $deltaMs): void;                     // 帧循环
    public function snapshot(): RoomSnapshot;                     // S5 的两级快照
    public function onEvent(string $type, mixed $payload): void;
}
```

房间分派（进程 vs 协程）的判断：

| 判据 | 走进程 | 走协程 |
|:--|:--|:--|
| 单房价值 | 高（对局、战场、副本） | 低（挂机、个人房） |
| 数量 | 少（数十~数百） | 多（上千） |
| 帧逻辑 | 有（每帧 tick） | 无或极轻 |
| 崩溃容忍 | 不能连累他人 | 可接受连带重建 |

AOI（大地图分线用）：

```php
$aoi->update($uid, $x, $y);              // 移动时更新九宫格
$aoi->query($x, $y, $radius): array;     // 取视野内玩家
$aoi->onEnter($cb); $aoi->onLeave($cb);  // 进出视野事件
```

**验收**：1,000 人同场景，AOI 更新 p99 ≤50 µs；房间 tick（200 实体）≤5 ms。

### 4.6 数据访问

```php
interface Repository
{
    public function find(int $uid): ?PlayerData;
    public function save(PlayerData $data): void;      // 写穿 + 事件日志
    public function transaction(callable $fn): void;
}
```

- ORM 用协程连接池；**禁止在 tick 路径里做同步 DB 调用**（必须走"先改内存 + 异步落库"）；
- 分库分表键固定为 `uid`，避免跨库事务；
- 缓存策略：读穿透 + 热点本地缓存（`Swoole\Table`）+ 写穿。

**验收**：单进程 1,000 次/s 玩家存档写入，p99 ≤5 ms（S5 实测快照写盘 4 ms 可作参考）。

### 4.7 快照与事件日志

直接复用已验证方案：

| 层 | 频率 | 内容 | 实测 |
|:--|:--:|:--|:--:|
| 房间全量 | 5–30 s（±20% 抖动） | 共享态 + 玩家冷状态，143 KB/房 | 恢复 9.6 ms |
| 玩家热增量 | 0.5–3 s | 坐标/HP/buff，2.7 KB/房 | 可忽略 |
| 高价值事件 | 实时 | 充值/交易/装备，L0 批量、L1 批量+fsync | 1.55 M/s / 45 k/s |

恢复顺序固定：**房间全量 → 重放增量 → 补事件日志**，三者都带版本号，基线不匹配就拒绝叠加（E2 实测过这个保护有效）。

**验收**：kill -9 房间进程后，恢复 ≤50 ms、账目零丢失、冷数据哈希一致（S5/E2 已达成）。

### 4.8 wasm 业务模块

### 4.9 RPC 与集群

```php
// 业务侧写法统一，本地/远程透明
$result = TSF\Rpc::call('world.rank', 'topN', [100], timeoutMs: 500);

// 集群
TSF\Cluster::nodes(): array;                   // 存活节点
TSF\Cluster::route(string $service, string $key): string;  // 一致性哈希
TSF\Cluster::onNodeDown(callable $cb): void;
```

- 注册中心：起步用 Redis（简单、够用），后期可换 etcd/consul；
- 分片：一致性哈希 + 虚拟节点（每物理节点 150 个），节点变更只迁移 1/N 数据；
- 超时/重试/熔断：默认超时 200 ms、重试 1 次（幂等接口）、连续失败 20 次熔断 5 s。

**验收**：跨服 RPC p99 ≤2 ms（同机房）；节点下线后 3 s 内路由完成收敛。

## 六、与早期构想（typeGame.md）的两处修正

`typeGame.md` 是验证之前的构想，其中两条假设被实测推翻，这里明确改掉，避免团队按旧假设排期：

| 早期构想 | 实测结论 | 现在的方案 |
|:--|:--|:--|
| 网络层引入 libhv（C++ 库 + stub 桥接） | Swoole 已在 AOT 下跑通（S4 房间进程、S6 压测 3,300 在线/worker 都跑在 Swoole 上）；libhv 需要额外写 stub 且**未验证** | **用 Swoole**，不引入 libhv。省掉一次未验证的桥接，也少一个长期维护点 |
| 内嵌 Zend VM + 运行时 `require` 实现脚本热更 | `embedded-files` 确实支持运行时 `require`，但它是从**构建期生成的 opcode 表**加载，**改磁盘 PHP 文件不生效**；`eval()` 与动态 `include` 对 AOT/Native Class 不可用 | **三级热更**（配置数据 / wasm 模块 / 滚动重启），见 §1.4 |

第一条修正省钱省风险；第二条修正更重要——**它是"能不能用 PHP 取代 Lua"这个问题上唯一的硬约束**。结论是：可以取代，但热更方式不同，必须从第一天就按三条轨道设计。

## 八、v1 的完成定义

**场景验收**

**⚠️ M1 三行的问题（2026-11-13 复核发现）**

1. **"单 worker 在线 4,300" 是用裸转发数据算的，但生产一定开网关层。**
   裸转发 43k → 4,300 人；开网关后 35k → 3,500 人。目标应该按"开网关"的口径定，
   要么把网关层开销压下去（现在 −19%），要么把目标下调到 3,400。
2. **"单消息 CPU 成本 22.96 µs" 是负载的函数，不是常数。**
   同一份二进制在 45k msg/s 时是 21.9 µs，在 38k 时是 26.3 µs。报单点值等于没报，
   应写成"在 X msg/s 负载下 ≤Y µs"。
3. 这几项都是端到端压测，**受机器负载影响远大于代码改动**（实测同机波动 12%），
   复测必须用 harness 的配对比较 + 离散度检查，不能单跑一次。

**复核总结（2026-11-13，全部 -O2）**

| 结论 | 数量 | 项 |
|:--|:--:|:--|
| ✅ 达标 | 10 | Service 延迟/吞吐、信箱上限、定时器、跨进程往返、慢消息检测、Room 帧耗时、Room 无泄漏、AOI 单次更新、codec 增益 |
| ⚠️ 目标口径有问题 | 3 | 单 worker 在线（裸转发 vs 开网关）、单机在线、单消息 CPU 成本（是负载函数） |
| ❌ 未达标（已改判） | 1 | AOI 整帧 1000 人 ≤50 µs（物理下限约 200 µs） |
| ⏳ 未做 | 4 | 跨进程 RPC p99、热更三项、崩溃零丢失、watch 生效时间 |

> 上面这 4 项「未做」指的是**那一轮复测没覆盖**，不是没实现：它们分别在 §13（RPC p99 377 µs）、§20（热更 34 ms / 坏数据拒收 / 万行表 71~106 ms）、§12.9（1,000 笔 kill -9 零丢失）、§24（watch 1.45 s）里已经测过。这张表是当时的快照，不改写它，只在此标注。

**下一步真正该做的**（按性价比排序）：

1. ~~1 万连接时的 OOM~~ **已修复**（2026-11-13）。根因不是泄漏：Swoole 每连接约 64 KB
   计入 **per-thread** 的 `memory_limit`（php85 是 ZTS 版本），单 reactor 阈值正好是
   `512MB ÷ 64KB = 8192`。`Server::ensureMemoryLimit()` 已按 `max_conn` 自动抬高，
   2 万连接在 2G 上限下跑通。完整排查链见 README §5.11。

2. **T1-07 的 CPU 指标必须改口径**。实测边际成本 **23.6 µs/消息**、固定开销 **0.33 核/worker**，
   10 万 msg/s 需要 **约 2.7 核**，而原指标写的是 0.6 核——差 4.5 倍。
   建议改成「单核 60% 承载约 1.1 万 msg/s」，或按场景分别给（@1Hz 心跳 vs @10Hz 操作）。

3. **网关层 −19% 吞吐要不要处理**——要么接受（把目标调成 3,400/worker），
   要么把鉴权/限流前移到独立接入层。这是产品决策，不是优化问题。

4. 其余 ⏳ 项都属于 M5/M6/E 阶段，按计划推进即可。

## 架构决策记录

### D-01 玩法功能一律做成可选包（2026-11-13）

判据不是"重不重要"，而是**"是否所有游戏都要"**。棋牌不需要帧循环和视野，SLG 不需要
50ms 帧同步，MMO 两个都要——这类东西焊进框架，等于逼所有人替别人的需求付费
（编译时间、产物体积、维护面）。

落地：`tsf/pkg/<name>/` + `pkg.json`（ns/desc/requires）+ 工程 `project.json` 的 `packages`。
`tsf list/add/remove` 管理，`tsf build` 只把声明的包编进 `project.yml`。
**没声明 = 不在产物里**，不是运行时开关。

已迁出的包：`entity`（可移动实体）、`frameloop`（帧循环）、`room`（房间，依赖前两者）、
`aoi`（九宫格视野）。核心只剩 Kernel/Protocol/Transport/Gateway/Service/Timer/Cluster。

拆分的粒度标准：**每个包都要能回答"什么场景下我会单独用它"**。
`room` 原本把实体+状态机+帧循环捆在一起，棋牌要房间却不要帧——所以拆开，
且 `Room` 本身不依赖定时器（`RoomService` 的 `autoFrame=false` 可关帧驱动）。

### D-02 不引入 ECS（2026-11-13，实测）

ECS 的性能前提是连续内存 + 顺序遍历。实测 AOT PHP 下（`bench/probe-ecs`，1000 实体更新位置，-O2）：

| 写法 | 单实体 |
|:--|--:|
| 对象数组（当前做法） | **99 ns** |
| 组件并行数组（SoA） | 332 ns |
| 组件哈希表（常见 PHP ECS） | 368 ns |

**对象反而快 3.4 倍**——AOT 下每次数组下标都要边界检查和取值，`-O2` 优化不掉这部分，
而对象方法体可以被充分优化。ECS 只在"新增实体"上占优（117 vs 192 ns），但那是低频操作。

另外两条理由：一房一 Service 串行调度已经消除了 ECS 想解决的并发写问题；
真需要组合式行为时，组合对象比整套 ECS 机器便宜。

**结论**：不引入 ECS 框架。若某个热点循环实测不够快，可以局部改 SoA（优化手段，不是架构）。

### D-03 所有基准必须走 `tsf build`（2026-11-13，测量事故复盘）

手写的 `project.yml` 只写了 `sources:`，漏掉了 `cxx-flags: -O2`。结果是**在 -O0 上跑了整轮基准**，
所有性能数字偏低约一倍，还导致误判：

| 指标 | -O0（当时报的） | -O2（实际） |
|:--|:--:|:--:|
| 单服务吞吐 | 510k msg/s | **1,161k msg/s** |
| 单条消息 | 1,959 ns | **861 ns** |
| 10 万定时器误差 | max 5 ms | **0 ms** |
| 200 实体单帧 | 176 µs | **67 µs** |
| AOI 格内移动 | 940 ns | **322 ns** |

最直接的后果：吞吐**早就达标了**（116 万 vs 目标 50 万），我却为了"差 2% 未达标"
花了半轮做微优化，还把参数从 -O2 的编译结果里推导了一堆错误结论。

对策：工程一律用 `project.json` + `tsf build`（自动写全 `cxx-std`/`cxx-flags`），
禁止手写 `project.yml`。已把 bench 下所有工程改造完毕。
