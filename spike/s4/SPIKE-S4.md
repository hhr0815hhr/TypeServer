# Spike S4 —— 房间能否独立成子进程（崩溃半径）

> 执行时间：2026-11-12
> 环境：WSL2 Ubuntu 22.04 / tpc v0.9.6 原生 AOT（Linux + GCC）/ Swoole 6.2 / PHP 8.5.12 ZTS
> **结论一句话：能，而且很干净——`Swoole\Process\Pool` + 协程 + AOT 全部可用，杀掉一个房间只影响它自己，重启 4 ms，其他房间 tick 连续。但 Swoole 没有任何重启退避，且协程模式下「一个房间卡住 = 200 个房间一起卡」的实测差距是 1.8 秒。**

---

## 一、结论

| 待验证项 | 结论 | 实测 |
|:--|:--:|:--|
| AOT 能否编译 `Swoole\Process\Pool` | ✅ | 原生二进制 114 KB，6 个翻译单元，约 40 s 编译 |
| worker 内协程能否调度 | ✅ | 两个协程通过 `Channel` 通信，200 ms 心跳稳定 |
| 杀掉一个房间是否只影响它自己 | ✅ | 房间 1 换 pid，其余 3 个 **pid 不变、tick 连续**（30 → 46） |
| 重启耗时 | ✅ | **3.7–6.9 ms**（首次含首拍 27.7 ms） |
| 是否有重启退避 | ❌ **没有** | 连续 kill 10 次，每次都在 3.7–4.4 ms 内复活，无任何节流 |
| 是否累积僵尸进程 | ✅ 无 | 始终 4 worker + 1 parent |
| 单房间内存（进程模式） | ⚠️ **19.6 MB** | parent 42 MB |
| 单房间内存（协程模式） | ✅ ~0 | 200 房间共 47 MB |
| 协程模式的隔离缺陷 | ❌ **确认存在** | 一个房间烧 1.5 s CPU → 其他 199 个房间 5 秒内少跑 **18 个 tick**（46 → 28） |

## 二、实测明细

### 2.1 AOT 原生构建可用，但有两个语法约束

`tpc project.yml`（不带 `--wasm`）走的是 Linux + GCC 原生后端，输出 `room_pool`：

```
Initialized platform/backend: Linux + GCC (g++)
[pch] cache: .../typephp_pch.hpp.gch
Starting parallel compilation with 4 jobs for 6 files
Successfully compiled 6 files
Build successful: room_pool          # 114 KB，动态链接 libphpx / libphp
```

两个实测踩到的约束：

| 约束 | 现象 | 处理 |
|:--|:--|:--|
| 入口必须是 `main()` | 顶层 `echo` 报 `Unsupported statement: Stmt_Echo` | 全部逻辑放进 `main()` 及被它调用的函数 |
| `go()` 短函数不存在 | 运行时报 `function 'go' is undefined` | 用 `Swoole\Coroutine::create()` |

第二条尤其值得记：`go()` 是 Swoole 的全局短名函数，AOT 环境里没有注册，编译期不报错、运行期才炸。

### 2.2 房间独立进程：崩溃半径 = 1 个房间

```
== 初始状态 ==
room 0: pid=31252 tick=30
room 1: pid=31253 tick=30
room 2: pid=31254 tick=30
room 3: pid=31255 tick=30

== kill -9 房间 1 (pid=31253) ==
房间 1 新 pid=31308, 恢复耗时 0.0069 s

== 事后状态 ==
room 0: pid=31252 (原 31252) tick=46 (原 30)
room 1: pid=31308 (原 31253) tick=16 (原 30)   ← 只有它换了 pid，计数归零
room 2: pid=31254 (原 31254) tick=46 (原 30)
room 3: pid=31255 (原 31255) tick=46 (原 30)
```

三个观察点：

1. **其余房间 pid 完全没变**，tick 从 30 连续推进到 46（1.6 秒 × 10 Hz，符合预期）——说明没有连带重启；
2. **被杀房间的 tick 归零**——内存态丢失，这印证了架构文档的判断：进程隔离只解决"不连累别人"，要"不丢状态"必须配快照/迁移链；
3. **恢复 6.9 ms**，后续重复测量 3.7–4.4 ms。

### 2.3 关键缺口：Swoole 没有重启退避

连续 kill 同一个房间 10 次：

```
第  1 次: 31667 -> 31689, 恢复 0.0277 s
第  2 次: 31689 -> 31702, 恢复 0.0039 s
第  3 次: 31702 -> 31711, 恢复 0.0040 s
...
第 10 次: 31783 -> 31793, 恢复 0.0038 s
```

**每一次都在 4 ms 内复活，没有任何退避或强度限制。** 这意味着：如果某个房间存在"启动即崩"的 bug（比如加载了坏配置、连不上 DB），它会以 250 次/秒的频率无限重启，把 CPU 和日志打爆。

架构文档 §10 提过这条，现在有了实测证据。**必须在业务层自己实现监督**：

```
60 秒窗口内重启次数 > N（建议 3）→ 停止创建该房间 + 告警 + 标记隔离
```

### 2.4 协程模式的代价：一个房间卡住，200 个房间一起卡

200 个房间跑在同一个进程的协程里（`Swoole\Coroutine::create`），对比有无 CPU 占用：

| 场景 | 5 秒内 room0 的 tick 增量 | 折算 |
|:--|:--:|:--|
| 无 CPU 占用 | **46 次**（理论 50） | 正常，8% 调度开销 |
| 一个房间烧 1.5 s CPU | **28 次** | **少跑 18 拍 ≈ 停摆 1.8 秒** |

`Swoole\Coroutine::sleep` 会让出，但纯 CPU 循环不会——PHP 协程没有指令级抢占，一个房间的长计算会把整个进程里所有房间一起按停。这与 S3 在 wasm 层测到的结论一致（wasm 的 epoch 能打断，PHP 协程不能）。

内存侧则完全相反：200 个协程房间共 **47 MB**（≈0.24 MB/房间），而进程模式 200 个房间要 **3.9 GB**。

## 三、两难与结论：房间必须分级

| 维度 | 协程模式（单进程 N 房） | 进程模式（1 房 1 进程） |
|:--|:--:|:--:|
| 内存/房间 | **~0.24 MB** | **19.6 MB**（82 倍） |
| 崩溃半径 | 整个进程（200 房） | **1 个房间** |
| CPU 长任务影响 | **全部房间停摆** | 只影响自己 |
| 重启成本 | 不可能（进程内无重启概念） | **4 ms** |
| 状态丢失范围 | 全进程 | 单房间 |

**没有任何一种模式能同时满足"便宜"和"隔离"，所以房间必须分级**：

| 房间类型 | 模式 | 理由 |
|:--|:--|:--|
| 对局 / 战场 / 活动副本 | **独立子进程** | 玩家密度高、状态价值高、数量可控（单节点几十个） |
| 大地图分线 | 独立子进程 + 分片 | 同上，且天然对应"分线"边界 |
| 挂机房 / 个人房间 / 离线托管 | **协程** | 数量上千，单房价值低，卡一下可接受 |

按 19.6 MB/房间算，一个 8 GB 节点能承载约 **200 个进程房间**（不含 wasm 宿主）；若某房间还要内嵌 wasm 宿主，再加 50 MB（S2 结论），就不适合一房一进程了——**wasm 宿主应该放在"跑玩法逻辑的进程"里，而不是"每个房间进程"里**。

## 四、对 E4 的落地建议

原提案是「房间用独立子进程 + `rest_for_one`」。实测后修正为：

1. **`Swoole\Process\Pool` 可用，但只提供"拉起"不提供"治理"**——重启强度、崩溃计数、隔离标记都得自己写，这部分是本项工作真正的工作量；
2. **重启 4 ms 足够快**，因此"崩溃后重建房间 + 从快照恢复"是可行路径（快照恢复耗时取决于状态大小，需 S5 标定）；
3. **协程不能承载"可能卡住"的逻辑**——若某个玩法含不确定复杂度（AI 寻路、大范围 AOI、玩家自定义脚本），必须进进程或进 wasm（S3 已证明 wasm 能 10 ms 内切断）；
4. **不要一房一进程地塞 wasm 宿主**：19.6 + 50 ≈ 70 MB/房间，成本会失控。

## 六、S4 判定

**通过，但暴露了一个必须在业务层补的缺口。**

- 「房间独立进程」这个原语成立：4 ms 重启、零连带、tick 连续，足以支撑"一个房间崩了只让该房间玩家重连一次"；
- 「协程承载房间」在内存上便宜 82 倍，但 1.8 秒的实测停摆证明了它不能承载不确定复杂度的玩法；
- **Swoole 不提供重启退避**，这是 E4 里最容易被漏掉、也最容易在线上炸的一环——必须在监督层自己数。

三关（S1/S2/S3）验证的是"wasm 能不能用"，S4 验证的是"崩溃半径能压到多小"。两项合起来，E1 与 E4 的技术前提都已具备，接下来对架构形状影响最大的就是 **S6（单 worker 安全在线数）** 和 **S5（崩溃恢复时延）**。
