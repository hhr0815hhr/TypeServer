# Spike S5 —— 崩溃恢复时延（两级快照）

> 执行时间：2026-11-12
> 环境：tpc v0.9.6 原生 AOT / Swoole 6.2 / PHP 8.5.12 / WSL2 ext4
> **结论一句话：50 人房间的端到端恢复 9.6 ms，200 人大房间 54 ms，冷数据零损坏、op 零丢失（相对最新增量）。两级方案完全成立，但暴露了一个必须处理的新问题——60 个房间同时恢复要 152 ms，是单房恢复的 15 倍，属于惊群效应。**

## 二、方案回顾

```
第 1 层  每 0.5 s  玩家热状态增量（坐标/HP/MP），约 2.7 KB/房
第 2 层  每 5 s（±20% 抖动）  房间全量（共享态 + 背包冷数据），约 143 KB/房
恢复     读全量 → 校验 base == snap.ops → 叠加增量 → 起主循环
```

关键实现细节（都在代码里）：增量只写 `[x,y,hp,mp]` 四个热字段，全量才写背包；房间周期带确定性抖动（`room % 10`）避免同刻落盘；状态文件末位记录**恢复瞬间的 ops**（`fixedOps`），否则重启后继续跑会污染判定——这一点第一次测就踩到了。

## 三、实测数据

### 3.1 小房间（50 玩家，143 KB 全量 / 2.7 KB 增量）

连续 kill 5 个不同房间：

```
room 3      9.51 ms  (房内自测 3.263 ms)  ops 50->50  冷哈希✓  模式=restore
room 11     9.01 ms  (房内自测 2.079 ms)  ops 50->50  冷哈希✓  模式=restore
room 25    10.11 ms  (房内自测 2.202 ms)  ops 50->50  冷哈希✓  模式=restore
room 42    10.11 ms  (房内自测 1.916 ms)  ops 50->50  冷哈希✓  模式=restore
room 58     9.35 ms  (房内自测 2.798 ms)  ops 50->50  冷哈希✓  模式=restore

平均端到端恢复: 9.61 ms
单次全量写盘最大 4 ms
全量快照 8.58 MB / 60 房 = 143 KB/房
```

拆解端到端 9.6 ms：**进程重启 ≈4 ms**（S4 实测）+ **房内恢复 1.8–3.3 ms** + 状态检测延迟（2 ms 轮询）。

### 3.2 大房间（200 玩家 × 200 件背包，2.17 MB）

| 房间 | 端到端 | 房内自测 |
|:--|:--:|:--:|
| room 2 | 51.63 ms | 32.34 ms |
| room 9 | 54.36 ms | 31.99 ms |
| room 17 | 57.12 ms | 37.74 ms |

体积放大 15 倍（143 KB → 2.17 MB），恢复耗时放大 13–15 倍，**近似线性**。折算反序列化吞吐约 **66 MB/s / 4 万对象**——比纯字节吞吐（171 MB/s）慢，说明**反序列化成本由对象数量主导，不只是字节数**。这给出一个直接优化方向：把 40,000 个小 Item 对象压成定长数组，能显著降低恢复时间。

### 3.3 增量基线校验（安全机制验证）

把 room 5 的 `delta.base` 从 46 改成 1045（故意不匹配），重启后：

```
room 5: mode=restore  fixedOps=46   ← 拒绝叠加，回落到快照（快照 ops=46）
room 6: mode=restore  fixedOps=65   ← 正常叠加（delta.ops=65）
```

room 6 相对快照多恢复 18 个 op，**相对最新增量丢失 0 个**。

这条验证很有必要：如果不做 base 校验，增量会被错误叠加到旧基线上，产生**静默的状态错乱**——线上极难排查，而且往往表现为"偶发资产异常"。

### 3.4 惊群效应：全量重启的真实代价

同一时刻拉起 60 个房间进程，全部走恢复路径：

```
60 房同时恢复总耗时: 151.77 ms
（单房冷启动恢复 1.8 ms，放大 84 倍）
```

原因：60 个进程同时读盘（8.58 MB）+ 同时反序列化（240 万对象）+ 4 核争用。**单房恢复再快，也抵不过同时恢复。**

这不是 S5 的"失败"，而是必须写进运维设计的约束：

| 场景 | 处理 |
|:--|:--|
| 单房崩溃（常态） | 直接恢复，9.6 ms，无需限流 |
| 全服重启 / 分批发布 | **必须限流**：每批 5–10 个房间，间隔 100 ms；或按分片渐进拉起 |
| 灾难恢复（整机） | 从最近的快照批量加载，按房间优先级排序（高价值房间先起） |

## 四、三个可用于实现的结论

**1. 两级方案的成本结构是对的，但瓶颈在反序列化的对象数。**

- 143 KB / 50 人 → 2 ms；
- 2.17 MB / 200 人 → 33 ms；
- 若压成定长数组（减少 4 万个小对象），预计可再降 30–50%。

**2. 增量层几乎免费，但同时是最该防错的一层。**

增量 2.7 KB / 0.5 s，60 房合计约 324 KB/s，成本可忽略。但它承载"最后 0.5 秒"的正确性，所以必须带版本号且校验基线——实测证明这道校验是有效的，且没有它就会静默错乱。

**3. 恢复时延的天花板不在本层，在进程启动。**

50 人房间端到端 9.6 ms 里，4 ms 是进程重启（S4），2 ms 是检测延迟。**继续优化序列化，收益上限只有 3 ms**；要再往下压，得优化进程启动或减少检测延迟（如用事件通知代替轮询）。

## 六、S5 判定

**通过。** 三个数字：

1. **9.6 ms**：50 人房间端到端恢复（含进程重启），比"< 3 秒"的目标好 300 倍；
2. **0 丢失**：相对最新增量 op 数为零，冷数据哈希 5/5 一致；
3. **152 ms**：60 房同时恢复的惊群代价——这是唯一需要在工程上额外处理的问题，解法是限流分批，不是优化代码。

配合前面几关：S1 证明 wasm 可以 0.87 µs 调用、S2 证明能嵌进进程（55 MB）、S3 证明卡死能 10 ms 切断、S4 证明崩溃半径能压到一个房间、S6 给出单 worker 3,300 人的容量基线——**E1/E2/E4 的技术前提已全部具备**，剩下的是工程实现与真机校准。
