# E2 一级落地 —— 高价值写操作的事件溯源

> 执行时间：2026-11-12
> 环境：tpc v0.9.6 原生 AOT / PHP 8.5.12 / WSL2 ext4
> **结论一句话：零丢失与幂等都验证通过。但吞吐数据给出了一个硬约束——逐条 fsync 只有 487 条/s，比批量写慢 300 倍，所以「每条高价值操作都同步落盘」这条路走不通，必须批量 fsync。好消息是进程崩溃（kill -9）本身不丢数据，游戏服最常见的崩溃场景不需要 fsync 兜底。**

---

## 一、结论

| 待验证项 | 结果 | 实测 |
|:--|:--:|:--|
| 快照 + 重放能否精确恢复 | ✅ | 快照 seq=900 + 重放 100 条 → 与期望状态**完全一致**（gold=142570, items=666, fp=452520979） |
| 幂等（重复投递） | ✅ | 每条投递两次：应用 100、跳过 1900，指纹不变，**无重复扣款** |
| 进程崩溃（kill -9）不丢已写事件 | ✅ | 写 5000 条后 kill -9，行数 5000 → 5000 |
| 逐条 append 吞吐 | ✅ | **161k 条/s** |
| 批量（100 条/次）吞吐 | ✅ | **1.55M 条/s**（9.6 倍） |
| 逐条 fsync 吞吐 | ❌ | **487 条/s**（慢 300 倍） |
| 批量 + 每批 fsync | ✅ | **44.9k 条/s**（比逐条 fsync 快 92 倍） |
| 全量重放速率 | ✅ | **1.2M 条/s**（2 万条 16 ms） |

## 二、实现结构

```
写路径：业务操作 → 生成事件(seq|type|a|b) → 追加日志 → 应用到内存态
                      ↑ 批量缓冲，满 100 条或超时一次写入

恢复：读快照(状态 + appliedSeq) → 重放 seq > appliedSeq 的事件 → 幂等去重
```

事件只有三种，覆盖三类高价值写：

| 类型 | 语义 | 字段 |
|:--|:--|:--|
| `charge` | 充值 | 金额 |
| `trade` | 交易（花金币换物品） | 价格、物品 id |
| `equip` | 装备获得 | 物品 id |

**幂等键是 `seq`**：状态里保存 `appliedSeq`，凡是 `seq <= appliedSeq` 的事件一律跳过。这一条同时解决了"重复投递"和"重放越界"两个问题，实现只有一行判断，但必须存在——否则重放会把交易重复扣款一次。

## 三、实测数据

### 3.1 零丢失验证

```
=== 生成 1000 条事件，快照点 900 ===
expected: seq=1000 gold=142570 items=666 fp=452520979

=== 崩溃恢复：快照(900) + 重放 901..1000 ===
recover: 快照 seq=900 日志行数=1000 实际应用=100 跳过=900 耗时=0ms
actual:   seq=1000 gold=142570 items=666 fp=452520979

正常重放 vs 期望: 一致 ✓（零丢失）
```

`跳过=900` 正是快照之前的事件被幂等挡掉——说明"快照 + 尾部重放"这条路径没有重复应用。

### 3.2 幂等验证

```
=== 每条事件重复投递两次 ===
recover: 快照 seq=900 日志行数=1000 实际应用=100 跳过=1900
actual:   seq=1000 gold=142570 items=666 fp=452520979

重复投递 vs 期望: 一致 ✓（幂等生效，无重复扣款）
```

1900 = 900 条快照前的 + 100 条尾部各一份重复。**处理了 2000 次投递，账目分毫不差。**

### 3.3 吞吐：fsync 是分水岭

```
逐条 append    : 20000 条 / 123 ms = 161525 条/s
批量(100)      : 20000 条 /  12 ms = 1550030 条/s
逐条 + fsync   :   200 条 / 410 ms =    487 条/s
批量 + 每批fsync: 5000 条 / 111 ms =  44911 条/s
```

三点解读：

1. **批量写比逐条快 9.6 倍**——纯粹是 syscall 次数差异（20000 次 vs 200 次）；
2. **逐条 fsync 是灾难**：487 条/s，意味着一台服每秒只能处理 487 笔高价值操作，一个热门区服的充值+交易峰值轻松超过这个数；
3. **批量 fsync 是可用的折中**：44.9k 条/s，损失的是"最近 100 条或 N ms"的持久性窗口。

### 3.4 进程崩溃不丢数据

```
=== kill -9 前后行数 ===
kill 前 5000 行，kill 后 5000 行
```

这条结论很重要：**append 成功即进入 page cache，进程被 kill -9 不会丢弃**。所以"游戏服崩溃"（进程级）这个最常见场景，不需要 fsync 兜底。fsync 防的是**机器崩溃/断电**（page cache 掉电丢失），那是另一类风险，窗口通常是几秒。

### 3.5 重放不是瓶颈

```
全量重放: 20000 条 / 16 ms = 1200190 条/s
```

按 S6 的容量基线推：单 worker 3,300 在线、高价值操作占比 5% → 约 1,650 条/s。**一小时全量事件 590 万条，重放约 4.9 秒**——超过 3 秒目标，所以快照是必需的；若快照每 60 秒一次，尾部只有 9.9 万条，重放 **82 ms**。

## 四、三个落地结论

**1. 三级持久性，按操作价值分配。**

| 级别 | 写法 | 吞吐 | 防什么 | 适用 |
|:--|:--|:--:|:--|:--|
| L0 | 批量 append，不 fsync | 1.55M/s | 进程崩溃 | 普通交易、装备、掉落 |
| L1 | 批量 + 每批 fsync | 45k/s | 进程崩溃 + 断电（窗口 100 条/N ms） | 充值、大额交易 |
| L2 | 逐条 fsync | 487/s | 断电（窗口 1 条） | 仅极端场景，一般不要用 |

按 S6 的数据，L1 的 45k/s 对单 worker 的 1,650 条/s 有 27 倍余量，**充值走 L1 完全够用，不需要 L2**。

**2. 幂等键必须落进状态，不能只靠日志去重。**

`appliedSeq` 存进快照，恢复时先看它——这比"扫日志找最大 seq"简单，也比"消费端维护已处理集合"省内存。代价是每次应用事件都要更新一个字段。

**3. 快照与日志的先后顺序不能错。**

落快照前必须先把已产生的事件 flush 到日志（代码里 `gen` 就是这么做的）。反过来的话，快照里包含了 seq=900 的状态，但日志里 901 之后的事件还没写——崩溃后那段就真丢了。这个顺序在 S5 的报告里也提过，属于同一条纪律。

## 五、与 S5 的关系

两层是配套的，缺一不可：

| 层 | 解决的问题 | 实测 |
|:--|:--|:--|
| S5 快照 | 恢复**快**（9.6 ms） | 房间级全量 + 玩家热增量 |
| E2 事件日志 | 恢复**准**（零丢失、可审计） | 高价值写操作 append-only |

正确顺序：**快照 → 重放事件日志 → 补偿未落快照的尾部**。S5 已实现前两步，E2 补的是第三步的"精确性"。

## 七、E2 一级判定

**通过。** 三个数字：

1. **零丢失**：快照 + 重放与期望状态指纹完全一致，重复投递下也一致；
2. **487 条/s**：逐条 fsync 的上限——这条数据直接否掉了"每条都同步落盘"的方案；
3. **1.55M/s 写、1.2M/s 读**：批量写的吞吐远超业务需要，真正的成本在 fsync 策略选择上。

**剩余工作（属于实现，不是验证）**：把日志从本地文件换成 Kafka/Redis Stream、按 `uid` 分区保证单玩家有序、日志清理与归档策略、以及"重放时与快照版本对齐"的版本号机制。

这套东西现在的形态是"能证明正确性"的最小实现，直接接生产还需要补分区与外部存储——但**正确性模型（幂等键、flush 顺序、快照边界）已经用实测钉住了**，换成任何存储后端都成立。
