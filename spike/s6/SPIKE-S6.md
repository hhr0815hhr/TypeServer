# Spike S6 —— 单 worker 能承载多少在线

> 执行时间：2026-11-12
> 环境：WSL2 Ubuntu 22.04 / tpc v0.9.6 原生 AOT / Swoole 6.2 / PHP 8.5.12 ZTS / 4 核
> **结论一句话：一个 worker 在 WSL2 上约能吃下 4,800 玩家（10 Hz 心跳）的理论上限，按 70% CPU 留余量实测建议按 3,300 算。每包 CPU 成本 20.9 µs，其中约 12 µs 是 WSL2 的系统调用开销、5.4 µs 是 Swoole+PHP 事件分发、3.6 µs 是业务状态写入。**

---

## 一、结论

| 待验证项 | 结论 | 实测 |
|:--|:--:|:--|
| 单 worker 逐级加压表现 | ⚠️ 3000→6000 之间有拐点 | CPU 6% → 21% → 76% → 95% |
| p50 延迟 | ✅ 3000 连接以内 < 0.5 ms | 200:0.38 / 1000:0.35 / 3000:0.50 / 6000:**74.78** ms |
| p99 延迟 | ❌ **本机测不准** | 连纯 C 回环服务在 3000 连接时 p99 也 100 ms+ |
| 每包 CPU（PHP+对象状态） | ⚠️ **20.9 µs** | 1000/3000 连接下稳定在 20.9–21.9 |
| 每包 CPU（PHP 无状态回环） | — | 17.3–18.4 µs |
| 每包 CPU（纯 C 回环） | — | **11.9 µs**（WSL2 系统调用底噪） |
| 内存/连接 | ✅ 很小 | RSS 42.9 → 62.8 MB（200→6000 连接）≈ **3.5 KB/连接** |
| 单 worker 容量（10 Hz 心跳） | ⚠️ 保守值 | **≈3,300 玩家/worker**（70% CPU） |

## 二、方法：两次校正才让数字可用

### 2.1 第一版测出的是"批处理排队"，不是延迟

第一版压测端每 100 ms 把所有连接**同时**发一遍，结果：

```
conns=200    p50=2.24ms  p99=14.50ms
conns=1000   p50=8.75ms  p99=18.04ms
conns=3000   p50=33.07ms p99=72.08ms
conns=6000   p50=71.72ms p99=156.77ms
```

p50 随连接数线性增长，这是**一批包同时在跑**造成的排队假象。真实游戏里每个玩家的心跳时刻是分散的。

**修正**：给每条连接一个相位偏移（`next_ns = now + (idx % 100ms)`），把发送打散到 100 ms 窗口内。修正后 p50 立刻回到亚毫秒：

```
conns=200    p50=0.38ms  p99=22.62ms
conns=1000   p50=0.35ms  p99=31.56ms
conns=3000   p50=0.50ms  p99=168.45ms
conns=6000   p50=74.78ms p99=195.76ms   ← CPU 已 95%
```

### 2.2 第二个校正：p99 不可信，必须做 C 对照

3000 连接时 p99 就已经 168 ms，但服务器 CPU 只有 76%，不合理。于是写了一个**纯 C 的 epoll 回环服务**用同一份压测端打：

| 服务器 | 3000 连接 p50 | 3000 连接 p99 |
|:--|:--:|:--:|
| C 原生回环 | 0.34 ms | **80.75 ms** |
| PHP/AOT | 0.48 ms | 154.76 ms |

**连 C 服务器都有 80 ms 的 p99**——说明这个尾巴来自压测端与 WSL2（单线程客户端、syscall 昂贵、调度抖动），不是被测服务的性质。

因此本报告只采用三个可信指标：**p50、服务端 CPU%、每包 CPU 成本**。p99 留到真机复测。

### 2.3 压测端自身也到顶了

`/usr/bin/time -v` 显示 6000 连接 8 秒：用户态 0.92 s、**内核态 6.08 s**（78% CPU），35.7 万包 → 约 17 µs 系统调用时间/包。**WSL2 的 syscall 比裸机贵数倍**，压测端在 ~45k pkt/s 封顶。所以绝对吞吐不可比，改用每包 CPU 成本做横向对比。

## 三、每包 CPU 成本：三档拆解

同一压测端、同一连接数（3000），只换服务端实现：

| 服务端 | 每包 CPU | 相对 C 基线 | 说明 |
|:--|:--:|:--:|:--|
| 纯 C epoll 回环 | **11.89 µs** | — | WSL2 的 syscall 底噪 |
| PHP/AOT 纯回环（无业务） | **17.29 µs** | +5.4 µs | Swoole 事件分发 + PHP 闭包调用 |
| PHP/AOT + 对象状态 | **20.94 µs** | +9.1 µs | 再加 3.6 µs 业务写入 |
| PHP/AOT + 数组拷贝状态 | **21.46 µs** | +9.6 µs | `$s = $state[$fd]` 拷入拷出更贵 |

三点解读：

1. **框架固定成本约 5.4 µs/包**（Swoole 事件循环 + 闭包调用 + `$serv->send()`）——这是纯 AOT 也去不掉的；
2. **业务状态写入约 3.6 µs/包**——比预想高，说明 AOT 下的对象属性写入并非免费的指针操作；
3. **数组拷贝比对象属性再贵 0.5 µs**——量不大，但趋势明确：**用对象承载玩家状态，别用数组整块拷入拷出**。

### 容量换算

```
1 核 = 1,000,000 µs/s
20.94 µs/包 × 10 包/s/玩家 = 209.4 µs/s/玩家
单核理论上限 = 1e6 / 209.4 ≈ 4,780 玩家
按 70% CPU 留余量      ≈ 3,300 玩家 / worker
```

与实测吻合：3000 连接时 CPU 76%、p50 仍 0.5 ms；6000 连接时 CPU 95%、p50 崩到 75 ms。**拐点就在 3000 与 6000 之间**。

> 注意这是**保守下界**。WSL2 的系统调用开销远高于裸机（C 回环就要 11.9 µs，真机通常 2–4 µs），裸机上每包可能降到 10–12 µs，单 worker 容量有望翻 2–3 倍。这个数字必须上真机复测后才能用于正式容量规划。

### 内存不是瓶颈

RSS 从 42.9 MB（200 连接）到 62.8 MB（6000 连接），增量 20 MB / 5800 连接 ≈ **3.5 KB/连接**。加上 S4 的结论（进程模式 19.6 MB/房间），内存远早于 CPU 到达瓶颈——**瓶颈永远是 CPU，不是内存**。

## 四、对分片与分线的含义

按 3,300 玩家/worker（保守）与 4,800（理论）：

| 单服在线 | 需要的 worker 数 | 说明 |
|:--|:--:|:--|
| 1,000 | 1 | 单 worker 轻松承载 |
| 5,000 | 2 | 留 30% 余量 |
| 20,000 | 6–7 | 已接近单机合理上限 |
| 50,000 | 15–16 | 需多机，或按玩法拆分 |

三条结论：

1. **不要指望单 worker 扛万人在线**——10 Hz 心跳下，一人一包的成本已经把 1 核吃掉了约 1/4800；
2. **心跳频率直接决定容量**：从 10 Hz 降到 5 Hz，容量翻倍。这是最便宜的扩容手段，比加机器划算；
3. **分线人数建议按 2,500–3,000 设计**，留出 20–30% 余量给活动峰值与 GC 抖动——这个数字与 S4 的"房间分级"配合：大地图分线按 3,000 人切，战斗房间单独进程。

## 六、S6 判定

**通过，但必须带着两个限定使用。**

- **可用数字**：每包 20.9 µs（PHP+对象状态）、单 worker ≈3,300 玩家@10Hz（70% CPU）、3.5 KB/连接；
- **不可用数字**：p99 与本机 pkt/s 上限——WSL2 的 syscall 成本与单线程压测端把这两个指标污染了，必须上真机复测；
- **可立即采纳的优化**：玩家状态用对象而非数组（-0.5 µs/包）、心跳降频（收益翻倍）、单 worker 别超过 3,000 人。

这条结论同时修正了架构文档里"单机承载"的乐观假设：**10 Hz 心跳下，单机（4–8 worker）大致对应 1.3–2.6 万在线**，而不是原先设想的数万。容量规划应当以此为基线，并在真机复测后校准。
