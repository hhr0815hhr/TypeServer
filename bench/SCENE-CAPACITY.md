# 场景形态容量验证

> 执行时间：2026-11-23
> 问题：这套框架能不能同时撑住"大厅房间 / 万人世界 / 大量副本"这些形态？
> 结论：**能。三种形态在 20Hz 下余量都在 40ms 以上。**
> 复现：`bash bench/scene-scale/run.sh`

---

## 一、数据

单进程、单核、PHP 8.5.12 + opcache、AOT 产物。每项跑 5 轮取中位数。

| 形态 | 规模 | 单帧耗时 | 20Hz 余量 | 峰值内存 |
|:--|:--|--:|--:|--:|
| 万人世界（单场景） | 1 万实体 / 850 格 | **9.61 ms** | 40.4 ms ✓ | 4.0 MB |
| 大量副本 | 200 副本 × 20 人 | **2.07 ms** | 47.9 ms ✓ | 4.0 MB |
| 大量副本 | 500 副本 × 20 人 | **5.41 ms** | 44.6 ms ✓ | 4.0 MB |
| 混合 | 8000 人世界 + 100 副本 | **9.16 ms** | 40.8 ms ✓ | 6.0 MB |
| 对照：EntitySet 推进 | 1 万实体 tick | 2.60 ms | — | 6.0 MB |

### 规模扫描（单场景，5 万人口径的 20000×20000 地图）

| 实体数 | 单帧耗时 | 每万实体 | 20Hz |
|--:|--:|--:|:--|
| 10,000 | 9.98 ms | 9.98 ms | ✓ |
| 20,000 | 19.91 ms | 9.96 ms | ✓ |
| 30,000 | **44.78 ms** | 14.93 ms | ✓（贴线） |
| 40,000 | **69.54 ms** | 17.39 ms | ✗ |

**1→2 万是线性的，3 万起超线性。** 原因不是实现问题，是 AOI 的固有特性：
地图固定时增加人数 = 提高密度 → 每格人数上升 → 换格时要算的视野差集变大
（1 人/格时邻域 9 个，4 人/格时 36 个）。所以**"单场景能装多少人"取决于密度，
不是绝对人数**——同样 4 万人铺在 4 倍大的地图上，耗时会回到 20 ms 量级。

**读法**：50ms 是一帧的预算，上面是**纯逻辑**耗时（移动、换格、视野差集）。
广播编码与网络发送要另算——按 `REPORT.md` 的 1KB 包 23 µs/消息估算：

- 万人世界每帧约 250 个玩家换格（换格率 ≈ 2.5%），产生约 500 个"视野增量包"
- 500 × 23 µs ≈ **11.5 ms**
- 合计约 **21 ms/帧**，20Hz 下 CPU 占单核 42%

**内存是意外的亮点**：1 万实体只占 4 MB，AOT 下对象结构紧凑，没有 PHP 解释器的
per-object 开销。500 个副本实例（1 万实体）也是 4 MB——副本本身的容器开销可以忽略。

## 二、这份数据最初是错的，而且是错了两处

第一版跑出来是 **万人世界 121 ms、500 副本 65 ms，全部超标 2 倍以上**。
看起来很像真的：数字不离谱，刚好卡在"要用就得优化"的位置。

### 错因一：位移公式让所有实体每帧换格

```php
$x = ($i * 7 + $frame * 3) % $w;   // 错：每帧给所有人 +3
```

格子边长 200、每帧整体平移 3 —— 这个式子本身没错，但 `$frame` 对**所有实体**生效，
配合"格子 200"就变成每帧 1.5% 换格，再叠加另一处错误，放大成"全员换格"。

真实参数：20Hz 下玩家速度约 5 单位/帧，格子 200 → **换格率 ≈ 2.5%**，即每帧
250 人换格而不是 1 万人。

### 错因二：`Grid::move()` 的返回值当成新 key 用

```php
// 错
$oldKey = $g->cellKeyOf($i);
$newKey = $g->move($i, $x, $y);
if ($newKey === $oldKey) { continue; }
```

`move()` 的返回值是：`>= 0` = **旧**格子 key（换格了）、`-1` = 没换格、`-2` = 不存在。
注释里写得明明白白，是我没读就用。拿它跟 `cellKeyOf()` 比较，等于：
- 没换格 → 返回 -1，`-1 !== oldKey` → **判成换格**
- 换格了 → 返回 oldKey，`oldKey === oldKey` → **判成没换格**

**判断完全反了**：每一帧都在给 1 万个实体算"进出视野"，真正的换格反而被跳过。

### 两处叠加的结果

```
错位公式 + 反了的判断  →  25 万条视野变化/帧、121 ms  →  "万人世界撑不住"
正确用法            →  9,448 条视野变化/帧、9.61 ms  →  余量 40 ms
```

**差 12 倍，结论完全相反。**

### 为什么值得记下来

如果没查这两处，就会得出"AOI 需要增量维护"这种结论，然后去优化一个不存在的瓶颈——
而 `Scene` 的注释里已经论证过"不维护有向边表"才是对的（77,940 条的平方级膨胀）。

**同一份 bench，两处错误叠加，产出了一个"看起来非常像真的"错误答案。**
数字不离谱 ≠ 数据可信。判据是：**换格率、视野变化量这类"中间量"是否符合现实**——
25 万条/帧对应"每人每帧换 25 次视野"，这本身就荒唐，一眼能看出来。

以后跑容量测试，先看中间量是否合理，再看耗时。

## 三、能力边界（这组数据没覆盖的）

数据只说明"单进程能算多少"，不说明以下这些能撑住：

| 没测的 | 会怎么露出来 |
|:--|:--|
| **多进程下的世界一致性** | 同一个世界拆到两个进程，跨进程视野/战斗要走 `rpc`，延迟和顺序是另一个量级 |
| **副本的创建/销毁开销** | 这里只测"稳定运行"，没测"每秒新建 50 个副本"的瞬时成本（建场 20 人约 5 µs，看起来可忽略） |
| **广播的真实包大小** | 用 1KB 估算；实际"视野增量"包可能只有 100 字节，也可能因为打包策略涨到 4KB |
| **持久化** | 万人世界的状态落盘（snapshot/db）完全是另一条路径 |

**容量刻度**（实测，20Hz、纯逻辑、单核）：

| 单场景人数 | 纯逻辑 | 加广播估算（≈+11ms/万） | 判断 |
|--:|--:|--:|:--|
| 1 万 | 10 ms | ≈ 21 ms | 余量充足 |
| 2 万 | 20 ms | ≈ 42 ms | 可用，开始紧 |
| 3 万 | 45 ms | ≈ 67 ms | **超了**，该拆场景 |

所以**单场景实用上限约 2 万人**（20Hz）。要更多人，方向是**分区/分片**（把地图切开，
每个区域一个 Service），而不是优化 AOI ——因为超线性的根源是密度，优化常数改变不了斜率。

> 这一节原本是"线性外推 3 万 29ms / 5 万 48ms"。实测后 3 万是 44.78ms，差 54%。
> 原因：外推假设了"每万人的开销恒定"，而实际上地图固定时人数增加会抬高密度，
> 换格时的视野差集随之变贵。**外推在"自变量会改变系统内部比例"时不成立。**
