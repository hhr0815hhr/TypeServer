# 编解码下沉决策报告

> 执行时间：2026-11-12
> 问题：PHP 层实现的帧编解码，值不值得重写成 C++？
> **结论：值得，但收益是 +11~14%，不是最初测到的 +55%。**

---

## 一、结论（修正后）

同一二进制、只切 `protocol.frame` 配置、**交替采样 5 轮 + 配对比值 + MAD 剔除**（由 `bench/harness` 自动执行）：

| 包大小 | PHP codec | 原生 codec | 吞吐 | CPU/消息 |
|:--|:--:|:--:|:--:|:--:|
| 16 B（指令包） | 34,738 · 26.84 µs | **37,749 · 24.60 µs** | **+14.4%** | **−8.4%** |
| 1 KB（状态同步） | 37,220 · 26.58 µs | **41,415 · 23.71 µs** | **+11.2%** | **−10.7%** |

> 16B 那行来自 harness 的一次干净采样（5 轮全保留、比值 1.071–1.205、绝对离散度 11.8%），原始数据见 `results/codec-16B.json`。
> 1KB 那行来自早期交替采样（同样 5 轮），尚未用 harness 重测，数值可能与上表口径略有差异。

换算容量（10 Hz 心跳）：

- 单 worker：**3,772 → 4,303** 在线（按 1KB 那组绝对值；16B 组绝对值偏低，趋势一致）
- 单机 8 worker：3.0 万 → **3.4 万** 在线

代价：C++ 实现已写完（本次产出），接入约 1 人日；PHP 版保留为回退，可随时用配置切回。

**口径说明**：本报告所有百分比以"配对比值的中位数"为准，不以绝对中位数的差值为准——后者会被"某一轮机器整体变慢"带偏。两者的差别见第二节。

## 二、这篇报告最初写错了，原因值得记下来

第一版结论写的是"**+55% / +32%**"。复核后发现那是**单次采样的离群值**，不是真实收益。

错在哪：

| 项 | 第一版做法 | 问题 |
|:--|:--|:--|
| 每个模式只跑 1 次 | 单次采样 | WSL2 上 CPU 频率与后台负载波动可达 ±30% |
| 两个模式顺序跑（先 php 后 native） | 未抵消漂移 | 后跑的那个恰好赶上更"安静"的机器状态 |
| 用不同二进制的 bench 端对比 | 编译差异混入 | 变量更多 |

修正做法：**交替采样 + 配对比值**。每轮把两个变体各跑一次（A→B→A→B…），每轮算一次 `B/A` 比值再取中位数——同一轮内两个变体紧邻执行，机器共同漂移在做比值时被约掉。

修正后同一份 bench 复跑也从 52k 回落到 44k，证明 52k 确实是离群值。最终 5 轮干净采样：比值 1.071 / 1.144 / 1.177 / 1.087 / 1.205，中位 **1.144x（+14.4%）**，0/5 被剔除，绝对离散度 11.8%。

> 这套做法已固化成 `bench/harness`：交替采样、配对比较、MAD 剔除、离散度超阈值直接拒绝下结论。以后任何"快了多少"都走它，见 `harness/README.md`。

## 三、微基准（仅作参考，不能用来决策）

同一二进制内链入 PHP 与 C++ 两版，先自检等价性（编码逐字节一致、解码结果一致），再比性能：

| 包大小 | PHP encode | C++ encode | PHP decode+滑动 | C++ decode+滑动 |
|:--:|:--:|:--:|:--:|:--:|
| 64 B | 482 ns | 49 ns | 888 ns | 53 ns |
| 1 KB | 489 ns | 82 ns | 899 ns | 70 ns |
| 8 KB | 622 ns | 281 ns | 1066 ns | 289 ns |

两个有用的观察：

1. **PHP 版成本几乎与包大小无关**（64B 与 1KB 都是 ~880 ns）→ 是固定开销（函数调用、`ord/chr`、字符串拼接、返回数组分配），不是数据拷贝。这也解释了为什么真实服务端上 16B 与 1KB 的 PHP 吞吐几乎一样（37.7k vs 37.2k）。
2. **C++ 版按字节走**（8KB 时 281 ns）→ 大包时优势缩小。

微基准推算"每消息省约 1.3 µs"，实测省 **3.4 µs**（26.35 → 22.96）。差 2.6 倍，原因：真实路径里每帧还有数组分配、`substr` 缓冲滑动、三层调用，微基准没覆盖。

**结论不变：每包都要跑的优化，必须用端到端吞吐验证。**

## 四、剩余成本在哪（决定下一步该做什么）

原生版 22.96 µs/消息：

| 部分 | 量级 | 依据 |
|:--|:--:|:--|
| syscall（recv + send + epoll） | ~12 µs | S6 实测纯 C 回环 11.9 µs |
| Swoole 事件分发 + PHP 闭包调用 | ~5 µs | S6：PHP 回环比 C 回环多约 5.4 µs |
| 框架层（缓冲管理、派发） | ~1 µs | 待标定 |
| 编解码 | ~0.1 µs | 本次实测 |

**codec 已经不是杠杆了。** 下一步要压成本，只能动"每消息的 PHP 层调用"——例如把 echo/转发这类路径整体下沉。这是更大的改动，建议放到 M2 之后再评估。

## 五、过程中的三个问题（都已修复）

### 5.1 闭包按引用传参在 AOT 下静默不写回（危险）

第一版解码器是 `function (string $buf, int &$consumed)`，调用 `$dec($buf, $consumed)` —— `$consumed` 不会写回。

TypePHP 要求：**闭包/动态调用的引用参数必须显式 `toRef()`**。漏写的后果不报错，而是：`substr($buf, 0)` → 同一帧反复解析上千次 → **p50 从 0.2 ms 涨到 111 ms**，但吞吐看着"还行"。

已改为**返回值携带** `consumed`，彻底不用引用参数。

### 5.2 测试脚本自己有 bug，被更快的实现暴露

`frame-test.php` 原来的读帧函数是"读一块 ≤64KB、解出第一帧就返回"，用局部缓冲——两帧一起到达时丢第二帧。

对 PHP 版能过（慢，回包分两次到），换原生版立刻失败。**判据：只在慢实现上通过的测试，是在依赖时序。**

已改为按帧长度精确读。

### 5.3 Nagle 的猜测是错的

看到 111 ms 延迟，我怀疑服务端没开 `TCP_NODELAY`，并写进了代码注释。补做对照：

```
nodelay=on : p50=0.23ms p99=0.42ms
nodelay=off: p50=0.23ms p99=0.41ms
```

**闭路（请求-响应）场景下 Nagle 没有影响**——每连接只有一条未确认请求，Nagle 不会触发。111 ms 完全是 5.1 的 bug。

`open_tcp_nodelay` 仍默认开启（服务端**推送**小包时才重要），注释已改成实情。

## 九、2026-11-12 结构重构后的复测

把分帧实现从"注入闭包"改成"注入 `FrameCodec` 接口对象"后重新配对测量：

| 项 | 重构前 | 重构后 |
|:--|:--:|:--:|
| 16B 包 codec 收益 | +14.4% | **+13.3%**（另一次 5 轮测到 +7.8%，见下） |
| 网关层成本 | 记为"几乎零成本" | **−8% ~ −18%**（随机器状态浮动） |
| 解码结果承载 | `array{int,int,string,int}` | `DecodedFrame` 对象，快约 150 ns |

### 9.1 必须更正：`mixed` 参数并不慢

结构重构期间我曾得出"`mixed` 参数每帧装箱 30 µs，吞吐从 33k 掉到 16k"，
并据此把 `Gateway` 拆成 `send(string)` / `sendData(mixed)` 两个入口。**这个结论是错的。**

- 那次是**顺序采样**（先跑 mixed 版、再跑 string 版），前一段正好撞上机器抖动
  （同一轮 harness 报的变异系数 106%）；
- 严格做法：编两个只差一个类型声明的二进制，交替压测。

复现方式（脚本：`bench/patch-ab.php` + `bench/ab-mixed.php`）：

```bash
cd /data/TypeServer/demo
tsf new ab-mixed && tsf new ab-string
php85 ../bench/patch-ab.php      # 把两个工程的 handler 分别固定成 mixed / string
(cd ab-mixed && tsf build .) && (cd ab-string && tsf build .)
php85 ../bench/ab-mixed.php 5 3  # 交替 5 轮，配对求比值
```

结果：

```
第1轮  mixed=37,648  string=36,917  比值=1.020
第2轮  mixed=35,105  string=35,030  比值=1.002
第3轮  mixed=34,817  string=35,985  比值=0.968
第4轮  mixed=37,513  string=36,419  比值=1.030
第5轮  mixed=34,683  string=34,698  比值=1.000

中位比值 1.002x（区间 0.968 ~ 1.030）→ 无实质差异
```

微基准（`bench/probe-types`）一致：动态闭包下 `mixed` 参数 496 ns、`string` 参数 493 ns；
联合类型 `string|array` 反而略慢（524 ns）。

**结论**：避免 `mixed` 的理由是类型安全，不是性能。既然它不慢，
`send(string)` / `sendData(mixed)` 的拆分就不成立了，已合并回单一 `send(string|array|object)`。

### 9.2 仍然成立的更正

1. **codec 比值变小不是因为接口分派变贵。** 单独测分派成本（`bench/dispatch`）：
   接口方法 262 ns、具体类型 274 ns、闭包调用 **356 ns**——接口比闭包更快。
2. **网关不是零成本。** 原先那个"+0.7%"是 payload 重构前测的，真实值在 −8%~−18%
   （固定 PHP 开销 / syscall 成本这个比值天生随机器变快而变大）。判断退化看 bare 的绝对吞吐。
